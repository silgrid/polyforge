# Machine load (Debug panel)

The Debug panel shows the load of the machine pi-web runs on: CPU usage with the core count, load average 1/5/15 and memory used/total. Nothing else (no hostname, disk, uptime, per-core, process, path or environment value), no history, no thresholds, no settings entry. The "Session info" / "会话信息" popover once carried the same section; it no longer does and issues no machine-load request.

## Route: `GET /api/machine-load` (`app/api/machine-load/route.ts`)
- Behind the existing `/api` gate: `isApiRequestAllowed(request)` first, `403 { error: "Forbidden" }` on refusal. No new permission; same reach as every other `/api` route.
- Success is exactly `{ metrics: { cpuPercent, coreCount, loadavg, memoryUsedBytes, memoryTotalBytes } }`: the route copies those five fields from the sample, so a field added to the sampler never leaks. `cpuPercent` is `number | null`, `loadavg` is `[n, n, n] | null`.
- Degradation-first, like `/api/polyforge/status`: any sampling or assembly failure answers `200 { metrics: null }` with no error detail. The only non-2xx answer is the gate's 403; there is no 5xx path. `dynamic = "force-dynamic"` so Next never serves a cached sample. GET only.

## Sampler (`lib/machine-load.ts`)
- `createMachineLoadSampler({ os, now, platform, readProcStatus })` takes injectable `os`, clock, platform and the `/proc/self/status` text (used for `coreCount` on Linux) for tests; `machineLoadSampler` is the one process-wide instance the route uses.
- On demand only: `os` and `/proc/self/status` are read inside `sample()` and nowhere else. No timer, scheduler or background task, so with the Debug panel closed nothing samples.
- One fresh sample is shared for `MACHINE_LOAD_WINDOW_MS` (2000 ms): every request inside the window, from any client, gets the identical object from one `os` pass; the first request at or after `T + 2 s` samples again.
- CPU comes from the delta between two fresh `os.cpus()` reads (summed over all logical CPUs): `(Δtotal − Δidle) / Δtotal × 100`, clamped to 0..100. Never the since-boot average. The first sample of a process has no baseline and returns `cpuPercent: null` (the other fields are real); a zero `Δtotal` is null too. The baseline ages out: a sample more than `MACHINE_LOAD_BASELINE_MAX_AGE_MS` (10 000 ms, five windows) after the baseline drops it and reports `cpuPercent: null` like a first sample, then becomes the new baseline, so the next 2 s sample reports a delta and no sample averages a long idle gap.
- `coreCount` matches `nproc`: on Linux it counts `Cpus_allowed_list` in `/proc/self/status` (the affinity/cpuset view, so a cpuset-restricted host no longer reports every host CPU); it is not cgroup-quota aware, by design — `os.availableParallelism()` counts the quota and disagrees with `nproc` on a quota-limited host. Other platforms, or an unreadable/unparsable list, use `os.cpus().length`. Memory is `used = totalmem − freemem`, clamped to `0..total`.
- `loadavg` is null on Windows (`os.loadavg()` answers `[0, 0, 0]` there, which is not a measurement) and for anything but three finite non-negative numbers. Linux/macOS zeros are real values.
- A failed pass (any `os` call throwing, including a partial failure, or an unusable reading) returns null without throwing and caches nothing: neither the failure nor a new CPU baseline.

## Host view caveat
The values are the host kernel's view (`os.cpus()`, `os.loadavg()`, `os.totalmem()/freemem()`), not a cgroup or container quota. The section heading carries a visible `session.machineHost` badge (宿主机 / Host) and makes no quota claim.

## Client (`hooks/useMachineLoad.ts`, `components/MachineLoadSection.tsx`)
- `DebugPanelView` (`components/DebugPanel.tsx`) is the one mount (`AppShell`'s Session-info popover and the Agents dropdown mount none). The section (same heading, badge, keys and poll) sits in a `.debug-load` wrapper as the grid's last area in DOM order, after the page, server and sessions columns, once the panel has its first page reading. On a wide panel that wrapper is the grid's narrow rightmost column, at middle widths the right column under the sessions, and on a phone the last block of the stack (see Layout). AppShell renders the Debug panel only while `activeTopPanel === "debug"`, so closing it unmounts the section: the timer, the request and the values go with it, no request while closed, and a reopen fetches once immediately from the unavailable state. At most one poller per page. The panel's tooltip hold does not freeze this section (it has no `title`s and keeps its own state). Machine load is not part of the debug snapshot or the panel's Copy JSON.
- The hook polls at the fixed `MACHINE_LOAD_POLL_MS` (2000 ms): no settings entry, no storage key, no argument.
- Only while `document.visibilityState === "visible"`: on mount and on becoming visible it fetches once immediately and starts the interval; on hide it clears the interval and aborts the request in flight, so a hidden page issues zero requests. Each request is also bounded at `MACHINE_LOAD_REQUEST_TIMEOUT_MS` (= one poll interval, 2000 ms; `AbortController` + `setTimeout`, cleared in `finally`): a request that never settles is aborted, the last good values stay and the in-flight slot is freed for the next tick. Hide/close still abort as before. Caveat: a cold `next dev` compile of the route can take longer than the 2000 ms bound, so the first request after a dev start may be aborted once and the section shows the unavailable text (`不可用`) until the next tick lands.
- At most one request in flight: a tick that finds one running skips.
- The first fetch is deferred by one microtask (not a timer) so React Strict Mode's synchronous mount → cleanup → mount in development issues a single first request.
- State changes only through `nextMachineLoadMetrics()` on a valid whitelisted body. A non-2xx answer, a non-JSON body, an abort or network error, `metrics: null` or a malformed object keeps the previous value: a failed tick after a good one changes nothing on screen (no placeholder flash). The component does no I/O.

## View rules and formats (`lib/machine-load-view.ts`)
- Client-safe (no `node:` import): the `MachineLoadMetrics` type, `nextMachineLoadMetrics()`, `machineLoadRows()` and the formatters.
- Exactly four rows: CPU, cores, load average, memory. With no good value yet every row is `session.machineUnavailable` (zh-CN 不可用); no `0` or `0.0%` is ever fabricated.
- Locale-invariant formats (`toFixed`, `.` decimal point): CPU `NN.N%`, cores an integer, load `N.NN / N.NN / N.NN`, memory `N.N / N.N GiB` (GiB = 1024³). A null CPU or loadavg renders `—` (U+2014), never `0.00`.
- Labels are the seven `session.machine*` keys (`machineLoad`, `machineHost`, `machineCpu`, `machineCores`, `machineLoadavg`, `machineMemory`, `machineUnavailable`) in `lib/i18n/messages/en.ts`, `zh-CN.ts` and `zh-TW.ts`; zh-CN uses 机器负载 / 宿主机 / 不可用.
- Layout: the four rows are a two-column grid (`minmax(0, max-content) minmax(max-content, 1fr)`) whose cells wrap (`overflow-wrap: anywhere`): the label gives way before the reading, so a narrow column wraps "Memory (used / total)" rather than splitting `5.2 / 16.0 GiB`. In the panel it is the `load` area of `.debug-cols` (a later change reversed the earlier full-width last row): the grid's narrow rightmost column on a wide panel — `"page server sessions load"`, its own track `minmax(240px, 280px)`, so the block stays ~200-240px behind the 20px gutter, the 1px left rule and the 20px padding and never stretches with the panel; it carries the same left rule the server and sessions columns carry (their separator) and no top rule of its own there. Below the four-column width it is the right column under the sessions — `"page server" "page sessions" "page load"` — its own top border the horizontal separator again; at ≤760px it is the last block of the single-column stack (`"page" "server" "sessions" "load"`), top border and full width as before. The four-column layout starts at a 1412px panel width, measured in the browser: the page's 320px, the server's 380px and the sessions' 400px (each with its 20px gutter and 20px padding), the load's 280px and the scroll body's 32px padding hold without horizontal scroll there, and no width makes `.debug-panel-scroll` scroll horizontally because of the grid. The grid is `width: fit-content` (`max-width: 100%`) above 760px, so it ends at its last column's right edge.
