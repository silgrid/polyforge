# Tool selection and built-in extensions

**What `configured` means.** `configured` is the first entry of the composer's tool preset menu (the wrench button). It means pi-web sends no tool override: the session uses whatever `defaultTools` says in pi's `settings.json` (the global one, or a project's `.pi/settings.json`), exactly as the `pi` CLI does, and keeps following that setting when it changes. If no `defaultTools` is written anywhere, that is pi's built-in default list. Every other preset pins a list instead: Chat only (no tools), read-only (`read`, `grep`, `find`, `ls`), default (`read`, `bash`, `edit`, `write`) and full (all seven built-in tools). An existing session that was never pinned shows `configured`. claude sessions have no pi-web tool preset and so no `configured` state ([claude-sessions.md](claude-sessions.md)).

## New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` → `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries (ADR 0002). No entry, or a later `cleared: true` one, means no pin: the session follows pi's `defaultTools`, as the `configured` preset ("From settings.json defaultTools") does by sending no `toolNames`. An empty array is Chat only, resolved before services are created: no extensions/skills/prompts/themes, and the ordered contents of Pi's discovered context files replace Pi's base prompt. Crossing the Chat-only boundary or clearing a pin rebuilds the wrapper; changing between nonempty presets updates it in place.

**Chat only has no extension providers** (#804): the model selector's listing loads extensions, the session does not. A model only an extension provides (one `findDeferredModel()` remembers but the Chat-only runtime lacks) is named as such: a start refuses it when the browser chose it, `set_model` refuses it instead of "Model not found", and a prompt in a session that could start on no model at all names the one it wanted rather than pi's "No API key found". With no pick, another model in scope stands in for an extension's default, as for any default out of scope.

**Exact system prompts go through `before_agent_start`.** Chat-only sessions register `lib/exact-system-prompt.ts` as an inline extension factory, and subagents (any profile in replace mode, or one naming `skills:`) the equivalent handler in `lib/subagent-skills.ts`, which appends the named skills or, in replace mode, pi's skill catalog; the handler returns `{ systemPrompt }`, which the SDK sends as the provider's leading system prompt for the run while the transcript keeps Pi's structured sections. Assigning `agent.state.systemPrompt` (a getter replayed from transcript system messages) throws, and patching `prepareNextTurnWithContext` never reaches the model. `get_state.systemPrompt` reports the exact prompt for those wrappers.

**Agent language.** A session's Agent language (Settings › General, [settings-ui.md](settings-ui.md)) is fixed when it is created: a new pi session records the server setting in a versioned `pi-web:agent-language` custom entry beside `pi-web:tool-selection` (`lib/session-agent-language.ts`), and every later start reads that entry (none — every pre-#293 session — is English), so resume, restart, compaction and a later setting change keep it; a Chat-only rebuild that has no file yet passes the old session's language on. For 中文 the one fixed instruction (`AGENT_LANGUAGE_INSTRUCTION`, `lib/agent-language.ts`, the same text claude gets through `--append-system-prompt`) follows the prompt after one blank line: a normal session through `lib/agent-language-prompt.ts`'s `before_agent_start` handler, registered last; Chat only through its exact-prompt getter, so the provider receives the exact Chat-only prompt followed by the instruction; a replace-mode or Chat-only subagent after its exact text and skills (`createSubagentSkillsBinding({ agentLanguage })`); an append-mode subagent as the last `appendSystemPrompt` entry. This is the only relaxation of the exact-prompt guarantee, and only for 中文. An English session gets no instruction at all: its system prompt, Chat-only exact prompt included, is byte-identical to before. It never enters the user message or the session title, and `agent.state.systemPrompt` is never assigned. A pi subagent inherits its parent session's language: the runtime writes the parent's language into the child's `resourceSnapshot.agentLanguage` and its own `pi-web:agent-language` entry, and a reopened subagent composes it once from the snapshot (an absent or unknown value is English). Subagents persist their tools and the profile's skill / extension switches in `resourceSnapshot`, and extensions never expose the reserved `Agent`, `get_subagent_result` or `steer_subagent` to them (ADR 0002).

**claude sessions have no pi-web tool preset** ([claude-sessions.md](claude-sessions.md)), and therefore no `configured` state: the pi presets above do not apply to them, and claude's tools, MCP servers, hooks and the cwd's `CLAUDE.md` come from the user's own claude config; the former `read-only` / `writable` presets are retired.

The last preset the user explicitly selected is kept in browser `localStorage` and initializes fresh-session composers only. Existing sessions never trust it: a pinned one shows its selection (`toolNames` from `GET /api/sessions/[id]`, then its live `get_tools`), an unpinned one `configured`.

**Tool exposure.** pi activates `direct` and `model-only` tools on registration unless their definition sets `defaultActive: false` (`codemode` and `tool_search` do), leaves `codemode` and `deferred` tools undeclared until something activates them, and ignores `hidden` (withdrawn) tools in `setActiveToolsByName()`; `get_tools` leaves hidden tools out.
- Pi Web's environment-sanitizing `bash` (`lib/project-command-env.ts`, ADR 0001), an extension tool standing in for pi's built-in, sets `defaultActive: false` too, so like the built-in it is on only when `defaultTools` (pi's default list included), a preset or `set_tools` names it; registered active, it came back in every session whatever `defaultTools` left out (#1235). A user extension's `bash` still replaces it (`preferUserBashExtension()`) and activates as in the CLI.
- `get_tools` reports an active tool's description from `agent.state.tools`, what the model is sent. Under `codemode.mode: "only"`, while `codemode` is active, the active `direct` tools stay active and callable (`get_tools` reports them so, with `declarationHidden: true` from the AgentSession's private `_hiddenDeclarations`), but codemode's `hiddenDeclarations` leave their declarations out of every request, so the model reaches them only from scripts. The toolbar's Tools panel lists only what requests declare; presets still read `active`. A preset still bounds them: a `direct` tool is callable only while active. `prepareLoadout` hooks rewrite it there on every loadout change (tool registration included): codemode's definition holds only the intro, while the declared one lists the tools scripts can call, MCP namespaces and types, and appends the codemode declaration to the callable `direct` tools.
- A preset replaces only the coding tools. `resolveActiveToolNames()` carries every other tool that is active, registered and not hidden, so what an extension, `tool_search` or a `defaultTools` entry such as `+codemode` activated survives startup, `set_tools` and `reload`, a tool an extension switched off stays off, and a preset never turns `codemode` on. It adds nothing else: pi activates extension tools itself, so re-adding them would override an extension (or a branch's recorded loadout) that keeps a `direct` tool off. `reload` carries the set pi rebuilt after extensions restarted, not the previous one.
- `navigateTree()` restores the target branch's loadout from its transcript (bringing back `write` under a Read-only pin, dropping `codemode`), so a normal session then reapplies its pin (the restored set when unpinned) and carries over from the branch it left the session's own tools: `codemode`, `tool_search` and pi-web's subagent tools. Other extension tools follow the target branch's loadout, as in the pi CLI; since pi 1.4 (#11062) one that branch never added or removed, such as one registered after that branch point, is active unless it is registered with `defaultActive: false`. When pi restores the same set that was active (editing a history message, or going back to a point after the last tool change), the session keeps the order pi restored: pi replays the branch's recorded loadout, so that order is that point's prompt (#1405). Reapplying keeps the carried positions of the survivors and appends newly selected coding tools at the end, so the prompt's `<tools>` section stays byte-identical with the `pi` CLI's for the same set; regrouping the coding tools ahead instead rewrote it and dropped the prompt cache on every harness switch. Chat-only and subagent wrappers keep what pi restored.
- A reopened normal session starts on the loadout its transcript last recorded (pi 1.3, as `pi --resume` without `--tools`: pi-web passes no `tools`), not on today's `defaultTools`, so `+codemode` or another `defaultTools` edit made since reaches only new sessions and transcripts that record no loadout. An unpinned session keeps the recorded tools; a pinned one gets its pin over the coding tools and carries the rest from that loadout. Chat only (`tools: []`) and subagents (`subagentToolOptions()`: an allowlist, or `noTools: "builtin"`) select their tools explicitly, so pi restores nothing for them.

**Built-in extensions** (`lib/builtin-extensions.ts`, ADR 0006). The CLI's built-in `codemode`, `tool-search` and `mcp` are rebuilt from the factories the SDK root exports, under the CLI's names with `replaceable: true, builtin: true`, so `-builtin:<name>`, project overrides, replacement by a third-party extension and `noExtensions` behave as in the CLI. Normal sessions load all three. Subagents load `codemode` through their profile's `codemode` policy, and `tool-search` and `mcp` with an MCP host of their own only under `mcp: on` (see [subagents.md](subagents.md)); they never share the normal session's.
- The MCP extension's `loadConfig` returns no servers (only `autoEnableCodemode`), so it connects nothing, and with `startupWaitMs: 0`, so its first-prompt wait for `direct` servers (which ignores Stop, and since pi 1.0 also sees servers registered right before the prompt) holds nothing; pi-web registers servers itself (**MCP host** in [mcp-runtime.md](mcp-runtime.md)). Servers connect through `createPiWebMcpTransportFactory()`; `openUrl` opens no browser on the server host.
- MCP is off (the `mcp` entry registers nothing) when `PI_WEB_DISABLE_MCP` is anything but empty, `0` or `false`, or `lib/pi-sdk-internals.ts` cannot load; never fall back to the SDK's own transport.
- `codemode` is offered only after a once-per-process self-test ran a script through the SDK's sandbox (`checkCodemodeSandbox()`). A built-in that cannot run keeps its `builtin:<name>` entry with an empty factory, so a setting naming it means the same.
- pi lets at most two codemode workers live per process, across all sessions (`DEFAULT_MAX_CODEMODE_WORKERS` in the SDK's `dist/extensions/codemode/execute.js`); `PI_CODEMODE_MAX_WORKERS` changes it, read on every script. Since pi 1.4 a script at capacity waits for a free worker in arrival order, up to 60 s or its `timeout_ms`, then fails without running (pi 1.3 failed it at once with "Codemode worker limit reached"). A script holds its worker while it waits on its tool calls. The CLI runs one session per process; pi-web runs every session and subagent in one, so two parent scripts waiting on subagents took both workers and every script those subagents ran timed out. `applyCodemodeWorkerDefault()` (`lib/codemode-workers.ts`, from `instrumentation-node.ts` at server start) therefore sets the variable to 8 when it is unset or empty; any other value the user set is kept, even one pi rejects (it then uses 2). Each worker's QuickJS heap is capped at 256 MB. Eight parent scripts waiting on subagents at once still fill it; only pi releasing a worker while its script waits would end that. `lib/codemode-workers.test.mjs` fails if the SDK stops reading the variable per script.

**Read-only MCP policy** (`lib/mcp-read-only-policy.ts`, normal sessions; subagents with `mcp: on` have their own, `createSubagentMcpPolicyExtension()`, which reads the profile's tools instead of a pin). While the pinned selection is read-only (it names tools, none of `bash`, `powershell`, `edit`, `write`; no pin is not read-only), its `tool_call` handler blocks every MCP tool (the MCP extension's, or any named `mcp__`) whose definition lacks `annotations.readOnlyHint: true`, codemode scripts' calls included. It reads the pin from the session entries, which `set_tools` writes before applying it and cannot change mid-run. The hint is the server's word: this guards against model mistakes, not a malicious server.

**`defaultTools` switches.** Code mode's Always on is `+codemode` in the global `defaultTools`; Automatic writes nothing (ADR 0006). `/api/tools/settings` is the only writer of that key, for this and the PowerShell switch, and of the global `codemode.mode` and `codemode.inlineBudget` (Settings › MCP's Built-in tools switch and tool list budget), through `lib/global-settings-file.ts` (the lock pi's `SettingsManager` takes on that file). `lib/codemode-settings.ts` edits only entries naming `codemode` and appends `+codemode`, valid on plain and modifier-only lists; a modifier-only list left empty is removed, since `defaultTools: []` means no tools at all. `defaultTools` may hold `+name` / `-name` modifiers: read it resolved through `SettingsManager.getDefaultTools()`; `lib/powershell-settings.ts` resolves the raw global list by the same rule before editing, since appending a plain name to a modifier-only list drops pi's default tools.
