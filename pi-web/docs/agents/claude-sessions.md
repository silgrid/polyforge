# claude sessions (#250, #253, #270, #272, #363, #368, #370, #442, #445)

pi-web can run a session on the **claude** harness instead of pi: a `claude -p` child process per live session — the **system claude**, with the user's own config, login and `CLAUDE.md` — translated into pi-web's existing session events. pi sessions are untouched; everything below applies only to rows whose `harness` is `"claude"`.

Files: `lib/claude-shared.ts`, `lib/claude-argv.ts`, `lib/claude-config-dir.ts`, `lib/claude-index.ts`, `lib/claude-adapter.ts`, `lib/claude-subagent-view.ts`, `lib/claude-background-task-view.ts` (the background task model), `lib/claude-session.ts`, `lib/claude-permission.ts` and `lib/claude-permission-config.ts` (permission prompts), `lib/image-attachments.ts` (the claude image whitelist and `validateClaudeImages()`), `lib/agent-language.ts` (the Agent language and the one fixed instruction `--append-system-prompt` carries), `lib/agent-language-config.ts` (the server setting a new session captures), `lib/claude-settings.ts` and `app/api/claude-settings/route.ts` (Settings › Claude), `lib/claude-probe.ts` (what the claude on PATH reports), `app/api/claude/route.ts`, `app/api/claude-permissions/route.ts` (the permission settings), `components/ClaudePermissionSettings.tsx` (their Settings › General block), the claude branches of `app/api/agent/**` and `app/api/sessions/**`, `instrumentation-node.ts`, the claude parts of `hooks/useAgentSession.ts`, `components/ChatInput.tsx` (`ClaudeComposerControls`, `ClaudeLaunchPermissionModeMenu`, the claude model list, the claude effort entries `CLAUDE_EFFORT_ENTRIES`, the claude image gate `filterComposerImageFiles()`), `components/HarnessSelector.tsx`, `components/ChatWindow.tsx`, `components/ClaudeSubagentRow.tsx`, `components/ClaudeSubagentRunningList.tsx` (with the background tasks' buttons and `ClaudeForceStopNotice`), `components/ClaudeSubagentPanel.tsx`, `components/ClaudeBackgroundTaskPanel.tsx`, the claude anchor in `lib/message-display.ts`, `components/SessionSidebar.tsx` (`HarnessMarker`; a claude row's awaiting marker), `components/AppShell.tsx`, `claude.*`, `claudeSubagent.*`, `claudeTask.*` and `claudeStop.*` in `lib/i18n/messages/*`.

## Choosing the harness
- A fresh composer's bottom bar carries, left to right, the attach button (both harnesses), the **harness selector** (`HarnessSelector`: a popover with the model selector's toolbar button and menu rows, **pi** — the default, unchanged — or **claude**) and **the one model selector**. The model selector's list follows the harness: pi's models as before, or claude's (replacing the four full names pinned to 2.1.312): the aliases the claude on PATH lists in its answer to `initialize` — with 2.1.322 `default` / `opus` / `fable` / `sonnet` / `haiku` — then Settings › Claude's custom names, each shown as the name passed to `--model` verbatim (`claudeModelOptions()`; an open session's own model is listed too when the list lacks it, so an older session's full name such as `claude-opus-5-5` stays visible and choosable). Switching the harness resets the destination's model: claude → `default` (`DEFAULT_CLAUDE_MODEL`, claude's own alias, which the CLI resolves itself), pi → no override, so pi's default model is selected again.
- Under the selectors, while claude is chosen, one line: "Uses the system claude; if something goes wrong, adjust claude from the pi-web terminal." (zh-CN 「使用系统 claude；如有问题，请在 pi-web 终端手动调整 claude」, zh-TW 「使用系統 claude；如有問題，請在 pi-web 終端手動調整 claude」, key `claude.systemHint`); nothing for pi.
- **Model, effort and compact; this rewrites the earlier "fixed for the session's life" rule.** A claude composer uses pi's own toolbar controls in pi's slots: the model selector (`ModelSelector`, claude's model names as above, the current one selected), the reasoning button and its `SelectorRow` menu for claude's **effort** — exactly `low` / `medium` / `high` / `xhigh` / `max` plus 「默认」 (en `default`, zh-TW 「預設」; "No --effort: your claude configuration decides"), one active entry, a description per entry, no star, no `off` / `minimal` / `auto` (`CLAUDE_EFFORT_LEVELS`, `CLAUDE_EFFORT_DEFAULT` in `lib/claude-shared.ts`) — and, in an open session, pi's compact button. A fresh claude composer offers model and effort (no compact; nothing to compact yet), its effort pick seeds the created session, and its system-claude hint stays as it was. At ≤640 px an open claude session keeps the model selector in the bottom bar's left cell, right after the attach button, exactly where pi's sits; effort and compact sit in the composer's existing More controls menu, and opening and closing it changes nothing else (an owner-intended change): this moves only the model selector back out of the phone menu an earlier change had put it in. On a phone that selector, like an open pi session's, asks first: choosing another model shows `window.confirm` 「从 <当前模型> 切换到 <新模型>？」 and only a confirm sends `set_model`; a cancel or the current model sends nothing. A fresh composer and the desktop switch at once. The harness stays fixed: an open claude session has no harness selector, and the earlier "claude · <model> — fixed for this session" line and its `claude.fixedLine` key are gone.
- The three controls are usable only while the session is idle: they are rendered disabled while a turn or a compaction runs and until the page's event stream has said whether one runs; the server refuses `set_model` / `set_effort` / `compact` mid-turn ("A claude turn is running; … when it ends") and changes nothing.
- **Permission mode in the composer.** An open claude session has one more control in the same right-hand group (≤640 px: inside More controls, with effort and compact): the permission-mode button (`aria-label` "Permission mode", a shield icon, the session's mode as its text) and its menu (`ClaudeLaunchPermissionModeMenu` in `components/ChatInput.tsx`): **default**, labelled as Claude Code's own setting — en "Default (follows Claude Code's own settings)", zh-CN 「默认（按 Claude Code 自身设置）」, zh-TW 「預設（依 Claude Code 自身設定）」 (`claude.permissionModeDefault`, the key Settings › Claude reuses; owner ruling Q2=A: no `--permission-mode`, the user's `~/.claude` decides) —, **acceptEdits** with its description, and **plan**, enabled when the session's approvals come to Pi Web (ask mode) and otherwise disabled, its reason visible text in the row ("Not available: plan mode needs claude tool permissions set to Ask in a dialog (Settings › General) — on Deny silently claude would refuse to leave plan mode", `claude.permissionModePlanUnavailable`), never a tooltip only (r3; the composer reads `SessionInfo.claude.planAvailable`, `false` only on deny). Choosing a mode sends `set_permission_mode` `{ mode }` (`handleClaudeLaunchPermissionModeChange` in `hooks/useAgentSession.ts`); the button shows the new mode only once the server accepted it, and a refusal is the refused-switch line below ("Could not change permission mode: …", `claude.permissionModeError`). Unlike model and effort it is not idle-only: claude takes the switch mid-turn, so the control stays usable while a turn runs. The mode shown is the session's (`SessionInfo.claude.launchPermissionMode`, absent = default, then the page's accepted switch). A fresh composer has no permission-mode control: a new session takes Settings › Claude's mode.
- A switch claude refuses shows one visible line under the selectors, a localized prefix plus claude's own text — "Could not switch model: <claude's error>" (zh-CN 「无法切换模型：」, zh-TW 「無法切換模型：」; an effort refusal "Could not change effort: …"); the selector, the list row, the detail and the index keep the old model, and the next successful switch replaces the line. The control shows a new value only once the server accepted it.
- `PATCH` takes only `{ name }` / `{ archived }`.
- `POST /api/agent/new` takes `harness: "claude"` and `model` (required, any name `--model` takes — one of claude's aliases or a full name, Bedrock / Vertex ids included: `isClaudeModelName()`, 1–128 characters, never starting with `-`; anything else is refused 400), optional `effort` (a level or `"default"`; anything else 400 before any record or child; absent means the default) with type `prompt` or `ensure_session`; a #219 `claudePreset` is dropped unread. The order is the guard's: validate the fields, `isRegistrableRoot(cwd)` (the pi route's refusal and reason), claude on `PATH`, then the index entry and the first child. Nothing is created before the guard passes. The reply's model is `{ provider: "claude", modelId: <the model name> }`.
- `claude` is resolved from `PATH` only, on every call (`findClaudeBinary()`); there is no path setting and nothing bundled. `GET /api/claude` reports `{ available, reason?, models, defaultModel, version, versionRecorded, recordedVersions, capabilities, features, probeError? }`; it creates no session and persists nothing, but it asks claude once (a zero-cost `initialize` probe run in `$HOME`, so the user's own startup hooks may run; a successful answer is cached per binary); when claude is missing, the harness menu's claude row is disabled and the reason is visible text under the selectors.
- **The probe (`lib/claude-probe.ts`).** The model list is not pinned: `probeClaude()` runs the claude on PATH once — `claude -p --input-format stream-json --output-format stream-json --verbose --no-session-persistence --permission-prompts none`, cwd the user's home, env `buildClaudeEnv(process.env)` — writes one `{"type":"control_request","request_id":…,"request":{"subtype":"initialize"}}` and nothing else (no prompt: zero credit, no turn, no session file), reads the matching `control_response`, then ends the child the way claude ends itself: it closes the child's stdin, and only a child still running `CLAUDE_PROBE_EXIT_GRACE_MS` (2 s) later is sent SIGTERM, then SIGKILL after as long again (the background-task stub logs every signal it gets). 15 s deadline (`CLAUDE_PROBE_DEADLINE_MS`); a start failure, an exit, a refusal or the deadline is `{ error }`, never a throw. An answer is cached per binary (realpath, mtime, size) for the server's life, so an upgraded claude is asked again; an error is not cached. From the answer (`claudeInitializeInfo()`): `claude_code_version`, `models[]` (`value`, `displayName`, `resolvedModel` — claude's ModelInfo), and `capabilities`, listed verbatim (claude's protocol capabilities, never mapped to Pi Web features). `models` in the reply is those aliases (`source: "alias"`) followed by Settings › Claude's custom names (`source: "custom"`, a name already among the aliases listed once); `defaultModel` is `default`. A failed probe still offers `default` plus the custom names, and `probeError` carries the reason. `versionRecorded` says whether the version is one of `CLAUDE_RECORDED_VERSIONS` (`lib/claude-shared.ts`: the `lib/__fixtures__/claude-<version>/` directories, pinned equal by `lib/claude-shared.test.mjs`; null when the version is unknown): a version outside it is not covered by the fixtures. The `lib/__fixtures__/claude-2.1.322/initialize/` recording is the answer the stubs give.
- **Pi Web's claude features (owner ruling Q1=A).** Beside claude's own `capabilities` (listed verbatim — none of them names what Pi Web relies on: in 2.1.312–2.1.322 they are protocol capabilities such as `interrupt_*_v1`, `mcp_*`, `ui_surface_v1`), `GET /api/claude` answers `features`: three entries `{ id, available, basis }` judged from Pi Web's own evidence by `claudePiWebFeatures(version, buildClaudeEnv(process.env))` (`lib/claude-probe.ts`), never by parsing `claude --help` or probing flags. `available` is `true`, `false` or `null` (unknown); `basis` is a code the pages render as text:
  - **approvals** (`approvals`): judged by the global claude tool permissions (`claude-permissions.json`'s `mode`, read only; the route passes `readClaudePermissionConfig().mode` as `claudePiWebFeatures()`' third argument) — what a new session gets, the same source Settings › Claude's plan uses (r3, plan D12, owner ruling 2026-11-13T07:40:00Z). **ask** (`permissionPromptFlags()` in `lib/claude-argv.ts`: `--permission-prompts host --permission-prompt-tool stdio`, Pi Web answers claude's approval requests): `true`, basis `host-prompts`; **deny** (`--permission-prompts none`, claude denies what would ask): `false`, basis `no-host-prompts`. Not gated on the claude version (#442 is not). The basis text names the setting: "claude tool permissions is Ask in a dialog: …" / "… is Deny silently: …" (`settings.claudeBasisHostPrompts` / `settings.claudeBasisNoHostPrompts`).
  - **background tasks** (`backgroundTasks`): `null` / `version-unknown` without a version (the probe failed); `false` / `below-recorded` below `CLAUDE_FEATURE_MIN_VERSION.backgroundTasks` (`2.1.322`, the `relay/` recording's `background_tasks` control request); `false` / `env-disabled` when the child's environment sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` true as claude 2.1.322 reads it (`1` / `true` / `yes` / `on`, any case, trimmed — its env module's boolean; claude then answers "Background tasks are disabled in this session."); else `true` / `recorded`.
  - **subagent text** (`subagentText`): `null` / `version-unknown` without a version; `false` / `below-recorded` below `CLAUDE_FEATURE_MIN_VERSION.subagentText` (`2.1.322`, the `subagent-forward/` recording of `--forward-subagent-text`); else `true` / `recorded`.
  - Versions compare segment by segment as numbers (`compareClaudeVersions()`; a non-numeric version is unknown). A claude newer than the recordings is judged by the thresholds and flagged by `versionRecorded: false`. Recording a new claude version adds its directory and its `CLAUDE_RECORDED_VERSIONS` entry together, and moves a threshold when that recording changes a feature; every threshold is a recorded version (`lib/claude-shared.test.mjs`).

## Settings › Claude
- Stored on the server in `<pi agent dir>/pi-web-claude-settings.json`, `{ "version": 1, "launchPermissionMode": "default" | "acceptEdits" | "plan", "customModels": string[], "includeHookEvents": boolean }` (`lib/claude-settings.ts`), pi-web's own file: never the Agent language's `pi-web-settings.json`, never claude's `~/.claude`. Written like the Agent language's file: one write at a time, atomic, mode 0600, other keys kept, a file that is not a JSON object refused rather than overwritten. A missing or malformed file reads as the defaults (`default`, no custom names, hooks off), and each field reads on its own: an unknown mode is `default`, an invalid or repeated custom name is dropped (at most 50 kept).
- `GET /api/claude-settings` answers the stored settings; `PUT /api/claude-settings` with exactly `{ launchPermissionMode, customModels, includeHookEvents }` is the file's only writer, behind the proxy's `/api/*` authentication and the route's own trusted-request (403) and JSON (415) checks. A custom name must be a claude model name (`isClaudeModelName` in `lib/claude-shared.ts`: 1–128 letters, digits and `. _ : @ / [ ] -`, not starting with `-`, so `opus[1m]` and Bedrock / Vertex ids pass); repeats are merged, more than 50 is refused, and any refusal is a 400 naming the reason with nothing written.
- The page (`components/ClaudeSettings.tsx`, Settings' Claude section before Polyforge, openable without a project) edits these three values and shows, read-only, what the claude on PATH reports (GET /api/claude): [settings-ui.md](settings-ui.md), "Claude section". A save reaches claude sessions created afterwards only; an open session keeps the values it was created with and switches its own mode from the composer (below).
- Plan mode needs claude's approval requests to reach Pi Web (r3, plan D11, owner ruling 2026-11-13T07:40:00Z): leaving plan is ExitPlanMode, which always asks (claude 2.1.322's bundle: `checkPermissions` answers `behavior: "ask"`). Only the **ask** launches claude with `--permission-prompts host --permission-prompt-tool stdio`, so the ask becomes Pi Web's ordinary permission dialog; on **deny** (`--permission-prompts none`) claude refuses what would ask, and a plan session could never leave plan. `claudePlanModeAllowed(mode)` (`lib/claude-shared.ts`) is `mode === "ask"`. Settings › Claude judges it by the global mode (`claude-permissions.json`, read only): GET answers `planAvailable`, the PUT refuses `plan` on deny (400, `CLAUDE_PLAN_UNAVAILABLE_REASON`), and a stored `plan` reads as `default` on deny (the file keeps it). A session already created with plan keeps `--permission-mode plan` if deny is set later; it can switch to default / acceptEdits in the session (D13).

## argv (`lib/claude-argv.ts`)
One reduced set for every child, the model passed verbatim:

| launch | argv |
|---|---|
| first | `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --forward-subagent-text --model <model name> [--permission-mode <m>] [--include-hook-events] <permission words> --session-id <id>` |
| permission words | the session's permission mode, fixed at the child's launch (below): ask → `--permission-prompts host --permission-prompt-tool stdio`, deny → `--permission-prompts none` |
| restart | the same with `--resume <id>` instead of `--session-id <id>` (once claude has a transcript for the id) |
| in-session edit | the restart that sends an edited message: `--resume <id> --resume-session-at <entry>`, `<entry>` the edited message's parent (below); only that one launch carries it, the next restart is plain again |
| effort | `--effort <level>` right after `--model`, on every launch, when the session's effort is not 「默认」; the default entry passes no `--effort`, so its argv stays the words above: 16 in ask mode, 14 in deny mode |
| Agent language | `--append-system-prompt <instruction>` after `--model` / `--effort` and before `--permission-prompts`, on the first launch and every resume, when the session's Agent language is 中文; the instruction is `AGENT_LANGUAGE_INSTRUCTION` in `lib/agent-language.ts`, byte for byte the text pi sessions append to their system prompt. An English session (and every pre-#293 record) passes nothing: its argv is exactly the rows above, with no "reply in English" flag |
| permission mode | `--permission-mode acceptEdits` or `--permission-mode plan` after `--model` / `--effort` / `--append-system-prompt` and before `--permission-prompts`, on every launch, when the session's permission mode (Settings › Claude's, fixed at creation) is not `default`; `default` passes no `--permission-mode` (owner ruling Q2=A, 2026-11-13), so claude's own `permissions.defaultMode` from the user's `~/.claude` applies and the argv stays the rows above |
| hook events | `--include-hook-events` right after the permission mode (still before `--permission-prompts`), on every launch, when Settings › Claude's hook switch was on at the session's creation; off passes nothing |

`--forward-subagent-text` is there because claude 2.1.322 no longer forwards a subagent's text and thinking without it (only its tool calls and results), so a running subagent's replies would be missing from the live view; 2.1.312 and 2.1.319 list the flag too and accept it, and the sidecars hold the text either way.

Every launch reads the index record, so `--model` and `--effort` are always the session's current values (a model switch or effort change made earlier included), `--append-system-prompt` follows the language the record fixed at creation, and `--permission-mode` / `--include-hook-events` follow the permission mode and hook switch the record took from Settings › Claude at creation: changing the settings later rewrites no record and no resume's argv.

No `--bare`, `--strict-mcp-config`, `--disable-slash-commands`, `--tools`, `--allowedTools` or `--cwd`, and no `--permission-mode` for a `default` session: claude's tools, MCP servers, hooks, plugins, permission rules (its `permissions.defaultMode` included, for a `default` session) and the session folder's `CLAUDE.md` are the user's claude config's. The session folder is the spawn's working directory. The permission words decide only where an action claude itself would ask about goes: ask mode (`--permission-prompts host --permission-prompt-tool stdio`, the default) sends claude's question to Pi Web over stdin/stdout, where it is a dialog (Permission prompts, below); deny mode (`--permission-prompts none`, the argv before byte for byte) lets claude deny it on its own, shown as a warning notice and the tool error. Either way claude's own rules and permission mode decide everything else: an action the user's rules allow runs without a question. The #219 tool presets (`read-only` / `writable`) and their flag sets are retired; pi-web lists no claude tools (`get_tools` and the detail's `toolNames` are empty).

## Environment and config dir (`lib/claude-argv.ts`, `lib/claude-config-dir.ts`)
- The child's env is pi-web's minus `PI_WEB_PASSWORD`, `CLAUDECODE` and the server's own `NODE_ENV`, `TMUX` and `TMUX_PANE` (`buildClaudeEnv()`), by name; nothing is added (removed the `PF_CHAT_WATCHER=pi-web` marker with the chat watcher). Without the last three a session's `npm ci` keeps devDependencies under `next start`, and the session no longer runs inside the tmux pi-web runs in nor is told its socket when that socket is not the default one. The limit: a pi-web on tmux's default socket (`/tmp/tmux-<uid>/default`) is still reachable, because a bare `tmux` (`tmux kill-server` included) falls back to that socket when `TMUX` is unset (an owner follow-up). An `env` in the user's claude settings still applies: claude sets it itself. The user's `ANTHROPIC_*` and `CLAUDE_*` variables reach the child, and `CLAUDE_CONFIG_DIR` only when pi-web itself inherited it. pi-web never reads, logs or displays a credential.
- Transcripts live where the system claude writes them: the inherited `CLAUDE_CONFIG_DIR`, else `~/.claude` (`claudeConfigDir()`). pi-web finds a session's transcript there by id and, on delete, removes that one file; the only thing it writes there is a fork's copy beside its source (below), and it never creates the dir itself.
- The #219 dedicated config dir (`~/.pi/agent/claude` by default) is no longer created, read, migrated or deleted, and Settings › General no longer shows a config dir (Settings › Claude, shows no config dir either: claude keeps its own); it may be removed by hand. A failed turn (an authentication error, a child that exits) shows claude's own text plus `(claude config dir: <path>)` as an error notice.

## Index, list and history
- pi-web keeps its own index, `<pi agent dir>/claude-sessions.json` (`lib/claude-index.ts`): `{ id, cwd, name?, model, effort, agentLanguage, launchPermissionMode, includeHookEvents, permissionMode?, created, modified, firstMessage, usage, archived? }` (`model` the name passed to `--model`, an alias or a full name — the session's current model, rewritten by an accepted switch; `effort` a level or `"default"`; `agentLanguage` `"en"` or `"zh-CN"`, the server's Agent language when `POST /api/agent/new` created the record, never rewritten by a later setting change; `launchPermissionMode` (`default` / `acceptEdits` / `plan`, the value `--permission-mode` takes) and `includeHookEvents`, Settings › Claude's values when the record was created, never rewritten by a later setting change; `permissionMode` `"ask"` or `"deny"`, the session's override of the global permission mode, absent = follow the default, an unknown value read as absent; no preset), written whole per change (serialized per file, temp + rename), each write bumping the session list version. A missing or corrupt file reads as empty. The claude session id is pi-web's id.
- The reader is tolerant: `model`, else #219's `modelAlias`, kept as the name claude takes (no alias table — `sonnet` stays `sonnet` and launches `--model sonnet`; #219's `claude-default`, which is no claude alias, reads as `default`); a legacy `preset` is ignored and an invalid name (`normalizeClaudeModel()`) reads as `default`, so no record is dropped (only `id` and `cwd` are required). A record without `effort` (every pre-#272 record) or with an unknown one reads as `"default"` (`normalizeClaudeEffort()`); one without `agentLanguage` (every pre-#293 record) or with an unknown one reads as `"en"` and launches without `--append-system-prompt`. One without `launchPermissionMode` / `includeHookEvents` (every pre-#445 record) or with an unknown value reads as `default` / off and launches without `--permission-mode` / `--include-hook-events`. Reading never rewrites the file; the next index write stores every record in the new shape (`model` + `effort`, no `modelAlias`).
- `GET /api/sessions` adds those rows (`harness: "claude"`, `claude: { model, effort }`, `archived`; the detail's `info` and `POST /api/sessions/stats` carry the same current model) beside the pi rows; nothing scans claude's projects directory, so a claude session created outside pi-web is never listed, and nothing is written to the pi sessions store.
- A claude session's sidebar row (active and archived) shows only the harness chip `claude`: it is the last element of the title line, pushed to that line's right edge, the title ellipsizes first and the `filtered` chip stays beside the title. No model name appears anywhere in the row — text or tooltip. pi rows carry no harness marker. The row still keeps `data-harness="claude"`.
- History is claude's own transcript, `<config dir>/projects/*/<id>.jsonl`, found by id and read through the adapter (`GET /api/sessions/[id]`): no parallel event log exists. It is the transcript's active branch alone (below), with `claudeEditEntryIds`, the user messages an in-session edit can start from. The detail has no branch tree; `snapshotRevision` is null (the transcript grows behind pi-web).
- Subagent runs come back from claude's sidecars: `<transcript dir>/<id>/subagents/agent-<agent id>.jsonl` and its `.meta.json` (`claudeSidecarFiles()`), read by `readClaudeHistory()` and served as the detail's `claudeSubagents`. The main transcript keeps the `Agent` call and its tool result; the run is linked to its sidecar by the receipt's `toolUseResult.agentId`, else by the meta's `toolUseId`, and nested sidecars are followed the same way (no depth cap). The sidecar's opening prompt is the run's prompt, not a timeline entry; sidechain entries never enter the main list. claude's `<task-notification>` turn (`turnOrigin: task_notification`) gives the run's final status, `<result>` and usage, and becomes a hidden `claude:task-notification` anchor instead of a user bubble. A notification claude absorbed into a running turn (its `queued_command` attachment, no user entry) reports its run the same way and shows nothing. A notification names its run by `<tool-use-id>` (the `Agent` call, or the `SendMessage` that resumed it), else by `<task-id>`, the agent id (claude names no call, for example, for a run the agent resumed itself after its own background work). A notification naming several `<task-id>`s (claude reports the agents that didn't finish before the previous session ended in one) settles each of those runs with its one status; only the header before `<status>` / `<summary>` / `<result>` names tasks, so a `<task-id>` the agent's reply quotes in `<result>` settles nothing. One whose summary says the agent "is waiting on its own background work" is interim (claude still writes `completed`; the summary is the only signal): it carries its result and usage but settles nothing, and the agent notifies again. A missing or unreadable sidecar leaves its run without entries, silently. Entry ids are claude's `uuid`, the same on the live stream, so live and history yield the same entries and merge by id.
- The page (`hooks/useAgentSession.ts`) keeps one run map per session, by tool call id: every session read seeds it from `claudeSubagents` and every `claude_subagent` event merges into it, both through `lib/claude-subagent-view.ts` — an entry id already held keeps its place (a history read's copy wins), new ids append once, a settled status never returns to running. A reload in the middle of a run therefore shows the entries already on disk once and appends the later live ones; a session without the field keeps an empty map.
- **The Agent row** (`components/ClaudeSubagentRow.tsx`; `components/MessageView.tsx` renders it for an `Agent` / `Task` call that has a run, `components/ChatWindow.tsx` hands the runs down through `ClaudeSubagentContext`, so a pi session and a claude call without a run keep the ordinary tool card). Collapsed it is one header line with a subagent-colour bar: the `subagent_type` badge, the description, then while running the latest progress description and "Running", once settled the state when it is not "completed" and `N tools · duration · tokens` from claude's task statistics. State changes show in the header only; timeline entries are append-only. Expanded it shows, in place, the prompt (whole, in a scrollable block), the indented timeline — every step rendered by the chat's own `MessageView`, tool results under their calls — and, once settled, the Result (the run's final reply shows once, there; "No result" when claude reported none). Nothing of the body is mounted while collapsed. The first 25 steps show, then "Show N more" reveals the rest: nothing is truncated or hidden. A nested `Agent` call in the timeline is the same row, at any depth.
- Expansion: a row never toggled is open while its run is running, failed or interrupted (claude's killed/stopped/cancelled statuses) and closed once it completed; a manual toggle wins over every later state change, kept in page memory by tool call id (never stored), so it survives the row moving from the stream into the list and into the folded process details. A toggle changes nothing else: no message, composer or stream state, and the focus stays where it was.
- Strings: `claudeSubagent.*` in `lib/i18n/messages/{en,zh-CN,zh-TW}.ts` (running / failed / stopped, tool count, tokens, Prompt, Result, No result, Show N more).
- `PATCH /api/sessions/[id]` takes `{ name }` and `{ archived }` for claude rows (index only); the sidebar's archive set mirrors the index for claude rows and keeps the browser set for pi rows. `DELETE` ends the child, then removes that session's transcript and index entry, nothing else.
- Usage is the sum of each turn's `result` aggregate (input, output, cache read/write, cost), recorded in the index and served by `GET /api/sessions/[id]` `stats`, `POST /api/sessions/stats` and `get_session_stats` — never the streamed per-message usage, which under-counts.

## Lifecycle (`lib/claude-session.ts`)
- One `ClaudeSession` per live child in a `globalThis` registry. It implements the event-stream session shape, so `GET /api/agent/[id]/events` hands it to `createAgentEventStream()` unchanged; opening the stream starts a child when none is alive.
- The child lives while a page renews the lease (`POST /api/agent/[id]/lease` renews, never spawns), a turn runs, a background subagent is unsettled (below) or a background task runs (below), and ends one `PI_WEB_IDLE_TIMEOUT_MS` after the last renewal (`0` disables). It runs in its own process group (`detached`), which is what shutdown signals: stdin closed, SIGTERM, SIGKILL after 3 s; any descendant left after the leader exits is killed too. `instrumentation-node.ts` ends every group on SIGINT/SIGTERM.
- The next open or send after an exit starts `claude --resume <id>`: the same conversation, its history read from the transcript.
- Commands answered for a claude id: `prompt` (while a turn runs it is a steer, below; refused while a compaction runs), `abort`, `get_state` (`model`, `claudeEffort` and `claudeLaunchPermissionMode` from the index record as it is now, `claudePlanAvailable` whether this child was launched with ask mode (r3), `isCompacting` during a compaction, `contextUsage` as below), `get_tools`, `get_commands`, `get_session_stats`, and, added later, `set_model` (`{ model }`, or pi's `modelId`, any name `--model` takes; an invalid one is 400), `set_effort` (`{ effort }`, a level or `"default"`) and `compact`, and `fork` (`{ entryId }`, below; it needs no child and starts none) and a `prompt` with the `entryId` of the user message it replaces (an in-session edit, below), and `background_task` (`{ toolCallId }`, the relay's first half, under Subagents: refused with 400 when no child is alive, it starts none), and `stop_task` and `task_output` (`{ taskId }`, under Background tasks: refused with 400 when no child is alive, they start none), and `extension_ui_response`, the page's answer to a permission dialog (Permission prompts, below; an id no dialog of the child's holds is ignored, as pi ignores one; refused with 400 when no child is alive, since its dialogs died with it, and it starts none), and `set_permission_mode` (`{ mode }`, below). A malformed switch (a `set_permission_mode` naming a mode other than default / acceptEdits / plan, or plan for a session whose approval mode is not the ask, included), a fork without an `entryId`, an edit with an empty one, a `background_task` without a `toolCallId`, a `stop_task` / `task_output` without a `taskId` is 400. Every other command (`set_thinking_level`, `set_tools`, `fork_branch`, `clone`, `navigate_tree`, `steer`, `follow_up`, `reload`, …) is refused (400, "not available for claude sessions"), `bash` included) and starts nothing.
- **No shell mode**: a claude composer never enters pi's Bash mode. Text starting with `!` (or `!!`) shows a muted hint where pi's Shell label is (`chat.claudeNoShell`: the text goes to claude as a message), and Send sends it as an ordinary `prompt`, a staged edit with it. claude's stream-json input has no shell command (only its interactive TUI has `!`); wrapping the command in a prompt would ask the model to maybe run it, and running it in pi-web's server would make pi-web a second shell outside claude's permission model. The server still refuses `bash` for a claude id.
- **Model switch.** With a live child, `set_model` writes claude's own `control_request` `{ subtype: "set_model", model }` on stdin (`claudeSetModelLine()`) and waits up to 15 s (`CLAUDE_CONTROL_DEADLINE_MS`) for its `control_response`: accepted (`{ model }`), the index records the model and the same child and transcript go on — no restart, no resume — and the next turn's assistant `message.model` is the new model; refused (claude's `check_failed` "… model not changed", or no answer in time), the reply is `{ model: <old>, rejected: true, error, errorCode? }` and nothing changes. With no live child the switch is the index's alone (`{ model, pending: true }`, nothing spawned) and the next open or prompt resumes with `--model <new>`; so does a child that exits before it answers (the switch is recorded the same way, `{ model, pending: true }`). A child is not idle-reaped while a control request waits for its answer.
- **Effort change.** A level goes to the live child as `control_request` `{ subtype: "apply_flag_settings", settings: { effortLevel } }` (`claudeSetEffortLine()`), which the recording proves reaches the next request (`effort/runtime-probe.jsonl`), so the child and the conversation stay; the index records it for every later spawn. The default entry has no in-place value: picking it records the index and ends the idle child, so the next one starts without `--effort`. While that child holds unfinished background work — an unsettled background subagent or a running background task — ending it would end that work, so the default is refused instead, changing nothing (no index write, no stdin line, the child and its work left running): `{ effort: <the effort in force>, rejected: true, error }`, the error naming each piece (`A claude background subagent is still running ("<description>")`, `A claude background task is still running ("<command>")`; `claudeRestartRefusal()`), which the composer shows in its existing refusal line (`claude.effortError`, 「无法更改思考强度：…」). claude has no live equivalent to fall back on: `apply_flag_settings { effortLevel: null }` is accepted but sets claude's own `default` effort, while a launch without `--effort` inherits the user's claude configuration (2.1.322's bundle), so the two are not the same choice. With no live child, or one that exits before it answers, the change is the index's alone (`{ effort, pending: true }`).
- **Permission-mode switch.** A session's mode can change for that session alone ("temporary": Settings › Claude's default is not changed, and the session keeps the new mode in its index record for every later child). With a live child, `set_permission_mode` writes claude's own `control_request` `{ subtype: "set_permission_mode", mode }` (`claudeSetPermissionModeLine()`) and waits for its `control_response`, like a model switch but not idle-guarded (claude takes it mid-turn): accepted (`{ mode }`; claude also streams a `system` `status` frame with `permissionMode` when the mode changed, which the adapter ignores), the index records it and the reply is `{ launchPermissionMode }`; refused (claude's `invalid_mode` "Cannot set permission mode: must be one of …"), the reply is `{ launchPermissionMode: <old>, rejected: true, error, errorCode }` and nothing changes. With no live child, or one that exits before it answers, the switch is the index's alone (`{ launchPermissionMode, pending: true }`, nothing spawned) and the next child starts with `--permission-mode <mode>` (none for `default`). The route and the session refuse an unknown mode (`Not a claude permission mode: …`) and `plan` for a session whose approval mode is not ask (`claudeSessionApprovalMode()`: the live child's, fixed at its launch, else the one its next launch takes, `record.permissionMode ?? the global mode`; `CLAUDE_PLAN_UNAVAILABLE_REASON`, r3) with 400, before a child is started or stdin written. The request, the answers and the status frame are claude 2.1.322's as recorded (`lib/__fixtures__/claude-2.1.322/permission-mode/`, zero credit: control requests only); the unit-test stub answers the same way.
- **Compaction.** `compact` writes claude's own bare `/compact` user line (`claudeCompactLine()`, no instructions) as a turn: no other prompt or switch is taken meanwhile, the page gets pi's `compaction_start` / `compaction_end` (not a reply: no assistant message is shown for it), and the command resolves when that turn's `result` arrives — `{ tokensBefore }` from claude's `compact_boundary` (`compact_metadata.pre_tokens`), `{ aborted: true }` after Stop, claude's own error otherwise (also when claude ended the turn without compacting). It never restarts, resumes or appends instructions. The composer's result slot then shows one line with only claude's number, "Compacted from N tokens" (zh-CN 「已压缩：压缩前 N tokens」, zh-TW 「已壓縮：壓縮前 N tokens」, `claude.compactResult`) — no after or saved figure; a failed compaction shows its error in the same slot. While it runs Send is disabled with "claude is compacting; …", and the compact button is pi's Stop compaction, which sends claude's `abort` (the interrupt below): the turn ends stopped, without a marker or summary, and the session takes the next message.
- Stop acts only while a turn runs: it writes the stream-json interrupt control request with `spare_background_tasks: true` (`claudeInterruptLine()`), which ends the turn and leaves claude's background agents and tasks running — a plain interrupt stops the background agents too (2.1.319 `idle-interrupt/`), and claude 2.1.322's interrupt schema says of the flag "this Stop ends the turn and leaves running background agents and workflows alone", written by a client with its own stop for each task; a CLI that does not read it treats the request as a plain interrupt. The flag is claude's own `@internal` member, read from the 2.1.322 bundle's schema and print-mode handler, not from a recording (no build here calls the model to record one), so this sparing needs claude ≥ 2.1.322: an older claude ignores it, and its plain interrupt stops the background agents (and, as the background-task stub models it, the background tasks) with the turn — pi-web has no other way to end only the turn. A turn still running `CLAUDE_INTERRUPT_DEADLINE_MS` (5 s) later gets SIGINT on the process group when no background work runs (`ClaudeSession.backgroundWork()` is empty, Background tasks below — a finished subagent or task whose follow-up turn has not started leaves nothing a signal would end, so it asks for no confirmation); otherwise nothing is signalled, since that would end the work too: the session emits `claude_force_stop_needed` `{ work }` (`CLAUDE_FORCE_STOP_EVENT`; `work` is `backgroundWork()`, each `{ kind: "agent" | "task", id, label }`) and holds it as asked for until the turn ends — a page subscribing meanwhile (`onEvent`, a reconnect) gets it at once; the turn's end clears it, with no event of its own: its `agent_settled` (a compaction's `compaction_end`); an automatic compaction inside the turn (`auto_compaction_end`) ends no turn and leaves it. Only `abort` with `force: true` — the page's confirmation, after naming that work — signals the group at once, background work and all; a Stop again writes the interrupt again and starts a new deadline. The partly streamed reply stays as a final message, the turn ends `aborted` (no error notice), and the session takes the next message. With no turn running Stop writes nothing and signals nothing: claude 2.1.319 answers an interrupt while idle by stopping the user's running background agents (`lib/__fixtures__/claude-2.1.319/idle-interrupt/`), so an idle claude is never interrupted. A message claude still held queued when the stopped turn ended runs next as a turn of its own.
- **The turn boundary is claude's own.** Every user line pi-web writes carries a fresh `uuid`, so claude reports the message's `command_lifecycle` (`queued` on reading it, `started` when it takes it in, `completed` / `cancelled` after its turn; `lib/__fixtures__/claude-2.1.319/README.md`). A turn's `result` ends pi-web's turn unless claude still holds a message of pi-web's it has not `started` — that message is claude's next turn, which ends the run at its own `result`. No `init` is counted: an `init` after a `started` is that message's turn; one without, while a task notification is pending, is claude's own follow-up (below). A task notification claude took into the running turn (`absorbed_mid_turn`, which leaves no stdout trace) therefore opens no turn and owes no `result`; before the next message's `init` was counted as its follow-up, the turn waited for a second `result` forever, the input stayed locked and only Stop — which then killed the process group and every background agent — ended it.
- **Steer.** A message sent while a turn runs (the composer's Steer, pi's own control; claude sessions have no follow-up queue and no recall) is written to claude's stdin at once with its uuid. Until claude `started` it, it is listed in pi's queue (`queue_update` `steering`, `get_state`'s `queuedMessages` / `pendingMessageCount`; the strip reads "Queued · n"; while the turn runs the composer's placeholder says "claude is answering; a message sent now joins this turn or waits for the next.", `claude.steerWhileRunning`, and a pane without Steer keeps `claude.sendWhileRunning`). claude either takes it into the running turn — `started` inside the turn — or keeps it queued and runs it as its next turn; at `started` the page gets it as a user message carrying `claudeDelivery: "absorbed"` or `"queued"`, shown under the bubble as "Taken into the running turn" / "Queued" (zh-CN 「已并入当前回合」 / 「已排队」, zh-TW 「已併入目前回合」 / 「已排入佇列」, `chat.claudeDeliveryAbsorbed` / `chat.claudeDeliveryQueued`). Either way the run ends once, at the result of the turn that carried the last message. History keeps both: claude stores an absorbed message only as a `queued_command` attachment (no user entry), shown as that user message labelled absorbed; a user entry whose transcript `queue-operation` `dequeue` took a message enqueued before conversation entries it waited behind is labelled queued.
- A turn's end emits `agent_end`, `agent_settled`, `prompt_done` (the running indicator, completion sound and notification follow them as for pi) and records the `result` usage.
- A background subagent leaves the session **unsettled** from its `Agent` call until claude's own follow-up turn starts (`ClaudeStreamTranslator.hasUnsettledSubagents()`): the idle timer does not reap the child meanwhile, the lease reply and `GET /api/agent/running` (`subagentsActiveSessionIds`) report `subagentsActive`, and a turn ending meanwhile carries `subagentsActive: true` on `agent_settled` / `prompt_done`, so the page holds its chime and notification and the server sends no completion push. claude announces a finished background run with `task_notification` and then starts a turn of its own (its next `init`, with no `started` message before it): alone, that is a turn of its own — `agent_start`, the hidden `claude:task-notification` anchor (no user bubble), the reply, its normal end; when it starts while a turn still runs (claude 2.1.312's stdin mode emitted the parent's `result` only at the very end), it belongs to that turn, which ends at the first `result`. Either way exactly one completion is announced. A notification claude absorbed into a running turn has no follow-up: the next user turn's `init` settles it, without an anchor. Stop invents no subagent state: a run keeps the last state claude reported. A background task (a `Bash` in the background, a `Monitor`, below) is not a subagent: running, it leaves the session settled — no `subagentsActive` on the turn's end, the lease or `GET /api/agent/running`, so the chime, notification and push go out, and fork is not refused; only from its `task_notification` until claude's follow-up turn starts does it count as unsettled, as an agent's does — except a stopped one (`status` `stopped`, or `killed` and the other words the adapter reads as stopped), which gets no follow-up turn (Background tasks, below). A running one still keeps the child from the idle reap (`ClaudeSession.hasRunningBackgroundTasks()`), since ending the child ends the task.

## Permission prompts
claude 2.1.322's host permission channel (no recording: the frames' shapes are from the bundle's schemas; the unit stub's `permission` mode and the e2e stub speak them).
- **Modes.** Ask (弹窗询问, the default) or deny (静默拒绝, the earlier behaviour). The global default and the push switch live in `<pi agent dir>/claude-permissions.json`, `{ version: 1, mode, push }` (`lib/claude-permission-config.ts`; a missing or malformed file reads `mode: "ask"`, `push: true`; pi-web's own file, so the agent-language route stays the one writer of `pi-web-settings.json`). A session's override is the index's `permissionMode?`.
- **Fixed per child.** `ClaudeSession` takes `record.permissionMode ?? the global mode` once, at the child's launch (`permissionMode`, read-only), and builds the argv from it. A changed global default therefore leaves every running child as it is; the next launch (an idle reap's `--resume` included) reads it. An override (`setClaudePermissionOverride(id, mode | null)`) writes the index first, then ends the session's live child if it is idle; the next open or send starts `--resume` with the new argv (the effort 「默认」 rule). While a permission prompt waits, a turn runs or a background subagent is unsettled it is refused with `ClaudeSessionBusyError` and changes nothing; a turn that starts while the index is being written keeps its child, and the override applies at the next launch. A fork (below) does not copy the override: the new session follows the global default.
- **Data flow.** claude's `control_request` `can_use_tool` → `ClaudeStreamTranslator` (parsing only: `permissionRequest`, never a chat event) → `ClaudePermissionBroker` (`lib/claude-permission.ts`) → an `extension_ui_request` `select` (a permission; an AskUserQuestion single-select question) or `input` (a multi-select question, or 「其他…」's text), carrying the existing `timeout` / `expiresAt` and no new field → the page's existing `ExtensionDialog` → the existing `extension_ui_response` command (`POST /api/agent/[id]`) → `ClaudeSession.send` → the broker writes claude's `control_response` (`claudeControlSuccessLine()`) to stdin and emits `extension_ui_closed`.
- **The dialog.** Title: `claude wants to use <tool>` (zh-CN 「claude 请求使用 <tool>」), claude's title / description / decision reason, then the input summary (Bash's command, a file tool's path, else compact JSON cut at 400 characters). Options: Allow once (allow with the original input as `updatedInput`, `user_temporary`), Always allow in this session (only when claude sent `permission_suggestions` and no `suppress_always_allow_rule`: the suggestions go back as `updatedPermissions` with every `destination` set to `session`, `user_permanent`), Deny (deny, "The user denied this in Pi Web", `user_reject`); Esc is Deny. AskUserQuestion is asked question by question and answered allow with `updatedInput.answers` keyed by question text (multi-select answers comma-joined, claude's own format); Esc on any question denies.
- **Waiting.** The pending requests live only in the child's `ClaudeSession` (the broker's map, in arrival order). `onEvent()` replays every pending dialog to a new listener first, so closing the page, a reload or reopening the session shows them again and they can still be answered; `isAwaitingInput()` is true while one waits (`getAwaitingClaudeSessionIds()` lists those sessions), and the idle timer never reaps a child with one. The lease reply's `awaitingInput` is `isAwaitingInput()`, and `GET /api/agent/running` and `GET /api/sessions` add those sessions to `awaitingSessionIds`, so the sidebar's awaiting marker and the favicon count include them.
- **Timeout and withdrawal.** A request unanswered for 30 minutes (`CLAUDE_PERMISSION_TIMEOUT_MS`) is denied ("no answer within the permission timeout") and its dialog closed; the dialog's countdown shows the time left, and a late answer writes nothing. A withdrawn request (claude's `control_cancel_request`) closes its dialog and nothing is written back. A turn's end (its `result`) also closes every request of the main agent still open (one without `agent_id`), writing nothing: claude cannot end a turn while it waits on its own prompt, so after Stop the dialog closes whether or not claude withdrew it (that claude 2.1.322 withdraws on an interrupt is read from its bundle, not recorded). A subagent's request outlives the turn and stays.
- **Exit.** A child that exits (a crash, an idle or override restart, Pi Web's restart killing every group) takes its pending requests with it: every dialog closes, nothing is answered, which is a denial. A later `--resume` does not ask about that call again; the user sends a new message if it is still wanted. "Always allow in this session" rules live only in that child (destination `session`, never a settings file): the next child asks again.
- **Push.** When a request opens and the global `push` is on (read for every request, so a change applies at once), every subscribed device gets `notifyClaudePermissionPending` (`lib/web-push.ts`: tag `pi-claude-permission:<id>`, the session's URL, the subscription's locale text naming the tool). The page's own browser notification is the existing one for a blocking dialog.
- **Settings route** (`app/api/claude-permissions/route.ts`). `GET ?session=<id>` → `{ mode, push, session: { override } | null }` (`override` null = follows the default; `session` null without an id or for a non-claude id). `PUT { mode?, push? }` (at least one, no other key) → `{ mode, push }` as stored. `PUT { session, override: "ask" | "deny" | null }` → `{ override, restarted }` (`setClaudePermissionOverride`; `restarted`: an idle live child was ended). The body is checked whole before anything is written: a malformed one, a non-claude id or a bad value is 400, a busy child 409 (nothing changed); JSON only (415 otherwise), and an untrusted (cross-site / foreign host) PUT is 403. Like every `/api/*` route it sits behind the web password gate (`proxy.ts`); neither aihub nor a step agent reaches it.
- **Settings block** (`components/ClaudePermissionSettings.tsx`, Settings › General after Agent language; [settings-ui.md](settings-ui.md)). The global mode as two radios (弹窗询问 / 静默拒绝), the push switch (「有待授权时推送提醒」), and, when the open session is a claude session (the GET's `session` is not null), 「本会话」 as three radios (跟随默认 / 弹窗询问 / 静默拒绝). A value shows once the route stored it; a 409 keeps the old value and says the session is busy, any other refusal shows the route's error.
- **Sidebar.** A claude row's awaiting marker reads 「等待你的授权」 / "Awaiting your permission" (`sidebar.awaitingPermission`): a permission prompt is the only thing a claude session waits on. A pi row keeps 「等待输入」.
- **Language.** The dialogs' and notices' text follows the session's `agentLanguage` (zh-CN Chinese, else English); the deny messages claude reads stay English.
- **Denied by claude.** claude's `system` / `permission_denied` (deny mode, or a rule) becomes a `notify` warning, 「claude 拒绝了 <tool>：<reason>」 / "claude denied <tool>: <reason>" (claude's `decision_reason_type` / `decision_reason_code`), beside the tool card's error.

## Polyforge decisions
- retired the chat subscription model: a claude session in Pi Web starts no `pf watch`, is never woken by a decision, and shows no decision notice above its composer (the #389 watcher `lib/claude-chat-watch.ts`, its route `/api/sessions/[id]/decisions` and the notices are gone). Every human decision of the machine is read from the daemon's decision feed in the Polyforge panel (each work item's own panel in its job detail, background tasks in Work › Tasks, and the Polyforge button's attention state), documented in [polyforge-panel.md](polyforge-panel.md#decision-feed-workbench415).
- The Polyforge panel's former needs-input chat forked a **step's** claude session under the daemon's `<state>/claude-config` as a read-only discussion assistant; it was deleted — the job card talks to the step's own agent through the daemon's owner-message relay (`pf answer`, [polyforge-panel.md](polyforge-panel.md#job-card-conversation)), and Pi Web starts no claude process of its own for a work item.

## Fork and edit from here
A claude user message carries pi's two actions, 「新会话」 ("New session") and 「从此处编辑」 ("Edit from here"), under pi's rules, labels and titles: only user messages carry them (assistant, tool call and tool result rows carry neither), and the history's entry id of each is the transcript entry's `uuid` (above), stable across reloads; a message sent in this page gets its id when the turn's end reads the history again, as for pi. #219 had left both out on purpose. Both are hidden while a claude turn or compaction runs (`claudeActionsLocked` in `components/ChatWindow.tsx`).

**The tree and the active branch** (`claudeActiveBranch()` in `lib/claude-adapter.ts`). A claude transcript is a tree: each entry names its `parentUuid` (the entry claude wrote before it; a tool result its call's entry; a compaction boundary has `parentUuid: null` and its `logicalParentUuid`), and an in-session edit leaves branches in it. The chat shows one branch, the one claude continues:
- The leaf is the nearest user or assistant entry at or above the anchor: the newest `last-prompt` checkpoint's `leafUuid` while that checkpoint is `explicit` and nothing was written after it (claude's own rewind), else the last conversation row (`user` / `assistant` / `system` / `attachment`, main conversation); with no keyed checkpoint at all, that row's newest descendant by timestamp. A compaction boundary resets the checkpoint.
- claude 2.1.312 also lets a non-explicit checkpoint win over a last row that does not descend from it. pi-web does not: right after a truncating resume, claude's newest checkpoint still names the old branch's leaf (it writes the next only after 32 KiB of transcript or at exit), while the live child already continues the new branch. Over the 53 transcripts of a real `~/.claude` (read for shape only) both rules pick the same final leaf in every file; partway through, they differ only inside a parallel tool batch, where both leaves belong to one turn and the chat is the same.
- The path is the leaf's ancestors, crossing a compaction boundary through its `logicalParentUuid`, so the history before a compaction stays listed. Hidden: for each entry on the path, every child off the path that starts a turn (a user entry that is no tool result, `isMeta` companion or compaction summary), or is an attachment or system entry with such a turn under it (a resumed child's SessionStart hook before its prompt), and everything under it. Children off the path that start no turn stay shown: a parallel tool call's results and the reply's split entries hang beside the path inside one turn (claude re-collects them the same way). Sidechain entries are another conversation and never part of the tree. A transcript without a fork shows exactly what it showed before; on the same 53 real transcripts the rule hides 31 entries, all in claude's own rewinds.
- The history (`claudeTranscriptToMessages()`), its subagent runs (a run started on another branch is not listed) and the context meter's transcript count (`claudeTranscriptContextTokens()`) read the active branch only. There is no branch switcher: the replaced turns stay in claude's file, unreachable from the page.

**「新会话」** (`fork`, `forkClaudeSession()` in `lib/claude-session.ts`):
- **The fork point is pi's**: a copy of the conversation **before** the message (pi's `fork` copies up to the message's parent). The copy (`claudeTranscriptFork()`) is every line of the active branch claude wrote before the message's entry — the conversation as it stood when the message was sent; another branch's entries, and the checkpoints naming them, are left out — minus the `queue-operation` lines of that message's own submission (those after the conversation's last message before it: claude can write the previous turn's `stop_hook_summary` between them and the message), each entry's top-level `sessionId` made the new id; every other byte stays as claude wrote it: entry uuids (so the copy's entry ids are the source's), compaction boundaries with their hidden summaries, the hook attachments, `last-prompt` and other bookkeeping, sidechain entries of an older claude, a line that does not parse. A value an entry quotes (a tool result's text, a receipt's `outputFile`) keeps the source's id.
- **Refused**: an id that is no user bubble of the active branch (an assistant entry, a tool result, claude's bookkeeping, a compaction summary, the follow-up anchor, an `isMeta` companion, a sidechain entry, another branch's message) and a message inside a tool exchange — a call made before it answered after it, each answer closing the latest open call of its id — so a copy never ends on an unanswered call; the source running a turn or a compaction ("A claude turn is running; fork when it ends"), or holding an unsettled background subagent, whose sidecar is still being written and whose result has not reached the conversation (`claudeForkRefusal()`: "A claude background subagent is still running ("<description>", …); fork when its result is in", naming each one still running, or, when the only one has finished and its follow-up turn has not started, "A claude background subagent finished and claude has not taken up its result yet; fork when it is in"; the actions stay offered then, the refusal is the error notice). A running background task refuses nothing: the fork starts no child and ends none, and the task's output is no part of the conversation until claude's follow-up turn. A refusal writes nothing, and pi-web answers it 500 like the other claude command errors (a fork without an `entryId` is 400).
- **Files**: the copy is written atomically (0600) beside the source's transcript as `<new id>.jsonl`, with copies of the subagent sidecars it refers to (`claudeLinkedSidecars()`: by the receipt's `toolUseResult.agentId`, else a sidecar meta's `toolUseId`, then the runs those started; each sidecar's `sessionId` rewritten, its meta verbatim) under `<new id>/subagents/`, then the index record: the source's cwd and current model, effort and Agent language, `created` / `modified` now (so it sorts first), the source's `firstMessage`, no name, not archived and no usage (the totals count what this session spent). The source's transcript, sidecars and record are only read: byte-identical. The record is written last, so a write that fails part way (a disk error) leaves at most unlisted files under the new id. A message with nothing the chat shows before it (the first one) writes no transcript, so the new session's first launch is `--session-id` (a new conversation) with `firstMessage` empty until its first prompt. Nothing is spawned by the fork; the new session is a claude session like any other — listed, opened, resumed (`--resume <new id>` loads exactly the copy), renamed, archived and deleted as above (delete removes its transcript and record; its `<new id>/` folder, the copied sidecars and whatever claude adds there, stays, as a claude session's own folder does). A sidecar is copied whole: a background run launched before the fork point and finished after it shows as completed in the copy, with its whole run, although the copy's conversation never received that result (the `task-notification` turn lies after the cut). claude's own per-session data elsewhere (`file-history`, tool-result files the conversation names by path) stays the source's.
- The page posts `fork`, then opens the new session (`onSessionForked`), its composer empty.
- Not `--resume <id> --fork-session --resume-session-at <entry>`: the flags compose in the 2.1.312 bundle, but such a fork exists only once claude has run (a spawn per click, and no file before the first prompt), it cannot start before a compaction or before a first message, and what it writes cannot be checked without a real model; the copy needs no child and its ids are the source's.

**「从此处编辑」** is pi's in-place edit (`handleEditContent` in `hooks/useAgentSession.ts`, shared by both harnesses):
- Clicking it puts the message — its text and images — in the composer (when the composer is empty, as for pi) and marks the bubble as being edited, with Cancel in place of the action. Nothing is sent or written: Cancel leaves the session exactly as it was.
- Send is one command: `prompt` with the message's `entryId`. The view drops the edited message and everything after it, as pi's navigate does, and shows the new prompt. On the server (`editClaudeSession()`), the same session continues from before that message: the idle child is ended and the next one starts `--resume <id> --resume-session-at <the message's parent>` (`claudeEditResumePoint()`), then gets the prompt. The truncation is set before the old child ends and taken by whichever start comes next (this edit's, or a page's stream reconnecting first), so no plain `--resume` slips in between; a start that did not take it refuses the edit ("restarted before the edit"). The session id, its record and its row stay; no session is created. The replaced turns stay in claude's file on a branch of their own, which the history no longer shows (above).
- Offered only where claude can resume before the message (`claudeEditPoints()`, served as `claudeEditEntryIds`): the message and its parent lie on the active path after the latest compaction boundary (claude loads nothing further back) and no tool exchange spans it. So a first message with nothing before it in the transcript (no SessionStart hook output; the recordings' prompts are such) offers no edit, and neither does a message before the latest compaction; 「新会话」 still does.
- A message starting with `!` is a prompt like any other, so it carries a staged edit (below).
- Refused, changing nothing (500 with `code: "prompt_rejected"`, so the page puts the edit back as pending — unless the re-read history no longer holds the message — and returns the text to the composer): an empty prompt, a turn or compaction running, unfinished background work — an unsettled background subagent or a running background task — named in the error as for the effort above (ending the child would end it), and a message no edit can start from, with its reason ("Invalid entry ID for editing", "edits only at one of its user messages", "not on the conversation's current branch", "middle of a tool call", "before the conversation's last compaction", "Nothing comes before this message").

**What claude 2.1.312 does with the truncating resume**, read from its bundled JavaScript (`strings` of the binary; never run). Inferred from code, not observed:
- `--resume-session-at <message id>` (hidden; "When resuming, only messages up to and including the chain entry with <message.id> — any chain-entry UUID, typically the kept turn's last entry (use with --resume in print mode)") is refused without `--resume` ("Error: --resume-session-at requires --resume"). After loading the resumed chain, claude looks the uuid up in it and keeps the chain up to and including that entry; an entry the loaded chain does not hold is refused ("No message found with message.uuid of: <uuid>", exit 1). The loaded chain begins at the latest compaction boundary (the messages that compaction preserved are relinked after it), which is why pi-web offers no edit before one.
- Nothing is rewritten: the transcript is append-only, and the next entries claude records chain to the last kept entry (`insertMessageChain`: the first new entry's `parentUuid` is the last entry already on disk, each next one the entry before it, a tool result its call's entry), so the file holds both branches.
- `--resume-drops-turn <prompt uuid>` (with `--resume-session-at` only) refuses the resume unless everything discarded is that one turn (its prompt first, then only its replies, tool results and furniture: no other prompt, absorbed queued message, task notification or compaction summary). pi-web does not pass it: it would refuse every edit but the last turn's, and the edit is already refused while a turn runs or background work is unfinished.
- `--fork-session` is not checked against them: the truncation applies to the loaded chain either way.
- A live control request, `rewind_conversation` (`target_message_uuid` …), does the same in a running child and records an explicit checkpoint; it is not used (an undocumented wire protocol, unverifiable here).

## Context meter (#368)
The header's context meter (and the session panel's Context row) reads `get_state`'s `contextUsage`, pi's shape `{ tokens, contextWindow, percent }`, through the same usage reads as for pi. Before this, a claude session answered `null` from its first version on, so neither showed: the meter was never implemented for claude, not lost.
- **Tokens** are what the main conversation's latest API response filled: input + cache write + cache read + output (`claudeContextTokens()`), the count claude reports itself — the `compact/` recording's last reply sums to its compaction's `pre_tokens`, 16739. Live, `ClaudeStreamTranslator.contextTokens` takes each report of a message's usage (`message_start`, every `assistant` event, `message_delta`, whose output is the final one; within one message id each count keeps its largest value). A report that counts nothing (claude's synthetic and API-error replies) changes nothing; a subagent's replies (`parent_tool_use_id`, sidechain entries) are another context and never count. A compaction replaces the count with what claude reported it left (`compact_metadata.post_tokens`), or unknown when it reported none.
- A child that has reported nothing yet (a resumed child before its first reply) reads the transcript once (`claudeTranscriptContextTokens()`): the last main-chain reply with a usage, or a later `compact_boundary`'s `compactMetadata.postTokens`.
- **Window**: the one claude itself reported for the session's current full model name in this child's latest `result` that named it (`result.modelUsage[<model>].contextWindow`, `claudeReportedContextWindows()`, kept per model by `ClaudeStreamTranslator.contextWindow()`), the window claude's own compaction counts against; it depends on the account as well as the model, so an account without the long context gets a smaller one than the catalog's, and dividing by the catalog's would understate the usage. Until the child reported one for the model (a fresh or resumed child before its first `result`, a model switched to and not answered with yet), pi's built-in model catalog stands in: the `anthropic` entry of that full name (`claudeContextWindow()`). A session on one of claude's aliases reads both under the full name the probe's latest `initialize` answer resolves it to (`claudeResolvedModel()`, 2.1.322's `opus` and `default` → `claude-opus-5-5`); an alias whose full name the catalog lacks (2.1.322's `fable` → `claude-fable-5-2`) has no meter until claude reports a window. Nothing is persisted, so a resumed child shows the catalog's window until its first `result`. A model switch changes the window and keeps the count. Every 2.1.312 recording reports 1,000,000 for haiku, sonnet and opus, the catalog's figure (`lib/claude-session.test.mjs` pins this); `lib/claude-session-window.test.mjs` and `e2e/context-after-compact-368.mjs` replay the `compact/` recording rewritten to 200,000.
- Unknown is never shown as a number: no window (none reported, none in the catalog) → `contextUsage: null`, nothing is shown; a window but no count (no reply yet, or a compaction without a size) → `{ tokens: null, percent: null }`, shown `? / <window>` as pi shows it after a compaction (a phone shows no context figure). With no live child the routes answer `{ running: false }` as for an idle pi session; opening the session's event stream starts the child and reads the usage again.
- The page reads it when pi's does: an assistant reply's end, the turn's end, a successful compaction's end (`compaction_end`, the size claude reported after `/compact` shows at once, with no reply), a stream (re)connect and a session load with state.
- This is the context meter, not usage: the session's token and cost totals stay the `result` aggregates above.

## Live status
- **Retry banner.** claude's `system` / `api_retry` (it waits to retry a failed request; a rate-limited one is `error_status: 429, error: "rate_limit"`) is pi's `auto_retry_start` (`attempt`, `maxAttempts` = `max_retries`, `delayMs` = `retry_delay_ms`, `errorMessage` = `<error> (<error_status>)`), so the composer shows pi's `chat.retrying` banner. It goes at the next main `stream_event` (the retried request streams: `auto_retry_end` success), or at the turn's `result` (`auto_retry_end` unsuccessful), and `agent_end` clears it anyway.
- **Auto-compaction.** claude's `status: "compacting"` is pi's `auto_compaction_start` (`reason: "threshold"`), announced once although claude re-sends it every 30 s while it compacts; the next `compact_boundary` ends it with `result.tokensBefore` (`pre_tokens`), a `status` with a `compact_result` other than `success` ends it with `errorMessage` (`compact_error`), and a `result` while it is open ends it `aborted`. The composer shows pi's `chat.compacting` state meanwhile and claude's compaction line after. A manual `/compact` is unaffected: `lib/claude-session.ts` drops the translated events of its compaction turn and settles it from the boundary and the result.
- **`rate_limit_event` is not shown.** It is claude's quota report (`rate_limit_info.status` `allowed` / `allowed_warning` / `rejected`, `resetsAt`), sent whenever the quota information changes, `allowed` included: no waiting state. A rate-limited wait claude retries already comes as `api_retry` (the banner above), and a refused request ends the turn with claude's error `result`, which the chat already shows.
- **Hook activity.** Off by default: claude reports hooks only with `--include-hook-events`, which a session gets when Settings › Claude's hook switch was on at its creation (the argv table above). Then claude streams `system` `hook_started` / `hook_progress` / `hook_response` frames for every hook of the user's config (2.1.322: a `SessionStart` hook's frames come as claude starts, before the turn's `init`; `PreToolUse` / `PostToolUse` around each matching tool call). The adapter shows them in a light form through pi's own extension UI, never as a message or a transcript entry: each `hook_response` replaces the one status line above the composer (pi's `setStatus`, key `claude-hooks`, `CLAUDE_HOOK_STATUS_KEY`) with `hook: <hook_event> · <hook_name>`, plus ` · failed` for an `error` outcome or a non-zero `exit_code` and ` · cancelled` for a cancelled one; the turn's end (its `result`, or a turn that ends without one) clears the line. A failed hook is also one warning notice, `claude hook <hook_name> failed (exit <code>): <first output line>` (stderr first, at most 200 characters). `hook_started` and `hook_progress` show nothing, and the history replays no hook activity (the transcript is read as before). A hook that blocks an action still reaches the chat through claude's tool result or reply. The frames are claude 2.1.322's as recorded in `lib/__fixtures__/claude-2.1.322/hooks/` (one haiku turn; `lib/claude-hooks-445.test.mjs` replays it).

## Attachments
- Entry points: the attach button, paste and drag-and-drop, identical in a fresh claude composer and an open claude session (and while a claude turn runs, as for pi); paste and drop go through the same `processImageFiles()` as the button.
- Limits are pi's: at most 10 images per message (`MAX_ATTACHED_IMAGES`), each at most 10 MiB (`MAX_ATTACHED_IMAGE_BYTES`); the 11th and an oversized image are not attached, silently, as for pi. claude adds a format whitelist, PNG / JPEG / GIF / WebP (`CLAUDE_IMAGE_MIME_TYPES` in `lib/image-attachments.ts`): any other image (BMP, SVG, …) is not attached and the composer shows one visible line, "Only PNG, JPEG, GIF and WebP images can be attached to a claude session." (`chat.claudeImageFormats`, in all three locales), cleared by the next accepted pick or when the composer is cleared. pi's `image/*` gate, its silent handling and its warning rules are unchanged.
- No client-side resizing: an image is sent as picked. One over claude's own API limit (5 MB) goes to claude's own compression or fallback; if claude fails, its error shows as for any failed turn.
- The server validates before anything is written: for a claude `prompt`, `POST /api/agent/new` and `POST /api/agent/[id]` run `validateClaudeImages()` (array, ≤10, valid base64 within 10 MiB, whitelisted media type) before a record is created or a child started; a failure is `400 { error, code: "prompt_rejected", accepted: false }`, and nothing reaches claude's stdin. pi's path is untouched.
- Transport: one stdin user line whose content is the text block (omitted when there is no text) then one `{ type: "image", source: { type: "base64", media_type, data } }` block per image, base64 and media type exactly as the composer read them (`claudeUserInputLine()`; without images the content stays the plain string). Its `message` content is byte for byte that of the line claude 2.1.312 accepted in `lib/__fixtures__/claude-2.1.312/image/stdin.jsonl`; the line adds a top-level `uuid`, as every user line does (the turn boundary above).
- Image-only sends are turns. A session whose first prompt has no text is listed with the locale-independent `firstMessage` `[Image]` (`claudeFirstMessage()` in `lib/claude-shared.ts`, used by the server's index record and the client's transient sidebar row); a prompt with neither text nor image is still refused ("A claude prompt needs text").
- Display: the live user bubble carries the images (`claudeUserPromptEvents()`), and a reload maps them back from claude's transcript (`image` blocks with inline base64). pi-web keeps no copy. claude's hidden `isMeta` `[Image: source: …]` companion entry renders nothing. claude's own `/tmp/claude-<uid>/…/images` copies belong to claude and are untouched by pi-web; delete still removes only the transcript and the index entry.
- No "Images may not be sent" warning for any claude model, whatever pi's model list says; pi's rules are unchanged. A claude draft keeps its images like a pi draft; while a claude turn runs the composer offers Steer, which sends the draft with its images to claude's stdin at once (the Steer bullet above).

## Subagents
claude's own subagents — an `Agent` (or older `Task`) tool call — are first-class runs attached to the call that started them, never main-conversation messages. claude's `local_bash` tasks — a `Bash` command, foreground or background, and a `Monitor` — also send `task_*` events but are no runs (below). The run model is `lib/claude-subagent-view.ts` (client-safe, no format parsing): `{ toolCallId, agentId, agentType, description, prompt, background, status, startedAt, progress, usage, result, entries }`, entries keyed by claude's entry `uuid`; `startedAt` is the timestamp of the assistant frame or transcript entry holding the run's `Agent` call, the same fact live and in history.
- **Live** (`ClaudeStreamTranslator`): every stdout event with a `parent_tool_use_id` is the subagent's — its `assistant` replies and `user` tool results become entries of that run (its `stream_event` partials are not shown); a nested `Agent` call inside starts its own run, at any depth. The `system` task events feed the header: `task_started` (agent id, `subagent_type`, description, prompt, `is_backgrounded`), `task_progress` (the progress description and running statistics), `task_updated` (status), `task_notification` (final status, result, `usage` → tokens / tool uses / duration). Each change goes out as one `claude_subagent` event: the run's header plus only the entries new in it. The `Agent` call's tool result stays in the main conversation; an async launch receipt (`status: async_launched`) names the agent and marks the run background, and is **not** completion: only claude's task events settle a run, and nothing pi-web does (Stop included) invents a state — except the child's exit: no event can come after it, so every run it still had running, at any depth, settles live as `stopped` with the usual `claude_subagent` event (`settleOnExit()`), and the running list drops it. History is not changed by this: a transcript whose run has no notification still reads it running.
- **Resume** (the 2.1.322 `relay/` recording): a `SendMessage` to a finished agent resumes it. claude's task events for the resume (`task_started`, `task_notification`) then name the `SendMessage` call, while the agent's entries still name the original `Agent` call and land in the same sidecar. So the run reopens (`running`, `startedAt` = the `SendMessage` call's time) and no second run appears; claude can also resume an agent itself with a message queued after its last tool round (a `task_started` under the `Agent` call again, started now). The resume's prompt (the relayed text) leaves the run's own. A resume claude runs in the background gets its own notification and follow-up turn (the run is unsettled until then); an `awaited` one hands its report back inline and gets none. Live and history alike, this is the one exception to "a settled run never returns to running".
- **Running list** (`runningClaudeSubagents`): every run claude reports `running`, at any depth, oldest `startedAt` first (an unknown start last). It goes out through the existing paths — steered into a running main turn (#395), a plain prompt when idle — and claude's `SendMessage` tool card follows it, so both come back from the transcript on reload; there is no new message type or field. Delivery is claude's, measured in the `relay/` recording: a running **background** subagent gets the message at its next tool round (the queued message shows in its timeline from the sidecar only), and a **finished** one is resumed with it, its reply streaming under its original `Agent` call (the panel's run). A running **foreground** subagent would only get it after it finished, because the main agent waits in the `Agent` call; so (owner ruling) pi-web first sends `background_task` `{ toolCallId }`: claude's own `control_request` `{ subtype: "background_tasks", tool_use_id }` (`claudeBackgroundTaskLine()`, the TUI's Ctrl+B) over the control channel with the same 15 s deadline as `set_model`, answered `{ backgrounded: true }`. It is not idle-guarded (it is meant for a running turn) and it pauses or stops nothing: the `Agent` call returns claude's async receipt, the main turn ends early, and the subagent's end comes as a background notification and claude's follow-up turn. Only on `backgrounded: true` is the relay message sent; a refusal or a failed send raises a notice, sends nothing more and rejects, so the panel keeps its text, which never goes into the main composer's draft. A staged edit stays staged. Reach: `background_task` is one more command of the existing `POST /api/agent/[id]`, behind pi-web's own access gate, acting only on that session's live child; nothing a step agent or the daemon calls.

## Background tasks
claude reports a `Bash` command and a `Monitor` as tasks of type `local_bash`, through the same `task_started` / `task_updated` / `task_notification` events as a subagent: the 2.1.319 `absorbed-notification/` recording holds a background Bash (`task_started` with `is_backgrounded: true`, `task_type: "local_bash"` and its `tool_use_id`; at its end `task_updated` `patch: { status: "completed", end_time }` and `task_notification` with its `output_file`) and a foreground one (`is_backgrounded: false`), and claude 2.1.322's bundle registers every task type that way (`task_type` is the task's type; `is_backgrounded` is set for `local_agent` and `local_bash`). A `Monitor` is a `local_bash` task too (its kind does not go on the wire), so the two are told apart by the tool name of the call the task names (`Bash` / `Monitor`); a background agent is `local_agent`. A foreground task claude moves to the background later says so in `task_updated` `patch.is_backgrounded: true`. `background_tasks_changed` is not read.
- **Not a run** (`ClaudeStreamTranslator`): a `local_bash` task's events never touch the subagent runs — no `claude_subagent` event, no entry in the running subagent list, nothing unsettled while it runs (before, a long background `npm run dev` held the session as an unsettled subagent: no completion sound, notification or push, fork refused). The translator keeps each task by its task id; one running in the background (`is_backgrounded`, a `Monitor`, or a later `patch.is_backgrounded: true`) is listed, and every change of a listed task goes out as one `claude_background_task` event `{ task }`, the whole snapshot (`lib/claude-background-task-view.ts`, client-safe: `taskId`, `toolCallId`, `kind` `shell` | `monitor`, `command` — the call's `input.command` —, `description`, `status` running | completed | failed | stopped, `startedAt`, `endedAt`). A foreground task is not listed. A settled task stays settled; its end is claude's `end_time`, else when pi-web saw it settle. `hasRunningBackgroundTasks()` / `runningBackgroundTasks()` answer from the listed tasks.
- **Follow-up turn**: claude follows a background task's notification with its own turn as it does a background agent's, so the notification counts as notified (unsettled) until the next `init`, which opens that turn with the hidden anchor (or, a user turn, takes it in), exactly as for an agent. A `completed` / `failed` notification is followed up (the 2.1.319 recording); a `stopped` one is not counted: claude 2.1.322's shell kill sets the task `status: "killed", notified: true` and then sends the SDK `task_notification` `status: "stopped"`, and a task already marked notified is never queued to the model, so no follow-up turn comes and counting it would leave the session unsettled for good (no chime, notification or push; fork refused).
- **The session** (`lib/claude-session.ts`): a running background task is not unsettled — a turn ending meanwhile carries no `subagentsActive`, the lease and the running list do not report it, fork goes ahead (Subagents and Fork, above) — but the idle timer does not reap a child while one runs (`ClaudeSession.hasRunningBackgroundTasks()`): the reap would kill it.
- **Restarts refused**: the operations that end the child to start another — the effort back to default (Model, effort and compact) and an in-session edit (Edit) — are refused while background work is unfinished (`ClaudeSession.hasUnfinishedBackgroundWork()`: an unsettled background subagent or a running background task), with every piece named. `ClaudeSession.backgroundWork()` is the one list of that work, `{ kind: "agent" | "task", id, label }` — background subagents this child reported running and claude has not followed up (`ClaudeStreamTranslator.runningBackgroundSubagents()`: their `Agent` call id and description, else agent type), then background tasks still running (task id, `claudeBackgroundTaskLabel()`); `restartRefusal(action)` turns it into the English refusal (`claudeRestartRefusal()`), which, when nothing is listed, says a finished subagent's or task's result has not been taken up yet (claude's follow-up turn is still to come). Every other claude command keeps the child: a model switch and an effort level go over the control channel, compact is a turn on stdin, a fork copies files, `background_task` is a control request; a session's deletion ends its child on purpose, and the server's own shutdown ends every child.
- **Stop one, read its output**: `stop_task` `{ taskId }` writes claude's own `control_request` `{ subtype: "stop_task", task_id }` (`claudeStopTaskLine()`; 2.1.322 schema: "Stops a running task.", answered `{}`) and resolves `{ stopped: true }` once claude accepts; claude then settles the task (`task_updated` `patch.status: "killed"`, `task_notification` `status: "stopped"`, both mapped to `stopped`), which reaches the page as the task's `claude_background_task` snapshot like any other change; the other tasks run on. `task_output` `{ taskId }` writes `{ subtype: "get_task_output", task_id }` (`claudeTaskOutputLine()`; 2.1.322 schema: "Reads the end of one background shell or Monitor task's output: at most the last 8 KiB … a host polls it while the task runs", answered `{ output, total_bytes, truncated }`) and resolves `{ output, totalBytes, truncated }`. Both use the control channel's 15 s deadline (as `set_model`), are not idle-guarded, and act on the live child only (`ClaudeSession.stopTask()` / `taskOutput()`): a missing `taskId` or no live child is refused before anything is written (the route answers 400 and spawns nothing, as for `background_task`), and claude's error comes back as the rejection with its text. claude 2.1.322 handles both in print mode beside `background_tasks`; shell task ids look like `b` + 8 of `[0-9a-z]`. Reach: two more commands of the existing `POST /api/agent/[id]`, behind pi-web's own access gate, acting only on that session's live child; nothing a step agent or the daemon calls.
- **Reconnect**: a page subscribing to a live session (`ClaudeSession.onEvent`: a reconnect, a session switched back to, a page after a pi-web restart) first gets the whole list of the tasks the child runs, one `claude_background_tasks` `{ tasks }` event (`CLAUDE_BACKGROUND_TASKS_EVENT`: running snapshots in start order, empty when none runs; a settled task is not in it), then a force stop still asked for (Lifecycle, above). The page replaces its tasks by that list, so a task that ended while the page was not listening — its `claude_background_task` never reached it — leaves the running list instead of staying there as running (and answering Stop task and its output with a 400).
- **Stop**: Stop mid-turn spares them, and a turn that outlives its deadline while one runs asks for a force stop naming them instead of signalling (Lifecycle, above).
- **Exit**: when the child exits its tasks end with it; a running one settles as `stopped` with the usual event (`settleOnExit()`).
- **The page** (`hooks/useAgentSession.ts`, `components/ClaudeSubagentRunningList.tsx`, `components/ClaudeBackgroundTaskPanel.tsx`, `components/ChatWindow.tsx`): the hook folds each `claude_background_task` snapshot into the session's tasks (`mergeClaudeBackgroundTask()`: the snapshot replaces the task, a settled task never goes back to running; another session's tasks start over), which are not persisted: a new stream's `claude_background_tasks` replaces them (`replaceClaudeBackgroundTasks()`: every running task is the list's — one the page held as running and the list lacks is dropped — while a task the page saw settle keeps its final state and never goes back to running; another session's tasks start over), so after a reload, a session switch or a pi-web restart the list shows what the child runs. The running background tasks are buttons of the subagents' list grid above the composer (/#505: same size, layout and three-row box), after the running subagents, oldest start first, in their own teal (`data-claude-task-item` = the task id, `data-claude-task-kind`): a kind badge (`Bash` / `Monitor`), the label (`claudeBackgroundTaskLabel()`, monospace, cut with an ellipsis, the full label as the title), the running label and the elapsed time; the list's group label names both (`claudeSubagent.runningList`). A task that settles leaves the list. A click opens the task's panel in the subagent panel's floating slot — one choice holds either kind, so one panel is open at a time, opening one closes the other, a session switch closes it, and Esc and Close close it as they do the subagent panel. The panel (`data-claude-task-panel` = the task id) shows the kind badge, the whole command (wrapped; a monitor's description below it when it differs), the status, the elapsed time, Stop task (while it runs: `stop_task`; claude's refusal shows as a line with its text) and Close; its body is the recent output (`task_output`): read on open, every 2 s while the task runs and the panel is open, once more when it ends; an empty output reads "No output yet", a truncated one says it shows the last part, and claude's refusal shows its text. A task that ends while its panel is open keeps the panel, showing the final status. The force stop (Lifecycle, above): on `claude_force_stop_needed` a notice (`ClaudeForceStopNotice`, `data-claude-force-stop`) above the running list says the turn has not stopped and that force stopping also ends the listed background work (each piece as Subagent / Task and its label), with Force stop (`abort` `{ force: true }`) and Keep waiting (closes the notice only; a later Stop asks again at its deadline); the turn's end (`agent_settled`, `prompt_done`, `compaction_end`) removes it. `CLAUDE_FORCE_STOP_EVENT` and the work's shape (`ClaudeBackgroundWork`) live in the client-safe `lib/claude-background-task-view.ts`, which the session imports. `e2e/claude-background-tasks-443.mjs` drives it in the browser against the stub below: `R443a` both tasks in the grid as task items (kind, command, running, a ticking time; no subagent item; the session not `subagentsActive`), kept by a reload, the panel showing the output from `get_task_output`; `R443b` the panel's Stop task sends `stop_task` for that task only, it leaves the list, the panel shows Stopped, the Monitor and its process run on; `R443c` Stop mid-turn (`hang`) sends the interrupt with `spare_background_tasks: true`, the turn ends, the Monitor stays listed and alive, nothing is signalled; `R443d` a `stuck` turn: at the deadline the notice names the Monitor with nothing signalled, Keep waiting removes it, a second Stop brings it back, Force stop sends SIGINT and empties the list.
- **The view** (`lib/claude-background-task-view.ts`): `runningClaudeBackgroundTasks()` (running, oldest start first), `replaceClaudeBackgroundTasks()` (the whole list's replacement, above), `claudeBackgroundTaskLabel()` (claude's own task-list rule: a shell task by its command, a monitor by its description, each falling back to the other) and `claudeBackgroundTaskElapsedMs()` (to now while running, to its end once settled). `lib/claude-background-tasks-443.test.mjs` replays the recording and synthetic frames in its shapes, and drives a session against the background-task stub `e2e/claude-stub/claude-bg-tasks.mjs`: a user line `bg: <command>` (or `monitor: <description>`) is a turn that starts a background `Bash` (`Monitor`) with a real child process standing in for the command, in the stub's process group; the turn's entries go to the transcript first; `hang` is a turn that streams a delta and ends (`error_during_execution`) at an interrupt, `stuck` one that only answers it, `stuck-finish: <command>` a `stuck` turn in which that command's task completes (a finished task awaiting claude's follow-up turn); an interrupt without `spare_background_tasks: true` also stops every running task (each settled as `stop_task` settles one), as claude's plain interrupt stops its background work, so a Stop that lost the flag fails `lib/claude-background-tasks-443.test.mjs` and `e2e/claude-background-tasks-443.mjs` `R443c`; `stop_task` of a running task answers `{}`, kills its child and emits `task_updated` `killed`, `task_notification` `stopped` and `background_tasks_changed`, `get_task_output` answers fixed lines naming the task's command, and an unknown id gets an error naming it; SIGINT / SIGTERM kill the task children.

## No tool preset, no `configured`
claude sessions have no pi-web tool preset and therefore no `configured` state: pi's tool preset menu (where `configured` means "send no tool override, follow pi's `settings.json` `defaultTools`", see [tools.md](tools.md)) is not offered, and claude's tools, MCP servers and hooks come from the user's own claude config.

## Unsupported pi features
Hidden for claude sessions: ask-in-new-chat (fork and edit-from-here are claude's own now, above), branch navigation (the history is the active branch alone), compaction recovery (pi's truncation prompt) and automatic-compaction settings, pi's reasoning levels and tool changes (claude has its own model, effort and compact controls, above), follow-up and queue recall (claude takes pi's Steer: the Steer bullet above), built-in slash commands (`/mcp` included), background tasks, the pi subagent switcher and side panel (claude's own subagents render in their Agent row instead), title generation. HTML export is disabled with visible text in the toolbar. claude's permission questions are Pi Web's own extension dialogs (Permission prompts, above), with no claude-only dialog type. A claude turn renders like a pi turn: once answered, its process details (intermediate text, tool calls and results) fold behind the turn's toggle — with one exception: a step whose only displayed blocks are `Agent` / `Task` calls of **background** runs still running renders after the fold, at the turn's top level, so the running subagent stays visible after the parent answered; once its run settles the step returns into the fold. A foreground `Agent` call is an ordinary step, and no other rule changes. claude's follow-up turn starts at its hidden `claude:task-notification` anchor (`isMessageGroupAnchor()`), live and in history alike: it is its own turn, with its own process details, and no user bubble.
