# Sessions, branching and live events

## AgentSession lifecycle (`lib/rpc-manager.ts`)
- One `AgentSessionWrapper` per session id in `globalThis.__piSessions` (`globalThis` survives Next.js hot reload; a module-level Map does not). Concurrent `startRpcSession()` calls share one start Promise (`globalThis.__piStartLocks`). Idle timeout: 10 minutes (`PI_WEB_IDLE_TIMEOUT_MS`, `0` disables).
- Stop cannot cancel a run awaiting a promise that ignores the abort signal (a third-party extension handler or tool): `inner.abort()` never returns. So Stop (`abort`, `abort_bash`) sets `forceShutdownOnIdle` and arms the idle timer, shutting the wrapper down one idle timeout after the first Stop even while it runs. Later commands (a reload's `get_tools`, Stop again) must not push that deadline back; with `PI_WEB_IDLE_TIMEOUT_MS=0` it still arms, at 10 minutes.
- **A wrapper is closing from the moment `shutdown()` or `destroy()` starts**: `isAlive()` turns false at once, so routes stop sending it commands, but `startRpcSession()` builds the replacement only once it has disposed (`closingRpcSessionWait()`, at most the shutdown deadline plus 1 s). Until then it owns the session: an extension's `session_shutdown` may append to the file, and `dispose()` releases provider resources (a Codex websocket) by session id. `setRpcSessionTools()` waits likewise for a closing wrapper or a start under way, then applies the selection to the resulting wrapper, never through a second `SessionManager`. A stuck run counts as busy (`isRunning()`) until disposal.
- `reload` is refused while the session runs (`isSessionRunningForReplacement()`, as `clone`): it invalidates the extension runner, and the running turn still holds the old `ctx`, so it died at its next hook with "This extension ctx is stale…" (#1172). pi's TUI refuses `/reload` while streaming or compacting too, with the same text. An extension command's `ctx.reload()` checks only streaming and compacting, as the TUI's does, and warns instead of throwing: the command runs inside its own `prompt`, so a pending prompt there is the command itself.
- The closing wrapper stays in `__piSessions` until disposed or replaced; its `onDestroy` removes the entry only while it still points at that wrapper, or a late cleanup would unregister the replacement. `registerRpcWrapper()` clears the callback of the entry it replaces (a pre-hot-reload wrapper still deletes by id).
- Extensions get `PI_WEB_SHUTDOWN_DEADLINE_MS` (5 s; `0` or invalid keeps the default) for `session_shutdown`, then the wrapper logs once and disposes anyway: closing an MCP connection has no upper bound. Extension binding is awaited first, without a deadline.
- A session whose cwd was deleted outside pi-web still opens (its transcript, the event stream's wrapper), but `send("prompt")` refuses with `Directory does not exist: <cwd>`, the text `/api/agent/new` answers for a fresh composer's missing cwd (#1061): a run would reach the model only for its tools to fail, and pi's `write` would recreate the folder. The pi CLI does not resume such a session either. The composer keeps the draft; `ensureNewSession()` passes the server's `error` on, never a bare `HTTP 400`. That refusal, `/api/agent/new`'s and `/api/models`' for a missing folder all add `reason: "cwd-missing"` and the folder (`lib/missing-cwd.ts`, #1422): the composer then shows a translated "Project folder not found" banner naming it, not the models' "Model error" banner nor an English notice, since nothing reached a model. The wrapper throws a plain Error with those fields and the route reads them, never `instanceof`: the wrapper may come from another route's bundle. The banner's two sources stay apart: a refused prompt, steer or follow-up keeps it until a send succeeds, and a model list load clears only what it set (a removed worktree's list loads from the main repo while the folder is still gone). The pi CLI instead offers to continue in the shell's cwd (`SessionManager.open(file, dir, cwdOverride)`); pi-web has no such cwd, and the sidebar's Fork keeps the source's cwd, so the way on is a new session in the new folder.

- **claude sessions are child processes, not wrappers** ([claude-sessions.md](claude-sessions.md)): no `AgentSessionWrapper`, one `claude -p` child per live session in its own registry. The lease renews it and never spawns, it ends one idle timeout after the last renewal with its whole process group, and the next open or send starts `claude --resume <id>`. Its list row comes from pi-web's claude index and its history from claude's own transcript; neither touches the pi sessions store.

## Fork never touches the running AgentSession
Never fork through `AgentSession.fork()` / `AgentSessionRuntime.fork()`: they replace the session in place (`inner.sessionId` becomes the new id; the current run is aborted first), so a wrapper registered under the old id would serve the forked state and corrupt the `parentSession` chain.

`send("fork")` / `send("fork_branch")` open a separate `SessionManager` on the source file and `createBranchedSession()` from it. So forking works **while the source runs** (only a running `!` shell command refuses): pi appends each finished entry synchronously in this process, and the in-flight assistant message lands after the fork point. A source with no file yet is refused with the upstream "has not been saved yet" wording. After a `fork` (never `fork_branch`) an idle source is shut down, since the browser moves to the child; a running one keeps its run and its running row. `clone` refuses a running session: it copies the current branch, which is the run in progress, and then shuts the source down.

## In-session branching waits for the run
pi's `navigateTree()` refuses while streaming or compacting: the file has one leaf pointer that the run appends under, and navigating swaps the agent's context. So "Edit from here" is hidden while busy, the BranchNavigator renders read-only (`locked`) with a note, and `handleLeafChange` refuses (switching only the view would show the live run under another branch). To branch from a running session, fork it.

## Two kinds of branching — don't confuse them
- **Fork** ("New session" on a user message, or the sidebar's Fork): a new `.jsonl` file whose header `parentSession` names the source. It is its own row in its project group (`relation.kind: "fork"`); only subagents fold into a family, so copying a subagent session would carry its metadata and hide the copy in the parent's family. Rows sort by their last user/assistant message: a chat fork copies up to the parent of a user message, so it is older than its source and sorts below it (one made at the first message is header-only and sorts by its header time, first); a sidebar Fork of the newest branch ties with its source and sorts first (`[s, ...current]` on the client, newest-mtime-first on the server).
- **In-session branch** ("Edit from here" / BranchNavigator): `navigate_tree` within one file; entries share a `parentId`. Switching calls `/api/sessions/[id]/context?leafId=`.
- A claude session ([claude-sessions.md](claude-sessions.md)) has both: "New session" copies the active branch of claude's transcript up to the same fork point; "Edit from here" stages the same in-place edit, and its send resumes the same session truncated before the message (`--resume-session-at`), the replaced turns kept on another branch of claude's file that the history no longer shows. There is no branch switcher for it.

## Session files can be fully rewritten
`parentSession` in the header is **display metadata only**, so rewriting the whole file with `writeFileSync` is safe (pi does it in migrations); cascade-reparenting children on delete relies on this.

## ToolCall field normalization
Pi stores `{type:"toolCall", id, name, arguments}`; `ToolCallContent` uses `{toolCallId, toolName, input}`. `normalizeToolCalls()` (`lib/normalize.ts`) converts in both `session-reader.ts` (file load) and `handleAgentEvent` (`hooks/useAgentSession.ts`, streaming).

## Provider signatures in browser messages

Browser display copies omit content-block `thinkingSignature`, `textSignature`, and `thoughtSignature` through `lib/message-signatures.ts`. OpenAI reasoning signatures can contain `encrypted_content` needed for model continuation. `entryToUiMessage()` covers history and context pages; `projectTreeForResponse()` covers full navigation trees; `toClientAgentEvent()` covers assistant starts/ends and standalone tool calls. Reconnect snapshots pass through that event projection, while snapshot deduplication compares the original SDK message reference. The projection copies signed assistant messages and blocks, preserving visible content, display flags, and nested tool arguments. SDK state, persisted sessions, forks, and the raw entries embedded in HTML/JSONL exports retain their provider signatures for restoration and continuation.

## SSE reconnect on page refresh mid-stream
On mount `useAgentSession` loads the history, then `GET /api/sessions/[id]/state` (`loadSession(…, includeState)`): `state.isStreaming` or `state.isPromptRunning` resumes the run in the UI, and `thinkingLevel` / `isCompacting` sync from it. No reconnect is needed: the selected session's stream stays open whether or not it runs (`maintainEventsConnected()`, warm-session effect), and its `connected` event carries `isStreaming`.
- **A page hidden for `HIDDEN_PAGE_GRACE_MS` (30 s, `hooks/usePageHidden.ts`) lets go of the selected session's idle stream** (#1283): over HTTP/1.1 a browser has six connections per origin for all its tabs, and a few background tabs holding streams left Settings and message sync queued in the browser until one closed. A visible page always keeps its stream (it may send at any moment, and an idle session still streams extension statuses, widgets, names and runs an extension starts), and a quick tab switch closes nothing. A run, `!` command, compaction, open extension dialog or custom UI in the page keeps the stream without asking. Otherwise the grace ends with a lease request (next point; the renewal tick shares one in flight, `requestLease()`), and the stream closes only if `canReleaseHiddenEventStream()` (`lib/agent-event-connection.ts`) finds nothing under way in its reply: no run (`running`, the wrapper's `isRunning()`: a prompt, a queued one, a `!` command, a compaction), no extension dialog waiting for an answer (`awaitingInput`, `isAwaitingInput()`), and no unsettled subagent run under the session at any depth (`subagentsActive`, `hasUnsettledSubagentRun()`: a run counts until the turn its parent notification triggers starts, or the delivery is dropped or fails, past the moment it leaves the run map), since a subagent's end starts a turn in its parent (`notifyParent()`, `triggerTurn`). An error reply keeps the stream; either way it asks again each grace while hidden. The request is bounded (`SESSION_LEASE_TIMEOUT_MS`, 5 s): over HTTP/1.1 a request queued behind six open streams never leaves the browser, so no answer in time, like no network, releases. Waiting for it would keep every hidden tab's stream in exactly the starved pool the release exists for. A run that settles while hidden starts the grace again, which covers an extension's follow-up right after `prompt_done`. `eventStreamReleasedRef` keeps `shouldMaintain()` from reopening it. **A released page still hears the session:** each renewal reply that shows activity (`sessionLeaseShowsActivity()`: a run another tab, a device or an extension's timer started, a dialog) opens the stream again while the page stays hidden (`reattachEventStreamRef`), so the run's completion chime and browser notification, and an extension dialog's attention notification (replayed after `connected`), reach the hidden page as before the release; the reopen arms the grace again (`eventStreamReattachCount`), so the stream is let go a grace after the activity ends. The page's return reopens it at once. Both read the session with its state (`loadSession(…, includeState)`), applied as the mount does (`applyLoadedAgentState()`: a command, a `!` command or a compaction under way shows as such), and `connected` resumes a streaming run. Nothing is resent. What a released page can still miss: a run that starts and settles between two renewals (30 s; Chrome runs a page hidden for 5 minutes on a one-a-minute timer budget) has no chime or in-page notification there; web push still announces it when the browser is subscribed. Terminal streams are left alone: a shell without a listener is killed after `TERMINAL_RECONNECT_MS` (2 minutes).
- **The page, not its event stream, keeps the selected session alive.** It renews the session (`POST /api/agent/[id]/lease`) when it is selected, every 30 s and on return to the page, whether or not the stream is open, and each renewal resets the session's one idle countdown to the full `PI_WEB_IDLE_TIMEOUT_MS` (`AgentSessionWrapper.renewIdleTimer()`). pi-web keeps no lease records: a hidden page that let go of its stream keeps the wrapper, and an extension's timer in it, as warm as before, and a closed tab's session is reaped one idle timeout after its last renewal. A renewal never starts a wrapper (an unknown id answers 200 like an idle one), never moves Stop's forced deadline (`resetIdleTimer()` returns early for it), never revives a closing wrapper (`isAlive()` first) and is not a command (`lastCommand` unchanged); a wrapper from before a hot reload lacks the method and keeps its own timer. When the countdown ends, a run or an extension's liveness provider still re-arms it. Why one countdown: a 90 s lease record per page used to be a second clock that the idle timer consulted only when it fired, so a closed tab's session went at the first check after its lease lapsed, anywhere up to a full idle timeout later; now it goes at the last renewal plus the timeout, and the Debug panel's idle bar is the whole story. The reply (`running`, `awaitingInput`, `subagentsActive`) reads wrapper fields only. Nothing reads the renewal to judge the stream (a renewal that found no lease once meant a dead stream): the server sends `{ type: "heartbeat" }` every `AGENT_EVENT_HEARTBEAT_MS` (30 s) as a data event, which an SSE comment is not to `EventSource`, and `AgentEventConnection` drops a ready stream silent for `staleAfterMs` (75 s) and reconnects, catching a half-open connection or a proxy that dropped it. The heartbeat never reaches `onEvent`.

The resume reads only say that the run is active, not what it is waiting on. Right after `connected` the server replays each top-level tool call still running (`AgentSessionWrapper.activeToolEvents`, its latest start or update; an update after the 150 ms coalescing), and the mount's state read, which waits for the history read, often lands after that replay: setting `waiting_model` there showed "Waiting for model…" for the rest of a tool that may run for minutes without another event. So the state reads go through `runStatePhase()` (`lib/chat-phase-label.ts`), which keeps a `running_tools` phase the stream already reported: the mount's and a released page's return (`applyLoadedAgentState()`) and the stream-close re-check. `connected` does not: it sets `waiting_model` and lets the replay list the calls, since `tool_execution_start` / `_update` add to the listed tools and a call that ended while the stream was down (its end never reached the page) would stay, or show beside the replayed ones (`hooks/agent-phase.test.mjs` plays both orders and the reconnect). A listed call is stale only when the stream missed its end, and the reconnect that follows clears it at `connected`.

## Loading older history (`components/ChatWindow.tsx`)
The chat renders the last `visibleCount` rows, kept at least the loaded message count, with a sentinel above them while rows are hidden or the server has older entries (`hasEarlierMessages`, paged with `loadContext(…, before)`). Rows are not messages: a turn's answer and its thinking render as two, so loaded rows can outnumber the window; with nothing older on the server, reaching the sentinel widens the window (`getNextVisibleCount()`). The sentinel element is state (a callback ref), so the observer attaches whenever it appears, and the observer is renewed when the window grows: IntersectionObserver reports only changes, so a sentinel still in view would wait for the user to scroll away and back. A page lands, and `loadingOlderRef` clears, a moment before the next cursor renders; a report in between still holds the old cursor and prepended the same page twice. So `loadOlderPage()` keeps the cursor it asked for until another one renders, and the observer skips it; a page that failed, or a cursor a reload brings back, can be asked for again.
- The minimap numbers turns from the branch's first, not the loaded page's (#791). Each context page carries `turnsBefore`: the turn anchors on the branch above its oldest entry, counted with `isMessageGroupAnchor()` on the shape `entryToUiMessage()` would give (`countTurnsBefore()`, `lib/session-reader.ts`), so the client's turns and the server's count agree. The hook keeps one copy, the field on its context page beside the history cursor, and derives the `earlierTurnCount` it returns from it (also in the view cache: each read path takes it from the page that owns the cursor it applies, and a cached snapshot without `turnsBefore` reads as 0, so no offset and no stub); a loaded turn is numbered `turnsBefore + index + 1` and keeps that number as older pages land. While it is above 0 the rail shows a dotted stub above the first node and the preview's first row says how many turns are not loaded; clicking it scrolls the chat to the top, so the sentinel pages them in, and closes the preview like every other preview row (the preview opens and closes by click, pi#19, never by hover). At 0 neither the stub nor the row renders. Unloaded turns have no placeholder nodes yet.

## Compaction SSE events
`handleAgentEvent` accepts `compaction_start` / `compaction_end` and the older `auto_compaction_*` pair to keep `isCompacting` in sync. Manual compact is a blocking POST: `isCompacting` holds until it returns, the button meanwhile Stop compaction (`abort_compaction`). When a run ends, Compact (and the tools button) take the spot Stop held left of the sound toggle, so `ChatInput` ignores pointer clicks on them for `RUN_END_CLICK_GUARD_MS` (600 ms) after it: the second click of a double click on Stop otherwise started a compaction nobody confirmed (#1131). Keyboard activation (`detail` 0) and Stop compaction are never held back.
- **A successful compaction's end reads the context usage**: `compaction_end` (or `auto_compaction_end`) without `aborted` or `errorMessage` calls `refreshContextUsage()` beside its `loadSession()`, one read and no polling, for both harnesses (a claude session's `/compact` ends with the same event). A compaction changes the size the header's meter shows (pi: unknown, `? / <window>`, until a reply after it reports usage; claude: the size it reported it left), and a manual one is followed by no reply, so the meter kept the old number until the next reply, turn end, stream reconnect or page load. The event, not the compact POST's answer, is the trigger: it reaches every page showing the session, whoever compacted, and a stream that missed it reads the usage when it reconnects (`connected`). A stopped or failed compaction changes nothing and reads nothing. Tests: `hooks/context-usage-compaction.test.mjs`, `e2e/context-after-compact-368.mjs`.

## Prompts parked while compaction runs (`lib/rpc-manager.ts`)
pi's SDK refuses prompts during a manual compaction ("Cannot submit a prompt while compaction is in progress"; auto-compaction runs inside a run, where prompts queue as steer / follow-up anyway). The wrapper **parks** a refused prompt (`parkedDuringCompaction`) and flushes FIFO at `compaction_end`, whatever its outcome, as pi's TUI's `compactionQueuedMessages` (interactive-mode.js). The composer keeps taking text (`chat.compactingPlaceholder`), and the status line reads "Compacting… · N queued", for a manual compaction too.
- Parking happens on the SDK's refusal, before preflight, never before `inner.prompt()`: an extension command typed meanwhile still runs. The refusal handler runs a microtask after the refusal, so it can land after that compaction's end already flushed: it then flushes itself (`!inner.isCompacting`). A plain parked prompt is a steer, as the TUI parks Enter, so the rows, Recall and Stop keep arrival order. A parked prompt is acked `{ queued: true }` (`handleSend` drops its optimistic bubble; the queue rows show it) and keeps its admission's `pendingPromptCount` until it settles (`ParkedPrompt.settle`, the admission's own idempotent `finishPrompt`), so `isRunning()`, idle shutdown and the `reload` / `clone` refusals see it.
- The flush (`deliverParkedPrompt()`) goes through `acquirePromptAdmission()` one prompt at a time, each with a `streamingBehavior` (a plain one as `steer`): the first starts a run, the rest join it. An entry stays in `parkedDuringCompaction` (a queue row Recall and Stop take back) until its delivery holds admission; a delivery whose entry is gone skips it, and `delivering` keeps a second flush from scheduling it twice. Calling `inner.prompt()` for all at once let an `input` handler that took longer on the first prompt reorder them. The delivery that started the run sends `prompt_done` when it ends. A refused delivery settles its admission, reports `prompt_error` and stays a queue row for Recall or the next compaction end (the TUI's `restoreQueue()`); refused by another compaction, it parks again.
- `get_state.queuedMessages` and `queue_update` merge pi's queue with the parked ones; `clear_queue` (Recall) returns both, plus the parked prompts' `images`, which the client restores with the texts (`restoreRecalledPrompts()`, through `restoreSubmission`). Stop (`abort`) also recalls them before `inner.abort()` ends the compaction, and returns their texts for the composer: otherwise that compaction's end would send them and start a run right after Stop, as the TUI's abort restores queued messages to the editor. Stop compaction (`abort_compaction`) flushes them, as Esc during compaction does in the TUI. A recalled plain prompt gets `prompt_done` with `aborted`.
- `/compact` completes at once and runs the compaction detached (`handleCompact`, the button's path): `runBuiltinCommand` holds the composer's `<fieldset disabled>` until a builtin command resolves, and awaiting the blocking compact POST there disabled the input and Stop compaction for the whole compaction. A failed compaction puts `/compact <instructions>` back in the composer, where the awaited command used to leave it. Tests: `lib/rpc-manager-compaction-queue*.test.mjs`, `hooks/compact-command.test.mjs`.

## Process details start open without an answer (`ProcessDetailsGroup`, `components/ChatWindow.tsx`)
A grouped turn's Process details start collapsed only when the answer shown under them has text or an image (`collapsesProcessDetails()`, `lib/message-display.ts`). A turn that ends on an error or truncation notice alone, e.g. empty `stopReason: "error"` replies after text and a trailing tool call, still shows that notice but keeps them open: the earlier text is inside them (#906). The group is keyed on this decision, so a leaf switch that changes it resets the group; a search hit inside opens it (`reveal`).

## Turn duration (`lib/turn-duration.ts`)
A finished turn's length is the time from its anchor to the end of its last response or tool result (a response ends at its request `timestamp` plus the `durationMs` pi records since 1.1). It is wall-clock time, so a tool waiting on the user counts; only the wait between an answer and a run an extension started after it (`sendMessage` with `triggerTurn`, as pi's file-trigger example: its custom message is no anchor, so the run stays in the turn) is left out. It shows on the Process details line, or under the answer when the turn has no process details; a turn whose last response has no `durationMs` (an older session) shows nothing. The Process details line stays one line: the button's `maxWidth` lets its span's ellipsis cut the line at the column; without it a phone (320 to 375 px) ran the longer line past the gutter and clipped it at the screen's edge. A running turn shows no time, as in pi's TUI: a live timer would compare the browser's clock with pi's.
Both ends of the subtraction must be pi's times, and the browser's clock can differ (a phone on the LAN). The bubble a send shows at once is stamped in the browser and stays until the reload after the run (the delivered user message replaces it only when the two differ, `userMessageKey()`; an extension command's `/name` has none), so a turn is timed only when its anchor has an entry id (`entryIds`), which only messages read from the session file carry: from a run's end until that reload (`loadSession` at `prompt_done` / `agent_settled`), the turn shows no time rather than one taken across two clocks.

## A reply's usage line (`formatUsage()`, `components/MessageView.tsx`)
The line under a response is pi's TUI footer for that one response: `↑1.2k ↓567 R8.9k W12 $0.0036`, zero counts left out, counts through `formatNoticeTokens()` (the footer's `formatTokens()`, pinned by `lib/transcript-notices.test.mjs`), then the turn's time after ` · `. The arrows and letters are the TUI's, so there is nothing to translate; no click-through details or output speed: the TUI has neither.

## Compaction summary card (`CompactionMessageView`, `components/MessageView.tsx`)
Collapsed by default, as pi's TUI `CompactionSummaryMessageComponent` (#1026): the header, "Conversation compacted" and pi's "Compacted from N tokens" (`details.tokensBefore`, set by the reader). The title is the toggle (a button with `aria-expanded`); the description, the summary Markdown and the file lists mount only when expanded. Session search indexes user and assistant `message` entries first (`lib/session-search.ts`), then falls back to the displayed catalogue title (`name`, including manual/auto-generated `session_info`, else `firstMessage`) only when no message matched. A message hit keeps its entry navigation even if the title also matches; a title hit has no entry to reveal. No hit lands inside a summary and the card needs no `reveal` like Process details.

## Streaming token rate
The streaming reply's `t/s` counts estimated tokens from when its first ones showed. That start lives in `lib/stream-token-rate.ts`, keyed by the reply (provider, model and request `timestamp`), not in `MessageView`: switching sessions remounts the chat, and a start taken at the remount divided every token streamed so far by a fraction of a second. A reply joined with no record (a reload) counts only the tokens that follow.

## Auto-retry banner
`auto_retry_start` shows "Retrying (n/max)…" above the composer for the backoff wait. The retried run's `agent_start` clears it, as pi's TUI replaces its retry indicator at that run's `turn_start`: pi emits a successful `auto_retry_end` only with the retry's first complete assistant message, minutes into a long reply. `auto_retry_end`, `agent_end` and settling clear it too.

## Tool execution events on the SSE stream
- Calls made through `ctx.executeTool()` (a codemode script's) emit `tool_execution_*` with `parentToolCallId` and ids `<parent>/<n>`. `toClientAgentEvent()` sends their start and end slim and drops their updates; test for nesting *before* rebuilding an update, which keeps only `toolCallId`, `toolName` and `partialResult` (a nested update would reach the browser as a top-level tool). `handleAgentEvent` keeps them out of the running-tools phase; `AgentSessionWrapper` never records them for replay, a parent's end forgets every id under `<parent>/`, and `agent_end` clears the replay set.
- `tool_execution_end` never carries `result` (up to 1 MiB of bash output): the browser renders the tool result message that follows. `entry_appended` is omitted. A codemode update's `details.calls` keeps the newest 200, `omittedCalls` counting the rest.
- `tool_execution_end` never carries `result` (up to 1 MiB of bash output): the browser renders the tool result message that follows. A non-assistant `message_start` (that tool result, a delivered user message) goes as `{ role }` only: the loop sends it right before its `message_end`, and the browser builds only an assistant reply from a start, so an image read's base64 went out twice. `entry_appended` is omitted. A codemode update's `details.calls` keeps the newest 200, `omittedCalls` counting the rest.
- `createAgentEventStream()` coalesces `tool_execution_update` per `toolCallId` (latest wins, `TOOL_UPDATE_COALESCE_MS`) and discards that id's pending update before forwarding its `tool_execution_end` (`agent_end` discards all), or the tool would read as running again. Everything else goes at once, so a pending update can arrive after unrelated events.
- A codemode card shows the script in the box any tool's input uses (plain text) and its `details.calls` as rows, never as cards: those calls never reach the model as tool calls. `handleAgentEvent` keeps a running script's progress snapshot in `activeToolResults`, as for shell output, so calls list while they run.
- A tool card's time is the result's `durationMs` (pi 1.1: `execute()` measured with a monotonic clock, saved in the session file), formatted as the CLI's "Took" (`formatToolDuration()`), and none under 100 ms. An older result falls back to its timestamp minus the assistant message's, which is when that message's request **started**, so it counts the model's generation too. A thinking block's time likewise prefers the assistant message's own `durationMs`.
- A patch takes the columns the viewport has. `SplitFilesView()` reads `useIsMobile()` and gives `PatchDiffFiles` a `layout`: two code columns side by side, or one. Two columns are two code columns, and a phone does not have two — at 390px each half is about 150px, so every line of a real edit wrapped inside its own half and the reader compared two broken columns from memory. The one-column layout is the file viewer's diff (`components/FileViewer.tsx`), which has always been one column, and both now read off the same parsed rows: `unifiedDiffLines()` (`lib/patch.ts`) turns a file's paired rows into one column — each pair as its removed line above the added line beside it, so a block of several changed lines interleaves pair by pair rather than listing every removed line first, as the file viewer always drew it — so the two views cannot drift, and `FileViewer`'s own flattening is that call. A gap row between hunks passes through, so both layouts and the file viewer keep their "⋯ N unchanged lines" markers. One gutter, because a second costs the width the code needed: a removed line keeps its old number and every other line the new one, the rule `FileViewer`'s gutter already used. Hunk headers stay dropped as in the two-column view, and context lines print once rather than twice, which `MessageView.test.mjs` counts. A patch with several files names each section by the file's own path (its new path, the one that survives) instead of the two labels `Before` / `After`, which over one column would read as two columns. The layout is taken once, in the dispatcher both the `apply_patch` card and a result's patch render through, so a phone never gets one view of each; `MessageView.test.mjs` pins that both call sites go through it.
- A tool call whose arguments are all single values (string, number, boolean, null) shows them as rows instead of the input JSON (`lib/tool-fields.ts`, `ToolFieldRows` in `components/MessageView.tsx`): one row per argument in the order the tool received them, a value with newlines of its own in a scrollable block (a subagent's `prompt`). The rule is structural, not a list of tools, and all or nothing: one object or array value (`edit`'s `edits[]`, an MCP argument holding a list) keeps the whole JSON, since a row that drops a subtree hides an argument. A card with a view of its own keeps it: a write of just a path and its text shows the file text (the header has the path), codemode its script and calls, an applied patch its split diff; a call with no arguments keeps the raw body. An edit card with a result diff (`details.diff` / `details.patch`) draws the diff, and its input follows the same rule above it: a flat input (claude's `Edit`: `file_path`, `old_string`, `new_string`, `replace_all`) shows its rows over the diff, while a nested one (pi's `edits[]`) is replaced by the diff, which says the same thing; with no diff, any input shows. Input still streaming goes through pi's `parseStreamingJson()` (`@earendil-works/pi-ai/utils/json-parse`), the partial arguments pi's TUI hands `renderCall` while a call streams, so a multi-line `bash` command shows its lines before `toolcall_end` instead of JSON's `\n` escapes; until the arrived part parses to a flat record (nothing yet, `edit`'s `edits[]` begun) the card keeps the raw text, and a write or codemode call takes its own view once the call ends. The demo has no pi-ai and calls `partial-json`, the parser `parseStreamingJson()` wraps.
- A tool card's header shows the call's `command`, `path` or `file_path`; a call naming none of them takes the one file its result's `details.patch` changed (`singlePatchPath()`), before falling back to its first argument. Anchor-addressed edits (pi-hashline-edit-pro's `insert` / `replace`, #1460) carry no path: their TUI renderer resolves the anchor in process, which pi-web cannot, and a single-file patch draws no file header, so the name was shown nowhere. A patch over several files keeps the first argument.

## Custom messages collapse from their header (`CustomMessageView`, `components/MessageView.tsx`)
A displayed custom message starts expanded: pi's TUI draws its default custom message in full and has no per-message toggle (only a `registerMessageRenderer` renderer gets the global Ctrl+O `expanded` flag, and pi-web runs no TUI renderers). The header is a button (`aria-expanded`, the tool cards' chevron as its **last** element, the timestamp just before it) that folds the card to that one row, with the text's start on it as a one-line preview, like a tool card's header; the body, the footer (Copy, details) and the details mount only when expanded. The footer button is about `details` only. Session search never lands in a custom message (it matches titles and user/assistant entries only), so the card needs no `reveal`.

The body keeps the text's layout, as pi's TUI does (`MarkdownBody`'s `keepTextLayout`, `remarkTextLayout()` in `lib/markdown.ts`), since an extension may lay a status out for a terminal: a box, aligned bars, indented rows. Markdown still renders (pi-tui's `Markdown` draws these messages too), with the user message's rules on top: every line ending is a line break and raw HTML shows as text. The parser drops a paragraph line's indent from the text, so `restoreLineIndents()` takes it back from the source, counting line breaks from the paragraph's first line rather than reading text positions (a GFM autolink's split leaves the pieces without one). Only top-level paragraphs: in a list or a quote the line's whitespace belongs to the container, so an indent or a run of spaces there is not kept, unlike the TUI. The CSS keeps the rest: monospace, `white-space: pre-wrap` on paragraphs (not on `li`, whose block-separating newlines would show as lines) and a blank line's gap between paragraphs. `next/font`'s Noto Sans Mono has Latin and Cyrillic only, so arrows, box drawing and blocks would fall back to glyphs 12 to 17px wide in a 7.8px column; the `Terminal Drawing` faces in `app/globals.css` take those ranges from a system mono font (`local()`, `size-adjust` to the 0.6em column). CJK stays its font's 1em, not the TUI's two columns.

## Transcript system messages, usage entries and context edits (pi >= 0.86)
- A new session's first request persists a `message` entry with `role: "system"` (prompt sections, tool declarations); prompt or tool changes append more, announced with `message_start` / `message_end`. They are provider input, never conversation: `toClientAgentEvent()` drops them (they carry every tool schema), `handleAgentEvent` skips strays, `entryToUiMessage()` returns null, and `BranchNavigator` / `lib/project-tree.ts` never label or preview a branch with one. They still count toward `messageCount` and `totalMessages`, as in the SDK.
- `usage` entries (`kind: "cache_warm"`): billed prompt-cache warming outside model context; `computeSessionStats()` adds them like compaction usage so counters match the TUI's `/session`.
- `context_edit` entries omit or replace an earlier entry's model context without changing raw history; the UI ignores them. A retain-none compaction stores its own id in `firstKeptEntryId`.
- `listSessionsIncremental()` must keep `SessionManager.listAll()`'s order: newest mtime first, then reverse filename, stable for equal activity time.

## Cache and cost notices (`showCacheMissNotices`, #1265)
- pi's own setting (project `.pi/settings.json` over the global one, off by default), read on every history read and every assistant `message_end` by `readShowCacheMissNotices()`: a plain `JSON.parse` of each file cached by inode, size and mtime, never `SettingsManager.create()`, which locks each file (a `settings.json.lock` directory in the project) and busy-waits up to ~200 ms when another writer holds it; Settings › General's switch (`/api/cache-miss-notices`) writes only the global key, removing it when off. The four notices are the TUI's (`interactive-mode.js`): a significant cache miss (from 20k re-billed tokens or $0.10; "after model switch", "after Nm idle" past the 5-minute TTL), cache warming (`usage` entries, `kind: "cache_warm"`), a compaction's or branch summary's billed usage, and Anthropic dropping more thinking blocks than for the response before (`anthropic_input_transformations` diagnostics). Unlike the TUI, the thinking drop also shows in history: a reload is routine here.
- Cache misses are never persisted, so everything is derived from the entries: `collectTranscriptNotices()` (`lib/transcript-notices-server.ts`) keys them by the entry whose chat message they follow, and both history routes hang them on a copy of that message (`transcriptNotices`, `attachTranscriptNotices()`); a reload, a reconnect or an older page gives the same lines, never twice. `scanCacheMisses()` ports the SDK's unexported `core/cache-stats.js` (every entry in file order, as `getEntries()` gives it); `lib/transcript-notices.test.mjs` compares it with the installed SDK's module and `formatTokens()`, so an upgrade that changes either fails there. Cache warming follows the nearest ancestor the chat shows (a tool result is drawn inside its call), so it lands on the same message on any page; it counts only when the usage entry is on the shown leaf's branch, since that ancestor is shared with every branch forked below it.
- A total miss (`cacheRead` 0) prices the cache read from what the session's own replies paid for one with that model (`withSessionPrices()`), then an open wrapper's `modelRuntime`, else at 0 like the SDK. The live reply and every later read price it alike. Never the shared extension-loaded runtime: building or refreshing it runs extensions with no deadline, and a history read would wait on it. The switch's state is part of `snapshotRevision`'s source id, or turning it on would keep the cached messages without notices.
- Live, the wrapper adds `transcriptNotices` beside an assistant `message_end` (never on the message: pi writes that object to the file), skipping the message if pi already appended it; `useAgentSession` hangs them on the message it appends. Cache warming and summary costs arrive with the reload after `agent_end` or the compaction; an idle-mode warming with no run shows on the next read.
- `ChatWindow` draws each message's notices under it (`TranscriptNoticeLines`; amber, cache warming dim) from the stored message, not a turn view's copy, so the final answer's go under the answer and not again inside Process details. A step that shows nothing else keeps its notice lines, not counted as a message. Folded, Process details adds the cache misses inside it to its header (`summarizeCacheMisses()`); open, the header drops that part and each line shows under its step. A compaction's cost is a line in its card.

## Turn grouping and custom messages in the chat (`ChatWindow`, `lib/message-display.ts`)
- A turn runs from one anchor (`isMessageGroupAnchor()`) to the next; its last assistant answer shows, everything before it folds into Process details. Anchors: user messages, the compaction summary, and background subagent completions, which arrive as a follow-up that triggers a new run after the answer: pi-web's `pi-web:subagent-notification` and `@tintinweb/pi-subagents`' bare `subagent-notification` (#891, #1075). Without the anchor, the reply to the notification becomes the turn's answer and the real one folds away.
- A custom message without `display` (`display: false` keeps it for the model alone) stays in `messages` and `entryIds`, from the reader and from `message_end`, but renders nothing, as in pi's TUI: `isHiddenCustomMessage()` makes `renderMessage()` return null, keeps it out of the Process details count, and it never anchors a turn. An extension may send one on every `session_start`, i.e. on each idle restart (#1043).

## Running state polling + reconciliation
- The sidebar polls `/api/agent/running` every 2.5 s while the tab is visible; the session-list response is the initial fallback.
- The same poll's `recentSessionWrites` refreshes the open chat from disk when the selected session's watcher generation rises. A selected session already in the ring is baselined at that generation, so selecting it reads nothing; one absent from the ring is baselined at 0, so its first write is a rise and reloads (a first sighting no longer gets swallowed). While a run, `!` command or compaction is active the SSE stream stays authoritative: a rise reloads only when no completed message has arrived on the stream since the previous rise, which is the half-dead-stream case and costs no read on a healthy one. These reads are background reads (`loadSession(..., { quiet: true })`): a failure keeps the conversation and composer instead of setting the page `error`. A read carries the run id it started in and is dropped if the next run has begun (the idle branch included, so a read in flight when the user sends cannot put its pre-send snapshot back). Reads are also ordered against each other and against the stream: a response that started before the last applied read is dropped (a dropped read that raised the loading screen ends it at that moment, while the newer read's view is already shown, not after its own `/state` round trip; it clears only the loading it raised itself, never a newer read's), and when the stream delivered completed messages after the read was issued the snapshot keeps the view's live tail after their shared messages (`keepStreamedMessages()`), so a held answer generated before a reply cannot remove the reply the stream already rendered. A read that applies mid-run shows messages the stream has not delivered yet, and the resumed stream still buffers their `message_end` events: the read records only the tail after the view's anchor that the view did not already hold live (a still-pending optimistic prompt stays in it for its own event), and records none when a sliding window no longer holds the anchor; it consumes a buffered event matching the head of that tail (`sameMessage()`, so the prompt cannot land after the reply) and passes over an unmatched head the stream never reports with its own `message_end` (a `custom` compaction divider or extension boundary draft, a `bashExecution` entry), so such an entry cannot block the tail for the whole run and let a stalled stream's buffered prompt and reply render twice; a matching custom head is still consumed, because its own `message_end` comes first in file order. It clears the optimistic prompt's key when the snapshot holds that prompt and ends a partial streaming bubble when the snapshot holds the message it streams. A new run or a new connection discards that tail, since neither replays completed messages.
- The same poll carries `awaitingSessionIds`: the running sessions with an unanswered blocking `extension_ui_request` (`isBlockingExtensionUiRequest()`, `lib/extension-ui-queue.ts` — select / confirm / input / editor, or a custom overlay that has not closed), as `AgentSessionWrapper.isAwaitingInput()` reads `pendingUiRequests`. A family row with such a session shows a static amber marker in place of the running spinner (`AwaitingInputIndicator`, `components/SessionSidebar.tsx`), so running, awaiting and unread stay distinguishable. The wrapper checks `isRunning()` first, so a custom overlay that outlives its turn is not a parked run. `/api/agent/running` is the only source: a background session's own SSE stream has no listener, which is why the browser notification (`#431`'s `handleAttentionNeeded`) cannot cover this.
- The list's `firstMessage` is a row title, not the prompt: `catalogFirstMessage()` sends a skill expansion as its `/skill:` command and cuts the rest to 500 code units (persisted rows and live ones from `getRpcSessionInfos()`). Whole first messages made the list 3.2 MB (one row 325 KB), fetched again by every tab after each run. Fork naming reads the file itself and is unaffected.
- A run's end costs one list rebuild: the wrapper invalidates the list at `agent_end`, before the event reaches any browser, so nothing after it forces one. The tab showing the session reloads through `refreshKey` (`handleAgentEnd`; the reload's row reaches the selected session through `handleSessionsChange` → `mergeCatalogRow()`, which also clears a fresh session's `transient`), the others through the version poll and the background-completion reload, all plain `loadSessions()`. A `force=1` there rescanned again and bumped the version, so each tab not showing the session made every other tab reload once more (5 list requests and 3 rebuilds per run with two tabs). Only the first page load's details hydration still forces, to pick up what the pi CLI appended meanwhile.
- A name set through `AgentSession.setSessionName()` invalidates the list as well, on the wrapper's `session_info_changed`: an extension's title (pi-autoname, pi's `examples/extensions/session-name.ts`) lands after `agent_end` or with no run at all, and the sidebar kept the old name until something else bumped the version (#1237). The open chat's name (`selectedSession.name`) follows through the version poll and `handleSessionsChange`; the state route carries none. The sidebar's rename (`PATCH /api/sessions/[id]`) goes the same way whenever a wrapper holds the session, subagents included (`renameRpcSession()`, after a start in flight but, like the `set_session_name` command, never waiting for session_start, which an unanswered dialog can hold forever; a closing wrapper is waited out and the file renamed after it, the write running synchronously after the check): appended to the file from outside, the `session_info` was a dead branch off the live leaf, extensions never got `session_info_changed` and `getSessionName()` stayed old (#1388). Only a session no wrapper holds is renamed on disk.
- `invalidateSessionListCache()` bumps the generation but **keeps** the previous scan, fresh only while its generation matches. Callers needing only metadata (search hits to sidebar rows) pass `listAllSessions({ allowStale: true })` to read it while it rebuilds in the background, accepting that a seconds-old session is missing.
- `useAgentSession` treats per-session SSE as primary and opens it before each prompt. `prompt_done` completes the UI stage and notification at once (none for a stopped run: `prompt_done.aborted`, see **Completion sound** in [client-platform.md](client-platform.md)), but the stream stays open for the next prompt: the selected session's while selected, unless its page stays hidden (`scheduleEventStreamClose()` skips it; see the hidden-page release above), any other's for a 30-second grace window. `agent_start` cancels the close timer; `agent_settled` finishes extension-injected runs that have no wrapper-level `prompt_done` and starts a fresh grace window. Never close on the first `agent_end`: retries, compaction and extension-queued messages continue the same logical prompt.
- While a run is active, `useAgentSession` polls `GET /api/agent/[id]` and reconciles on `visibilitychange` / `online`, for terminal events missed by background tabs or half-open connections. Busy replies also refresh context usage; each completed assistant message requests an immediate usage read between model calls, and so does each `connected`: opening the stream is what resumes an idle-reaped wrapper, so the mount's state read can find no runtime and no usage. Usage reads from mount, stream connect, message completion, reconciliation and `agent_end` share a monotonic request id and check the current session/run and mounted hook. A reply applies only when its id is newer than the last applied one, so a delayed read cannot overwrite newer usage, and a newer read that fails does not discard an older one still in flight. Each mount marks the reads started before it as stale. A read's `extensionWidgets` section is ordered against the stream per key instead: each `setWidget` event records the sequence it arrived at, so the mount/reattach read (`loadSession(…, includeState)`), reconciliation's idle reply and `agent_end`'s read capture that sequence before their request and, for every key touched after it, keep the page's state (present or removed), so the stream wins over an older read per key exactly as the usage request id makes it win for usage (#153); every other key takes the snapshot's entry, including a removal the stream never touched, and the reply's other fields still apply (#169). The mount's widget section is decided once in `loadSession`; `applyLoadedAgentState()` never applies it again. `extensionStatuses` (`setStatus`) shares that per-key ordering at the mount/reattach read, reconciliation's idle reply and `agent_end`'s read: a status event that arrived after the read was issued keeps its live value, and every other key takes the snapshot's, so the latent race the widget work (#169) closed for widgets is closed for statuses too. These status reads and the settle polls go through `agentStatusUrl()` (`?systemPrompt=0`): the system prompt is nearly all of the state (context files, skills; hundreds of KB in a large project), and a usage read after every model call re-downloaded it (#1302). Only `agent_end`'s read, the mount's `/api/sessions/[id]/state` and reconciliation's finish (one extra read) still fetch it. The same reads carry the wrapper's active time: `get_state` computes `computeSessionTotalActiveMs()` over its live entries on every read, since the SDK's `getSessionStats()` carries no active time and the Session Info panel otherwise kept a snapshot's value while a run appended entries behind it, for as long as the run lasted (#1334). The scan is cached per `SessionManager` until its entry count or last entry changes (`computeLiveSessionTotalActiveMs()`, as `POST /api/sessions/stats` caches its summaries): a status read every 600 ms while a prompt settles would otherwise re-parse the whole transcript. The panel takes the larger of that reading and the snapshot's, since both are the same monotone sum: the live state leads while a run appends entries behind a snapshot the panel still holds, and the snapshot leads after a compaction or a reload, which install a newer one without reading the state.
- The composer clears before the prompt request, so a failed send gives its text and images back through `restoreSubmission` (merged in front of what was typed since, into the sending session's draft; images within the attachment limits), and nothing is ever sent again (#1432). Only `prompt_rejected` + `accepted: false` says the prompt was not sent: the text comes back at once with the error. A network error or a proxy's non-JSON answer after dispatch may hide an accepted prompt:
  - A steer or follow-up has no bubble, so its text comes back at once, with `chat.sendUnconfirmed` (could not confirm; check the conversation before sending again).
  - A normal send keeps its bubble (copyable) and the run state, and records the send (`unconfirmedSendRef`). Its text comes back, with `chat.sendNotReceived`, only once the server is idle (`finishPromptWithoutStream()`, reached from the settle poll or, after its 20 s, from `reconcileAgentState()` on the 15 s tick, `online` or the page's return) and a session read started after that (`lastReadContextRef`) does not show the prompt. Arrival takes positive proof, never just a context that changed: one of the run's events (`agent_start`, `prompt_done`, `queue_update`, a user `message_end` while its bubble waits), before or after the request failed (`markPromptLanded()`), or in the read more user messages with the bubble's `userMessageKey()` after the view's last saved entry at the send than the view already had there (the stream's unsaved run messages count, so the same text sent before is not this prompt). Any other outcome gives the text back: `chat.sendNotReceived` only when the read ends on that entry and the prompt is no slash command; otherwise `chat.sendUnconfirmed`: the read moved on (a reply the view had not saved, more than its 50-entry window), it failed, or a command or template need not become that user message. With the text back, the bubble leaves the view and the session's cached view whenever that read succeeded (`dropUnconfirmedBubble()`): a read of a file the prompt never changed has the same `snapshotRevision`, so `loadSession()` keeps the view's messages, bubble included, and the notice would contradict the transcript. A failed read keeps it. A baseline that is stale (the view lagging after a navigation) only makes it unconfirmed. Known misses: a prompt an extension's `input` handler rewrote, sent while the stream was down too, comes back as unconfirmed though it arrived; a stray event of another client's run reads as arrived.
  - Unmounting with the send unsettled (a session switch) gives the text back unless one of the run's events arrived first. The stream closes with the hook and nothing settles it later, so a prompt that did arrive comes back too, without a notice (the draft is all the next view shows): the price of losing nothing. It goes to the session's draft, or for a fresh composer to its cwd's parked draft (`parkedNewSessionDraftKey()`), which the next fresh composer there takes back. The bubble leaves the cached view (the release runs after the unmount's snapshot save, and again for a request that fails after it), so coming back to an unchanged file shows no bubble beside the restored text. Not to its new session's id through `promoteNewSession()`: a session the prompt never reached is never listed (`getRpcSessionInfos()` leaves out an idle unsaved session without a user message), so a draft under its id could not be reached.
- A fresh composer's first send outlives the composer: switching sessions while it runs unmounts the hook and closes its stream, but `handleSend` still posts the prompt (skipping the stream wait once unmounted) and promotes the session, so it runs and gets its sidebar row. Before #1146 a switch during the `connected` handshake rejected the wait, and `restoreSubmission` drops an abandoned composer's draft, so the text was lost.
- Prompt runs carry a monotonic run id; late SSE or reconciliation answers from an old run must be ignored, or they resurrect stale streaming bubbles.
- Every SSE (re)connection is gated on `sessionHookMountedRef`. Under React Strict Mode (`next dev`) the mount-only effect's cleanup clears it and restores it only after the warm-session effect re-runs, so that effect must re-assert it before `maintainEventsConnected()`, or a dev tab never opens its stream.

## Debug panel (`components/DebugPanel.tsx`, `GET /api/agent/debug`)
- A bug icon in the top bar, left of the session stats (on a phone up to 480px, in the "more" overlay after the chat's actions), opens a top panel with the page's connections, the server's state for the chat shown, and the sessions the server holds something for. **Opening it only reads.** The toggle is `toggleTopPanel("debug")` and nothing else: never `handleSystemInfoToggle` (it creates a fresh composer's session and POSTs `get_state`/`get_tools`), `/session`, `sendAgentCommand`, the lease route or an EventSource, because `POST /api/agent/[id]` starts a reaped wrapper, every command but `get_state` resets the idle timer, a lease POST resets it too and opening the events stream resumes the wrapper. The panel stays open across a session or project switch (it follows the chat shown) and closes when no chat shows.
- Server: `buildDebugSnapshot()` (`lib/debug-snapshot.ts`) is synchronous and reads fields: `__piSessions` directly (closing wrappers included; `getRegistry()` would install process handlers), each wrapper's `getDebugSnapshot()`, the per-id lifecycle map (`Symbol.for("pi-web:session-lifecycle")`: starts, last start and close; 1000 ids, LRU, ids with a live wrapper never trimmed), the event-stream info map beside the closer Set (`Symbol.for("pi-web.agentEventStreamInfos")`), subagent runs and pending parent notifications, the MCP host, `globalThis.__piWebTerminals` (not `registry()`) and `lib/file-watch-registry.ts`. Never `send()`: `get_state` waits for extension binding with no deadline and builds the system prompt. Each source sits in its own try/catch, so one stale object (a wrapper from before a hot reload lacks the new methods) or a throwing getter never fails the answer. The answer is states, counts and times: no prompt, message, session file, task, config value or env. The one exception is who opened each event stream, for the SSE badges' titles (`lib/stream-client.ts`, read once in the events route): the request's `x-forwarded-for` first entry (Next fills it with the socket's address only when the request has none, so behind a proxy it is the proxy's word, and a client can send its own) and a "Chrome · macOS" label read from the user agent, which itself is never kept. Both belong to a page, not a stream, so they are shown once per page: the server column lists the connected pages under its head (`PageList`: browser and system marks, `CLIENT_GLYPHS`, strokes for the browsers and filled Simple Icons (CC0) shapes for Windows and the apple, which outlines blurred at 12px, macOS and iOS sharing the apple; the label in words; the address; "this page" or the page's short id; its SSE count; the server's SSE total in the head; this page first on the current row's tint). Every SSE response counts there, as each takes a connection of the browser's pool: the agent's streams, terminals' (`/api/terminal/[id]/events`) and file watches' (`?type=watch`). Those two carry the page id too (`?holder=`, `pageId()` in `lib/page-debug.ts`) and register in `lib/page-stream-registry.ts` for the life of the stream; the row's title splits its count by kind. The head's total is the counters' (agent streams, terminal listeners, file watches), so it can exceed the rows' sum by streams opened without a page id before a reload. The session rows' SSE badges stay plain words, their titles naming page, label and address; marks in every badge made each badge wide and still too small to read. Labels to tell pages apart, never an identity: nothing decides access by them (`lib/auth-throttle.ts` says why there is no per-IP key). By default pi-web listens on 127.0.0.1, so every page reads 127.0.0.1 or ::1 until a proxy or another bind address is in front. Extension liveness providers are counted in the summaries without being asked; only the selected session's are asked `isActive()`, quietly.
- The bookkeeping behind it is assignments, guarded where a throw would break a wrapper: the lifecycle start is written before `registry.set` (never between it and `start()`), the close in `finishDispose()` before `resolveDisposed()` (a replacement swaps the old wrapper's `onDestroy` for a no-op). `idleDeadlineAt` is the next idle *check*, not a close: a run or a provider re-arms a full timeout there unless Stop forced it (`forcedByStop`), and each lease renewal moves it a full timeout on. There are no server-side leases to list: `sessions` holds the ids with a wrapper or an event stream. `lastCommand` leaves out `get_state`, the chat's own status read. `pendingPrompts` counts prompt calls beyond the running one. A `__new__…`/`__recreate__…` start key maps to its real id once registered, so a session switching to a deferred model is not counted both alive and starting.
- Streams carry the page id: the events URL has `?holder=<page id>` (`pageId()`; `peekPageId()` reads it without creating it, the client snapshot's `pageId`, which marks this page's streams), validated by `isValidLivenessHolder()` and used only as a label. The lease request carries none: it only resets the idle countdown.
- Client: `AgentEventConnection.snapshot()` and refs in `useAgentSession` (lease outcomes recorded in `requestLease()`'s finally inside their own try, so a summarising bug can never turn an error reply into "unanswered", which releases a hidden page's stream; release, reattach and grace due times) are read by a reader the chat registers through `onDebugSnapshotReaderChange`, which AppShell keeps in a ref. None of it is React state or an effect dep: ChatWindow is not memoized, and the release and lease effects re-arm on their deps. The mount cleanup block stays textually unchanged (`AppShell.workspace-memory.test.mjs` runs it in a sandbox). `lib/page-debug.ts` tracks the page's EventSources through extra `open`/`error` listeners, held by `WeakRef` so a closed viewer or terminal is collectable at once; it also records visibility, the sidebar running poll's outcomes and the navigation entry's `nextHopProtocol` (never Resource Timing: open streams are not in it, and its buffer is global). Client counters live one chat mount; under Strict Mode (`next dev`) a mount reads two opens and a "deselected" close.
- The panel owns its clocks, never AppShell state: a 1 s tick reads the client, a 2 s poll asks the server while the panel is open and the page visible, one request at a time, aborted after 5 s by its own timer (no `AbortSignal.any`: Safari 16.2). No answer in 5 s reads as a starved HTTP/1.1 pool (#1283). Countdowns run on the server's `now` plus the local time since the reply. It polls the chat's working id (a fresh composer's ensure_session wrapper too), drops replies for another id and writes nothing once closed. A class error boundary keeps a panel error from unmounting ChatWindow, which would close the stream and stop the lease renewal.
- Machine load (a later change made the panel its only mount and moved it into the grid; another made it the grid's narrow rightmost column): `MachineLoadSection` is the last area of `.debug-cols` in DOM order, after the page, server and sessions columns — the narrow rightmost column on a wide panel, the right column under the sessions in the middle, the last block of the phone stack (see Layout). The Session-info popover no longer carries it. It keeps its own fixed 2 s poll of `GET /api/machine-load` while the panel is open and the page visible, unmounted (0 requests) when the panel closes. It adds no debug-snapshot or Copy JSON field and no POST, SSE or lease. See [machine-load.md](machine-load.md).
- Escape: the panel listens on `document` and takes an Escape no nearer handler took (`defaultPrevented`, `cancelBubble`, IME, an `aria-modal` dialog), so the window shortcut does not stop the run being watched; with focus inside the panel, focus returns to the toggle (`focusIfLost`). ## Manual fetch of the newest data (`manualFetch` in `hooks/useAgentSession.ts`, `lib/manual-fetch.ts`, `components/ChatWindow.tsx`)
- A saved session's chat offers one manual "fetch latest", the user's fallback when a weak network leaves the event stream half-dead and the newest reply never shows. Two entry points start the same action, both the chat pane's own (each pane of a split view fetches for itself; a later change removed the top toolbar's ↻ and its `manualFetchKey` plumbing, with no toolbar replacement): the chat's floating button (`.chat-scroll-to-bottom`, one element with two forms by scroll position) — at the list's tail it is ↻ (`chat.manualFetch`, starts the fetch, the list stays at the bottom), scrolled up it is ↓ (`chat.scrollToLatest`, scrolls to the latest and fetches nothing; at the bottom it turns back into ↻) —, and on a touch screen the bottom pull-up of the message list (see [client-platform.md](client-platform.md#bottom-pull-up-starts-the-manual-fetch-componentschatwindowtsx)). There is no fetch entry point while scrolled up (the pull-up arms only at the bottom too), so the original "a fetch while reading earlier content keeps it in place" path has no trigger any more, as the owner accepted; `e2e/manual-fetch.mjs` S20 now pins that scrolled up the button is ↓ and fetches nothing. A new unsaved session offers neither (`manualFetchAvailable`: a session id and not `isNew`; its floating button keeps only the ↓ form and is hidden at the tail); any run state, compaction or unconfirmed send does not hide it, and the action never touches send confirmation, the optimistic bubble or queueing.
- One trigger is at most one forced read, one run-state read and one stream reconnect. The read is `loadSession(…, { force: true, quiet: true, preserveHistory: true, signal })`, called directly: `refreshFromDisk()`'s covered branch skips the read once the stream delivered a completed message, which is exactly what a half-dead stream fakes. The run-state read is the reconciliation's `agentStatusUrl()` read, made only while the view shows a run at the trigger (`reconcileAgentState(sid, manual)`), and it comes **before** the forced read: the status first, then the one forced read (`readSeqBefore` taken just before it). A stale run is ended through `finishPromptWithoutStream(…, { readSeqBefore })` only when the status reported idle (not busy), the forced read succeeded and the run id is unchanged: that later read settles it (an unconfirmed send included), as the passive reconcile settles on a read made after idle was seen, so a run ending between the two reads is in the read and a prompt that landed is never judged "not received". No second session read and no system-prompt read are made (a settled run's system prompt refreshes at the next run end). With no run shown the trigger makes the forced read only. The stream is closed and reopened once only when it has been silent longer than one heartbeat (`AGENT_EVENT_HEARTBEAT_MS`, 30 s: no byte since `lastSeenAt`, or since `openedAt` when none came, as the watchdog counts); a healthy stream is left alone, and with that reconnect the read's own `wrapperRebuilt` reconnect is suppressed (`suppressReconnect`), so the trigger never reconnects twice. The 75 s watchdog (`EVENT_STREAM_STALE_MS`) and the passive recovery triggers are unchanged; nothing here polls.
- Both reads give up `MANUAL_FETCH_TIMEOUT_MS` (15 s) after the trigger: one `AbortController` aborts them, and an aborted read applies nothing. The reconnect is not awaited. The fetch the user sees ends with the forced read (and the settlement it allows): the floating ↻ spins (`aria-busy`, label "Fetching latest…", fully opaque) until then, and a trigger meanwhile joins the fetch under way without a request of its own. It ends in exactly one notice on the existing notice shelf: "Updated to hh:mm" (local time, `formatFetchTime()`) when the read brought an entry id the view did not hold or changed a shared entry's message (`hasFreshContent()`, by entry id, never by text), "Already up to date" otherwise, "Fetch failed" when the read failed or timed out, which keeps the conversation and the composer. The strings are `chat.manualFetch*` in en, zh-CN and zh-TW.
- A changed revision does not collapse the view to the newest 50 entries: `mergeLoadedHistory()` keeps the entries paged in before the fresh window's first entry, with their older cursor and `hasMore`, and the fresh window replaces the rest (live messages included); with no overlap (more than a window of new entries) the loaded history stays and the fresh window follows it, a known gap until the next reload. The merged window is what the view cache stores. Reading position: a list at its bottom before the trigger is scrolled to the bottom once the read lands; anywhere else no scroll command is issued, so the content read stays in place.
- Read and stream are reconciled by the identity rules (`lateSnapshotTail()`, `sameMessage()`). A read while the view shows a run records its late tail as any mid-run read does. A read while the view shows none records the tail too, unless the trigger reconnected the stream (the new stream replays none of the old run's events), marked `beforeRun` with the open stream's `openedAt`: a half-dead stream may still hold that run's `agent_start` (and its own `connected`) ahead of the messages, so the first `agent_start` and a `connected` of that same stream keep the tail; the stream's copies of read messages are then dropped instead of rendered twice. A run the manual fetch settles keeps its read's tail the same way (`beforeRun`, unless the trigger reconnected): the view may know that run only from a state read, its `agent_start` still buffered in the half-dead stream, and settling would otherwise drop the tail before the stream delivers. A second `agent_start`, another stream or any other settled run discards it. The tail lives `MANUAL_FETCH_TAIL_MS` (100 s from when the manual fetch recorded it; `lateTailExpired()`): `EVENT_STREAM_STALE_MS` (75 s, two and a half heartbeats) plus one watchdog check (`staleCheckIntervalMs()`, 25 s, `lib/agent-event-connection.ts`). The manual fetch keeps a stream heard within one heartbeat, and the watchdog replaces a ready stream silent for 75 s only at its next check, up to 25 s later, so in a foreground tab the kept stream either delivers the run within the bound (SSE order puts it ahead of any later heartbeat) or is replaced, and the new stream's `connected` drops the tail. A background tab whose timers the browser throttles may check later still; a buffered run that half-dead stream flushes after the bound renders twice (the duplicate, a known residual). An `agent_start`, `connected` or `message_end` past the bound drops the tail instead of keeping or consuming it. Without the bound a stream that never delivered left the tail alive, and a later message with the same text was swallowed as "already loaded".

## A run's messages keep their keys (`lib/message-keys.ts`)
- A message's React key is its entry id, but one added during a run (the sent prompt, each `message_end`) has none until the file is read again: at the run's end, at the `agent_end` before an auto-retry, at `compaction_end`. pi persists a message only after emitting `message_end` and never announces its id. Keyed by its index until then, it remounted on that first read and lost its DOM state: the prompt bubble's inner scroll, open thinking, a tool output's scroll (#1184).
- Such a message is keyed by its place after the last loaded entry (`live:<anchor>:<offset>`), which appends and older pages leave alone. `loadSession`'s replacing read hands those keys to the entry ids at the same places after the anchor (`carryMessageKeys()`; the hook keeps the aliases while their ids are loaded), each checked against the message it replaces: `userMessageKey()` for the prompt (sent with the browser's timestamp), `customType` for a custom message, `timestamp` for the rest. From the first mismatch on, or when the window no longer holds the anchor (a run past the first page), messages keep their id keys and remount as before. Fork, search and `data-entry-id` still read the real `entryIds`.
- A kept message keeps its blocks too: `AssistantMessageView` keys a block by its index (`${entryId ?? "stream"}-<index>` re-keyed every block on that read), so open thinking, a tool card and its output's scroll survive it. `ThinkingBlock` drops what it loaded (`content`, `loading`, `error`) when its session, entry or block index changes, so a reused block never shows another entry's thinking; an open block the read turns `deferred` shows "Loading thinking..." until its full text arrives. The run's end still remounts the process messages as they move into Process details (another parent), and an answer that followed thinking in its message (its blocks move up as the thinking leaves); that is the grouping, not the read.

## Streamed chunks re-render only the reply (`lib/streaming-message.ts`, `hooks/useStreamingSelector.ts`)
- The streaming message lives in a `StreamingStore`, not in `useAgentSession`'s state. A reducer there re-rendered ChatWindow, the hook and the whole composer (`ChatInput`, `ModelSelector`) per chunk: at 4x CPU throttling about 500 ms of commits in a 40 s reply, with `ChatInput`'s props unchanged in 543 of 555 renders. ChatWindow subscribes only to whether a reply streams and has content yet; `StreamingReply` subscribes to the message and calls the prompt anchor's update after each chunk commits; `ChatMinimap` reads the message through `getStreamingMessage()` when it measures the turns.
- `useStreamingSelector()` subscribes with a state update, not `useSyncExternalStore`: that one renders every chunk on its own, while state updates let React batch the SSE events that arrive before it renders. The store calls its listeners synchronously in `dispatch`, so `message_end` appending the reply and ending the stream stay one render.
- `ChatInput` and `ChatMinimap` are `memo`'d as well, for the renders a running tool still causes. Their props must keep their identity across ChatWindow renders.

## Streaming markdown renders block by block (`components/MarkdownBody.tsx`, `lib/markdown-blocks.ts`)
- A streaming reply grows by a few characters per chunk, and one parse of the whole reply per chunk made a long reply quadratic: at 4x CPU throttling a 14k-character reply spent 8.8 s in react-markdown, its commits growing from 5 to 16 ms. While `isStreaming`, `MarkdownBody` cuts the text with `splitMarkdownBlocks()` and renders one `memo`'d `MarkdownBlock` per piece, so finished blocks keep their parse and only the last is parsed again. The pieces are siblings in the one `.markdown-body` div (react-markdown renders a fragment), so the DOM is the whole parse's, less the whitespace text nodes between blocks. A finished message is one block: its rendering is exactly what it was.
- A cut goes only after a blank line, before a line at column 0 that is not a list item; never inside a code fence or a `$$` block, never after the first line with an HTML tag outside inline code (a `<details>` or an open `<b>` spans blank lines through rehype-raw), never in a document opening with front matter. Link reference definitions and footnotes do not reach earlier blocks while streaming. `lib/markdown-blocks.test.mjs` checks that every prefix of a mixed document parses the same split as whole; keep that test passing when changing the rules.
- `onNavigateLink` (Settings › Skills) hands a document reader its local links: an anchor with `role="link"` and no `href`, so no click, middle-click or "Open in new tab" loads the path on the app's own URL; an empty (sanitized) `href` and HTML anchor destinations render as in chat. It also switches to `markdownDocumentRehypePlugins`, which give headings github-slugger slugs as `data-heading-anchor` (never an id, so two readers cannot collide), set after sanitizing and before KaTeX writes each formula's text twice. Chat rendering is unchanged.

## Hand-written anchors in rendered Markdown land (`lib/markdown.ts`, `rehypeMatchClobberedIds`)
- The sanitizer's `defaultSchema` clobbers ids: every `id` in content gains the `user-content-` prefix, so untrusted content cannot shadow the page's own elements. GitHub does this on both sides — cmark-gfm also rewrites a same-document `href="#x"` to `#user-content-x` — so a hand-written pair (`<a id="s2"></a>` with `[S2](#s2)`, the shape of a hand-built table of contents) still lands after rendering. The schema carried only the id half, so every in-document anchor pair broke: the element gained the prefix and the link pointing at it did not.
- `rehypeMatchClobberedIds` runs after sanitizing and prefixes fragment links exactly as unconditionally as sanitizing prefixes ids, so an id and an href that matched before sanitizing still match afterwards. Footnotes need it for the same reason: `mdast-util-to-hast` generates both their sides already prefixed and sanitizing prefixes the id once more, so an href left as generated would strand the link behind the doubled prefix. A bare `#` has no fragment to pair and stays as written; a link from content to one of the page's own ids stays unreachable — that is the clobber protection doing its job, not this rule.
- Registered in the chat and file-preview rehype lists, so both read the same rule. The document reader (Settings › Skills) keeps its own list: it turns `#headings` into `data-heading-anchor` slugs and hands every link to `onNavigateLink` before a URL matters, so it is not given the prefix. `lib/markdown-anchors.test.mjs` pins the hand-written pair, the footnote links, a raw-HTML anchor's fragment, and the untouched external fragment and bare `#`.
- A click on a `#fragment` link never leaves the job to the browser (`jumpToMarkdownFragment()`, chat's `MarkdownBody` and the file preview): it scrolls to the matching `id` (or `a[name]`) inside the link's own closest `.markdown-body`, as the Skills reader does with its headings. The browser's jump searches the whole page, and ids repeat there: every chat message with a footnote has its own `user-content-user-content-fn-1`, and the preview sits beside the chat, so a click in one landed in the other (headless Chrome). It would also put the fragment in the app's `?session=` URL as a history entry, and chat links open in a new tab (`target="_blank"`), which for a fragment was a second Pi Web tab that never scrolled. A fragment link therefore gets no `target`; a modified click is the browser's. Headings get no id in chat or the preview (no slug plugin), so a link to a heading still lands nowhere, as before.

Files: `lib/markdown.ts` (`markdownClobberPrefix`, `rehypeMatchClobberedIds`, `jumpToMarkdownFragment`, the plugin lists), the `a` renderers of `components/MarkdownBody.tsx` and `components/FileViewer.tsx`, `lib/markdown-anchors.test.mjs`.

## Windows Markdown file links (`lib/markdown.ts`)
- Markdown `link` and `definition` destinations matching `^/?[A-Za-z]:/` become `file:///C:/…` before rehype sanitization: otherwise a drive letter is rejected as an unknown URL scheme before the in-app file handler sees it. Chat, user messages and file previews share this rule. Only the prefix changes; Unicode, spaces, percent encoding, line/column suffixes and fragments retain their existing meaning. Raw HTML, code and direct image destinations are untouched, and the scheme allow-list stays fixed; renderers without an in-app file handler still filter out `file:` links.
- A click resolves the rewritten link as any `file:///C:/…` one (`resolveLocalFileHref()`): `C:/reports/REPORT.md`, its `:12` line suffix and `#fragment` dropped, as for a POSIX `/home/me/a.md:12`. A `/C:/…` destination kept its `href` before; it now opens as `C:/…` too, not as a tab for the path `/C:/…`.
- Backslash destinations (`C:\reports\a.md`) are not rewritten and still lose their `href`. CommonMark has already removed a backslash before punctuation (`C:\proj\.pi` reaches the plugin as `C:\proj.pi`), so the path cannot be read back from the url; pi gives the model its cwd with forward slashes.

## A ```svg fence previews as an image (`components/SvgBlock.tsx`, #1404)

## Long thinking renders in pieces (`ThinkingBlock` in `components/MessageView.tsx`, `lib/message-display.ts`)
- Thinking is plain `pre-wrap` text, never markdown. A model looping in its thinking writes megabytes (#1196), and as one text node the expanded block was laid out whole again on every streamed chunk (`StreamingReply` reads the prompt anchor's layout after each commit): in headless Chrome at 4x CPU throttling, 440 ms per chunk for 500k Chinese characters, so the page never caught up. `splitThinkingPieces()` cuts at the first line break past each 8,000 characters, and `ThinkingText` renders one div per piece. A cut depends only on the text before it, so while thinking streams only the last piece changes: 6 ms per chunk there. The line break at a cut is left out of both pieces and the block boundary stands in for it, so the lines, `innerText` and a selection's text are the single node's (headless Chrome). A line break that ends an empty line is never a cut: the piece would end in a line break, which a block draws no line for, and that empty line would be lost. Thinking that fits one piece is the one text node it was.
- A piece with no line break by 16,000 characters is cut there (a code unit earlier rather than inside a surrogate pair), so a loop that never breaks a line gets pieces too: at 1x, 500k Chinese characters went from 1,082 to 4 ms per chunk (and from 1,061 to 134 ms to expand), 2M English ones from 120 to 0.6 ms. That cut leaves nothing out, so it shows: a line end every ~16k characters of an unbroken line, and one more `\n` in a copy across it.
- The pieces are plain divs, not `memo`'d: React already leaves a div whose text is unchanged alone. A memo bailout keeps the old props, and each old piece is a V8 slice pinning the whole thinking string of the chunk it last changed in: streaming 2M Chinese characters retained 995 MB until the reply ended, 9 MB without memo (React 19 in headless Chrome).
- Expanding a finished block still lays out all of it once, as before (about 500 ms for that text at 4x). `content-visibility: auto` on the pieces would skip the ones off screen (70 ms to the first frame), but its placeholder heights, about half the real ones in the bench, change the scroll height as pieces come into view; it is not used.

## Deleting the selected session outlives the delete click (`components/AppShell.tsx`)
- `SessionItem.performDelete` captures `onDeleted` at the delete click, and `handleSessionDeleted` is a `useCallback` whose `selectedSession` closure is from that same render. The DELETE request can complete **after** the user has switched sessions, so the captured selection still names the session being deleted.
- The empty-composer fallback therefore guards on the latest selection read from a render-synced ref (`selectedSessionRef.current`), not the captured state, and takes the fallback cwd from that ref too: a user who navigated away stays on their new chat, and a user who lands on the deleting session in flight still gets a fresh composer in its cwd.
- `setRefreshKey()` and `invalidateWorkspaceRestore()` run unconditionally, so the sidebar list and any pending workspace restore never resurrect the deleted session.

## A link to a session that is gone (`components/AppShell.tsx`, `lib/initial-navigation.ts`)
- When the sidebar's list lacks the `?session=` id (`linkedSessionId()`), it toasts `sidebar.sessionNotFound` and `handleInitialRestoreDone` sets `skipWorkspaceRestoreRef`: the next `handleCwdChange` (the sidebar adopting its most recent project) shows a fresh composer instead of `restoreWorkspaceContext()`'s last open session, which the URL would then name (#1168). Later project switches restore as before; a gone session only this tab remembered (`sessionFromTab`, from `withTabOpen()`) still falls back as a fresh tab does.

## External session file discovery (`checkSessionMembership()`, `lib/session-list-scanner.ts`)
- Sessions the pi CLI (or any other process) creates or deletes bump no `sessionListVersion`, and the 30 s list cache's age is only looked at when a list is requested, so the sidebar's running poll never reloaded for them. `getSessionListVersion()`, which that poll calls every 2.5 s, now starts a filename check: it lists `sessions/<cwd>/*.jsonl` (`enumerateSessionFiles()`, directory reads only, no transcript opened) and invalidates the list when the set differs from what the last scan listed (`listSessionsIncremental()` records it). The poll that follows sees the new version and reloads.
- Appends never change a filename, so a running session costs nothing here: no rescan, no reload. Content rewritten under the same name is not a membership change either; in-process writers invalidate on their own as before.
- One check at a time, at most one per second (`SESSION_MEMBERSHIP_CHECK_MS`) whatever the number of tabs, none before the first scan. A change is recorded as it is reported, so it bumps once, not on every poll until the rescan. A scan that records its listing while a check reads replaces the baseline and the check's result is dropped: comparing an older read against a newer scan would bump for nothing, and the next check compares against the scan anyway.
- No `fs.watch`: a recursive watch on Linux is Node's JS layer (one inotify watch per file and folder, a synchronous walk of the whole tree when it starts, and a silently partial watch at the inotify limit), and on macOS it reports appends as `rename`. A missing sessions directory counts as empty; a changed `PI_CODING_AGENT_DIR` is just another listing. The cost is a readdir per project folder per second while some tab polls (about 10 ms for 18,000 files).

## History caches and deferred highlighting (`lib/session-reader.ts`, `lib/session-view-cache.ts`, `lib/highlight-queue.ts`)
- `GET /api/sessions/[id]/entries/[entryId]/tool-result-image?blockIndex=` answers `private, max-age=31536000, immutable`: a session's entry id and block index name the same bytes for good (pi only appends, a migration's rewrite keeps every entry, a `context_edit` leaves raw history alone). With `no-cache` every view re-sent multi-MB images and decoded their base64 again. Error replies carry no cache header.
- A list rebuild reads a fork's or subagent's run (`readSubagentRun()` over the file's bounded head and tail) once per scanned row: `listSessionsIncremental()` hands back the index's same row object while the file's size and mtime hold, so a `WeakMap` keyed by the row caches the run. A rebuild on 355 sessions (137 subagents) went from 36 ms to 7 ms, synchronous reads that blocked the event loop. A row the scanner makes anew (a changed file, a restart) is read again; a failed read is not cached.
- `listSessionsIncremental()` parses a file that only grew since its last scan from just past the last newline that scan read (#1259): the index keeps that offset with the row's running totals, the file's inode and a hash of the header line plus the 512 bytes before the offset, so a file replaced by a rename (sed -i, an editor, git checkout), a rewrite in place that changes the header (pi's migrations, delete's reparenting), a same-size or shorter file, or an unterminated last line that counted gets a full read; a same-length edit that keeps the inode, the header and those 512 bytes is missed, and stays missed through later appends. Lines end at `\n`, `\r\n` or a lone `\r`, as the scan's readline did on Node 22; a raw U+2028/U+2029 (JSON.stringify leaves both raw), which Node 24's readline and so `SessionManager.listAll()` split on, stays in its line, as pi's loader keeps it. An appended line on a 150 MiB session went from 260 ms to under 1 ms; `pi-web-session-index.json` is written at most once per 5 s (a trailing throttle, into the agent dir of the scan that queued it), not after every listing.
- `lib/session-view-cache.ts` measures a snapshot (its `JSON.stringify` length) once, when it is stored, and evicts by the stored sizes: snapshots are never mutated in place. Re-serializing every cached session on each store took 7.7 ms with eight 0.8 MB snapshots (1.3 ms now), at every run's end, compaction and session switch. The unmount check for a wider cached window is `snapshotCoversLoadedEntries()` (a `Set`), not nested `includes`.
- Code fences (`CodeBlock`, `components/MermaidBlock.tsx`): Prism tokenizes in the render, about 5-10 ms per 1,000 characters of TypeScript on a desktop. Within one task the first 2,000 characters of fences are highlighted at once (`takeHighlightBudget()`); the others render through the same `SyntaxHighlighter` as `text` (same lines, numbers and box, no tokens) and take their language one per idle slice, newest first (`waitForHighlight()`; Safari has no `requestIdleCallback` and waits 50 ms). Opening a session with 86 fences at 4x CPU throttling, the commit that shows the messages went from 1.1 s to 0.66 s; the end of a streamed reply gets the same budget. `codeTagProps` sets no class, so tell a highlighted fence by its `span.token` elements other than `.linenumber`, not by a `language-*` class. Fences wrap long lines, as pi's TUI does (no toggle; #1360): `renderCodeLines()` makes each line a flex row of its number and its text (`.markdown-code-line`, `overflow-wrap: anywhere` for URLs and paths), so a wrapped line goes on under its text, the text keeping the row's classes (the later lines of a block comment take their color from them), and an extension dialog measures its fences unwrapped (`.extension-dialog-measuring`) so it still widens to show them whole where the screen allows (#947).
- Prism languages load on demand (`lib/prism-languages.ts`, `hooks/usePrismLanguages.ts`). `CodeBlock` and `FileViewer` render with `react-syntax-highlighter/dist/esm/prism-light` (refractor's core), never the package index: its `Prism` imports `refractor/all`, which registers about 300 languages when evaluated, ~650 ms of the first `AppShell` render at 4x CPU throttling on every page load, code on screen or not. The first highlighter to mount imports `refractor/all` as a chunk of its own; it registers into the same core instance, so every language and alias works as before. Until then fences render as `text` and files as `plaintext` (same lines, numbers and box). A page with no code never loads it. Client code imports only types from `react-syntax-highlighter` itself.
