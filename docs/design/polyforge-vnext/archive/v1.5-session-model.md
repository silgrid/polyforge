## Origin

Phase-0 pilot (40 wrapped WIs) exposed F13/F16/F18 credential races,
adoption-window fences, and intent-mapping ambiguities — all symptoms of
one design gap: multi-daemon coordination was specified only as "zero
daemon-to-daemon communication" (00-architecture) without writing the
"how do they coordinate through aihub" half. Industry research (ZooKeeper
sessions, K8s UID replacement, Azure message sessions, Celery workers)
confirmed the correct family: **ownership epoch + fencing-on-use**.

## The model (owner's proposal, refined after review)

### Core mechanism

- WI table gets a `session_id` column (the ownership token)
- **Claim** = atomic CAS on aihub: set session_id only if currently empty
  AND status is claimable (queued). Generates a crypto-random session_id.
- **Same-machine recovery**: session_id UNCHANGED. Agent re-derived with
  `spawn_n` incremented. Recovery cascade unchanged (transcript → resume,
  no transcript → fresh, N fails → bounded fail).
- **Cross-machine takeover**: POST force-takeover → aihub atomically swaps
  session_id → new daemon clones capsule from bare repo → resumes.
- **Terminal** (wrap/fail/cancel): aihub clears session_id.
- **Bounded fail** → status=blocked AND session_id cleared; restart sees
  blocked under another (or no) session → reaps any orphan and DROPS the
  local record (repo review 2026-10-16 B-6: the hub's blocked is
  authoritative); the owner's `pf resume` then re-claims it through the
  ordinary start path (quarantine-or-clone of the old capsule), instead of
  being refused locally as "already active".
- **Graceful shutdown**: session_id stays on WI (status=paused). Same
  daemon restart: session_id matches → resume. Different daemon: needs
  force_takeover. Operator pause (pf-stop --pause): NOT auto-resumed on
  restart (restart distinguishes by a "clean_pause" flag on the WI).

### The three mandatory additions (fable BLOCKER findings)

These cannot be deleted — each guards against an already-paid-for failure:

#### B1: Pre-claim durable journal (crash safety)

The claiming journal shrinks to `{wi_id, session_id}` written durably
BEFORE the CAS call. Startup replays: hub session == journal's → adopt
and finish start; hub session empty/other → drop the record.
This is both the D5 #Start-crash fix AND the CAS retry-idempotency anchor
(ZooKeeper's "ambiguous claim" problem: response lost, retry must send
the same session_id).

#### B2: Flush fence = (session_id, spawn_n) dual key

Session_id alone cannot discriminate agent derivations within a session.
Every derivation gets a monotonic spawn_n. The agent's flush envelope
carries both. The fence: `session_id matches AND spawn_n == current`.
This replaces the attempt/instance/adoption-window fence (F16's fix)
with a simpler mechanism that covers the same threat: in-flight stale
flushes from killed derivations and escaped subprocess residue.

#### B3: Identity/credential split

Session_id is the SECRET (push credential). Public surfaces (WI reads,
events, logs, status displays) use a derived fingerprint (sha256 prefix).
Aihub stores only the hash; startup "matches mine" check is a
compare-only endpoint (POST /work-items/{id}/session/verify).
The agent NEVER sees the session_id. (Superseded by the audit
subtraction pass B: it sees no identity env at all — the PF_SPAWN_N /
PF_SESSION_HANDLE injections were deleted as unread; the derivation
counter and the public fingerprint live in the capsule's spawn journal.)
Push credentials travel via GIT_ASKPASS (one-shot, outside capsule),
never in env or argv.

### Deleted from v1

- owner_generations table (entire generation/attempt/instance lineage)

- The adoption-window fence (replaced by spawn_n)
- The claim/resume/takeover intent trichotomy (now: claim + force_takeover
  + session-match-attach for cross-machine pause-resume)
- The instance-id lineage (attempt#N)

### MAJOR findings and their rulings

| # | Finding | Ruling |
|---|---|---|
| M1 | "Empty session" = both terminal and claimable | CAS must be (status, session) joint; claim gates restored (TERMINAL_STATE, NOT_QUEUED, DEPENDENCY_BLOCKED, NOT_CLAIMABLE) |
| M2 | Bounded fail: keep session → restart revives (violates the bounded-fail contract); clear → CAS-claimable | Blocked = status blocked + session cleared; restart sees blocked → untouched; blocked excluded from CAS claimable set until unblocked |
| M3 | Paused-with-session: no liveness, cross-machine resume needs admin takeover, operator pause auto-resumed, pushes valid while paused | Push validation adds `status==running`; cross-machine resume via session-match attach endpoint (not force_takeover); operator pause distinguished by clean_pause flag; liveness = heartbeat (existing machines face, phase-1 wiring) |
| M4 | Zombie discovery latency unbounded (push-cadence-dependent) | Periodic session revalidation on monitor tick (~5 min); discovered mismatch → kill tree + quarantine + release |
| M5 | Same-machine dual daemon TOCTOU on socket probe | flock on daemon data dir in addition to socket probe |
| m3 | Answers lost at cross-machine takeover | Emit owner-visible "answer may be lost; question re-opened" event; phase-2: relay answers through aihub |
| m4 | Ownership/audit metadata deleted | WI carries {session_fingerprint, machine_id, owner, session_started_at}; events carry session lifecycle |
| m2 | "Session IS the credential" overstates (GitHub origin side channel) | Document explicitly: fencing covers aihub git proxy only; zombie's GitHub pushes bounded by M4's discovery timer |

## Implementation plan (parallel lanes)

### Lane A: aihub server (internal/aihub/)
- Add session_id column to work_items (schema migration)
- CAS claim endpoint (session_id set-if-empty + status claimable)
- force-takeover endpoint (atomic session_id swap + event)
- session/verify compare-only endpoint
- Git proxy: validate push session_id (compare against hash) + status==running
- Push-option backup fence: session fingerprint in push option, hook validates
- Delete owner_generations table + claim/resume/takeover intent code
- Keep: idempotency key (re-keyed on session), claim gates (status-based)

### Lane B: runtime (internal/polyforge/runtime/)
- state.json simplification (remove attempt/instance/generation)
- spawn_n counter (the PF_SPAWN_N env injection it originally shipped
  with was deleted as unread by the audit subtraction pass B; the
  counter lives in state.json and the capsule spawn journal)
- session fingerprint in the spawn journal (the PF_SESSION_HANDLE env
  injection was deleted with it)
- Claiming journal shrinks to {wi_id, session_id} pre-CAS
- Restart reconciliation: session_id match → resume; mismatch → release
- Recovery: spawn_n++ (no generation change); bounded fail → blocked + clear
- Graceful shutdown: leave session_id; distinguish clean_pause flag

- Flush fence: (session_id, spawn_n) dual key
- Answer ledger keyed on session_id
- Gitops push carries session_id via GIT_ASKPASS (not env/argv)
- Periodic session revalidation on monitor tick
- Push validation includes status==running check

### Lane D: test infrastructure (test/)

- harness: new session-aware assertions
- 12 new e2e scenarios (T1-T8 parallel + D1-D5 operator drills)

## Appendix: Industry research findings (2026-10-01)

Sources: Wikipedia Lease, K8s Pod Lifecycle, Azure Competing Consumers,
ZooKeeper Recipes, RabbitMQ RPC, Celery Workers.

Key insights:
1. The session_id model is the correct FAMILY (epoch + fencing), same as
   ZooKeeper sessions, K8s UID replacement, Azure message sessions
2. Queue-based competing consumers (RabbitMQ/Celery) are WRONG for
   stateful multi-step work — Azure added "message sessions" precisely
   for this, confirming our direction
3. THE critical design rule: "Invalidation-on-claim creates the credential
   race; fencing-on-use resolves it" — let every daemon keep its credentials,
   make the server reject writes from any session that is no longer current
4. Claim must be CAS that never evicts a live owner; takeover is a separate
   privileged operation
5. Zombie protection = fencing-on-write (only correctness layer when zombie
   is unreachable); signals (kills/broadcasts) are acceleration, not correctness
6. Ambiguous-claim problem (ZooKeeper GUID lesson): a claim that times out is
   unknown-outcome; retry must be able to discover "did my claim land?"
   → solved by the pre-claim journal (B1)
7. The one remaining gap in ANY model: git-push side channel to origin
   (GitHub) — a fenced zombie can still push directly; bounded by the
   session revalidation timer (M4)

Fable review verdict on the refined model: 3 BLOCKER + 5 MAJOR + 5 MINOR
findings, all addressed above. The core instinct (delete the lineage tower,
use session_id) was confirmed sound; the three mandatory additions (B1/B2/B3)
guard against D5, F16, and credential-leak failures respectively.
