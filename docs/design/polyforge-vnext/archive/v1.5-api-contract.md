## 0. Naming

- `session_id` — the SECRET. 32 crypto-random bytes, hex. Minted by the
  daemon (B1: journaled pre-CAS), presented once at claim/attach/takeover,
  used as the git push password. NEVER appears in: WI reads, events, logs,
  agent env, push options, argv.
- `session_fingerprint` — the PUBLIC handle. `hex(sha256(session_id))[:16]`.
  Appears in WI reads, events and logs. (Superseded by the audit
  subtraction pass B: the agent env carries NO identity markers at all —
  the fingerprint reaches the capsule's spawn journal, not the child
  environment.)
- aihub stores ONLY `session_hash` = hex(sha256(session_id)) full. It never
  stores or returns the secret.

## 1. Endpoints (server: Lane A implements; client: Phase 0 provides)

### 1.1 POST /api/v1/work-items/{id}/claim  (path reused, semantics replaced)
Request:
```json
{"session_id":"<64-hex-secret>","machine_id":"m1","owner":"op","idempotency_key":"..."}
```
CAS gate (M1 joint): `status == "queued"` AND `session_hash IS NULL` AND
bundle present AND no unfinished blockers. All checked in ONE transaction
(single-writer SQLite recheck is authoritative).
Success → status=running, session row fields set, event `session_claimed`.
Response: `{"claim": SessionClaim, "work_item": WorkItem}`.
Errors: `CORE-409 ALREADY_HELD` (session non-empty), `CORE-410 TERMINAL_STATE`,
`CORE-409 NOT_CLAIMABLE` (no bundle / not queued), `CORE-409 DEPENDENCY_BLOCKED`.
Idempotency: same idempotency_key returns the SAME response (D4); the cached
session must still be the live one (stale cache → CORE-403 STALE_SESSION).

### 1.2 POST /api/v1/work-items/{id}/session-verify  (compare-only, B3)
Request: `{"session_id":"<secret>"}`. Response:
```json
{"work_item_id":"...","matches":true,"status":"running",
 "current_fingerprint":"ab12...","clean_pause":false}
```
`current_fingerprint` is the fingerprint of the CURRENT holder (if any);
it lets a superseded daemon learn who holds it without ever seeing secrets.
No state change. GET on the WI also exposes `session_fingerprint` (public).

### 1.3 POST /api/v1/work-items/{id}/session-attach
For: same-session restart resume of a paused WI (M3). Request:
`{"session_id":"<secret>","machine_id":"m1","owner":"op"}`.
Gate: hash matches AND `status == "paused"` AND `clean_pause == false`.
→ status=running, event `session_attached`. Response: same as claim.
Errors: `CORE-403 STALE_SESSION` (hash mismatch), `CORE-409 NOT_ATTACHABLE`.
(clean_pause=true → operator pause: restart must NOT auto-resume; only
force-takeover or a CLI unpause may resume it.)

### 1.4 POST /api/v1/work-items/{id}/force-takeover
Request: `{"session_id":"<new secret>","machine_id":"m1","owner":"op",
"reason":"...","idempotency_key":"..."}`.
Gate: status non-terminal (running or paused), reason non-empty.
Authorization: admin or project maintainer (the human decision gate).
**AMEND (#109)**: a machine-credential caller (kind='machine', the
heartbeat-registration shape every execution daemon holds) with project
membership (writer+) is admitted when the request's `machine_id` is the
machine identity its own credential represents — the executor's
self-service recovery (`pf submit <id> --takeover` fencing a dead or
foreign holder), scoped so a machine can never hand a work item to a
third identity. Humans keep the v1 gate unchanged.
→ atomically swap session row to the new hash/fingerprint, status=running,
event `session_superseded` carrying the OLD fingerprint (m4 audit).
Old daemon learns at next use (fencing-on-use). Response: same as claim.
Producer note (#109): the CLI-side `pf takeover` mints the secret and
hands it to the LOCAL daemon over the UDS (POST /jobs/{id}/adopt-session,
verify-backed, custody-journaled) and labels the session with the
daemon's own machine id — a takeover whose secret no daemon holds (the
old cli-<hostname> mint) is refused by the verb instead of orphaning
the work item.

### 1.5 POST /api/v1/work-items/{id}/session-end
Replaces end-generation. Request:
`{"session_id":"<secret>","status":"wrapped|failed|blocked|paused","note":"...","clean_pause":false}`.
Gate: hash matches (fenced). Terminal verdicts (wrapped|failed|blocked)
→ set status, CLEAR session row entirely, event `session_ended`. Blocked
(M2): session cleared + status=blocked; blocked is excluded from the
claim gate until a human unblocks.
**AMEND (merge, 724c5e4)**: `paused` is the 4th legal status and routes
to the M3 pause transition — the session is KEPT, status becomes paused,
and `clean_pause` rides the SAME atomic fenced update (the operator CLI
is the only pause producer, so it is always a clean pause; the flag=false
daemon-shutdown shape exists on the server but has no producer today).
`pf resume` clears the flag via WI PATCH (whitelist gained `clean_pause`),
then asks the local daemon (`POST /jobs/{wi}/resume-paused`): a live
holder attaches and continues in place at once (v2-converge §7);
otherwise the holder's next start attaches.
Errors: `CORE-403 STALE_SESSION`.

### 1.6 Git push auth (fencing-on-use)
GIT_ASKPASS (one-shot, outside capsule) presents username=`<wi-id>`,
password=`<session_id>`. aihub git proxy validates: sha256(password) ==
session_hash AND `status == "running"` (M3: no pushes while paused).
Push-option backup layer: `--push-option=session-fingerprint=<fp>` — the
pre-receive hook rejects when it differs from the credential's fingerprint
(same structure as the v1 attempt-id backup layer, renamed values).
Rejection message names the CURRENT holder fingerprint so the superseded
daemon can self-diagnose.

### 1.7 GET /api/v1/work-items/{id}/session  (public holder read)
The operator's takeover-decision input: who holds this WI right now.
No request body. Read-only — no state change, no event. Response:
```json
{"work_item_id":"...","status":"running",
 "session_fingerprint":"ab12...","machine_id":"m1",
 "session_started_at":"...","clean_pause":false}
```
Fields: the PUBLIC audit set only — the same field set as the m4
`SessionPublic` block, with `machine_id` spelled per this endpoint
contract. `session_hash` and the session secret NEVER appear in any
response (B3; pinned by tests in the server, client and CLI suites).
Authorization: the same read gate as `GET /work-items/{id}` —
`wiProject` + `requireRead`, NOT the api-key scope check of §1.1–§1.5.
Any project member with read access (including role `viewer`) may ask;
non-members get the standard hidden-not-found answer (CORE-404).
Tri-state as 200: held-running, held-paused (session row kept per the
§1.5 amend; `clean_pause` rides along), and unheld (queued, blocked, or
terminal after a session-clear) are three ORDINARY HTTP 200 answers —
never 404/409 for an existing work item — so a takeover-decision script
needs no error handling to tell "free" from "taken". Unheld shape: the
holder fields are flat-omitted from the JSON (the implementer's-call
empty shape consistent with §1.2's precedent of simply omitting the
fingerprint when unheld): `{"work_item_id":"...","status":"queued",
"clean_pause":false}`. Unknown work item: CORE-404.

## 2. Wire types (api/types.go — added in Phase 0, do not modify shape)

```go
type SessionClaim struct {          // response envelope (claim/attach/takeover)
    WorkItemID        string        `json:"work_item_id"`
    SessionFingerprint string       `json:"session_fingerprint"`
    MachineID         string        `json:"machine_id"`
    BundleName        string        `json:"bundle_name"`
    ClaimedAt         string        `json:"claimed_at"`
    Repos             []ProjectRepo `json:"repos,omitempty"`
}
type SessionClaimRequest struct {   // claim + takeover (adds Reason field for takeover)
    WorkItemID    string `json:"work_item_id"`
    SessionID     string `json:"session_id"`
    MachineID     string `json:"machine_id"`
    Reason        string `json:"reason,omitempty"` // takeover only, required there
    IdempotencyKey string `json:"idempotency_key,omitempty"`
}
type SessionAttachRequest struct {
    WorkItemID string `json:"work_item_id"`
    SessionID  string `json:"session_id"`
    MachineID  string `json:"machine_id"`
    Owner      string `json:"owner"`
}
type SessionVerifyRequest struct { SessionID string `json:"session_id"` }
type SessionVerifyResponse struct {
    WorkItemID string `json:"work_item_id"`
    Matches    bool   `json:"matches"`
    Status     string `json:"status"`
    CurrentFingerprint string `json:"current_fingerprint,omitempty"`
    CleanPause bool   `json:"clean_pause"`
}
type SessionEndRequest struct {
    SessionID string `json:"session_id"`
    Status    string `json:"status"` // wrapped|failed|blocked
    Note      string `json:"note,omitempty"`
}
```
WorkItem JSON gains: `session_fingerprint`, `session_machine`,
`session_started_at`, `clean_pause` (public audit fields, m4; the
session-owner field is deleted, polyforge#149 C12). Never a hash,
never the secret.

## 4. Daemon-local contract

### 4.1 state.json jobRecord (Lane B)
```json
{"work_item_id":"...","session_id":"<secret>","session_fingerprint":"...",
 "state":"running","capsule_dir":"...","git_dir":"...","remote_url":"...",
 "spawn_n":3,"recover_fails":0,"candidates":[...],
 "live_transcript":"...","clean_pause":false}
```
`session_id` lives ONLY here and in GIT_ASKPASS (file mode 0600, wiped
after use). Never in capsule, never in agent env.

### 4.2 Claiming journal (B1, Lane B)
`claiming.json` entries shrink to:
`{work_item_id (submitted spelling), session_id, idempotency_key, machine_id, at}`
written durably BEFORE the claim call; cleared once the start settles
(job registered or session-end(blocked) compensation). Startup replays:
verify(journal session) → matches → adopt and finish the start; else drop.

### 4.3 Spawn identity (B2, Lanes B+C)
> Superseded in part by the audit subtraction pass B (2026-10-13): the
> two identity ENV injections below were deleted — nothing read them.
> The derivation counter and the public handle ride the capsule's
> `runtime-state/spawn-journal.jsonl` (last line = latest derivation),
> which is where every consumer already read them. The only env markers
> a step process gets are the cleanup markers `PF_WI_ID` / `PF_DAEMON_ID`
> plus the dedicated agent-directory pointers `PI_CODING_AGENT_DIR` /
> `PI_CODING_AGENT_SESSION_DIR`.
- ~~`PF_SPAWN_N` env~~ (deleted): the per-WI monotonic derivation
  counter. Local: state.json spawn_n + 1. After cross-machine clone:
  capsule `runtime-state/spawn-journal.jsonl` max + 1 (journal lines
  carry a `spawn_n` field; last line = latest derivation).
- ~~`PF_SESSION_HANDLE` env~~ (deleted): the public fingerprint, now
  journal-only.
- RTStarted/RTRecovered announcements carry `spawn_n` (payload field
  renamed from instance id).
- Flush fence (observe): request `spawn_n` must equal the monitor's CURRENT
  derivation or the LATEST ANNOUNCED (same recovery-window dual-match as
  v1's, keyed on the counter); anything else → `DAEMON-409 STALE_SPAWN`.
  Envelope field: `spawn_n` (int). Old `attempt_id` field deleted in cleanup.

### 4.4 Session revalidation (M4, Lane C)
Monitor tick piggybacks a `session-verify` every ~5 minutes per RUNNING
job. `matches == false` → kill tree → quarantine capsule (rename
`<id>.quarantined.<ts>`) → drop record → event. The daemon makes NO hub
transition (superseded, not terminal).

### 4.5 Answer ledger (Lane C)
Keyed on work_item_id + question_id (stable ids, F9). Survives daemon
restart (file) and same-machine recovery. Cross-machine takeover: the
ledger does NOT travel; on takeover the new daemon re-presents the pending
question from the capsule and the CLI relays; the takeover event note
carries "answers may be lost; question re-opened" (m3).

## 7. M3 machines heartbeat wiring (ADDITIVE, lane hb-m3 — post-freeze amendment, touches no §1–§5 shape)

The M3 gate metric (`--m3-heartbeat-max-age`, tools/gate-metrics.go) judges a
stuck step excused when its holder machine's heartbeat is alive. The face was
specified (02-aihub-core.md §4.10 row 21) but never wired: no daemon sent
heartbeats, and the gate's offline reader resolved "current holder" from the
deleted v1 `owner_generations` table, which matches nothing on a v1.5
aihub.db. This section is the wiring record; everything here is additive to
§1–§5.

### 7.1 POST /api/v1/machines/heartbeat (face pre-existed; payload extended)

- Auth unchanged (`s.auth`: any valid api key). Upsert semantics unchanged:
  first call registers (machine user + machines row + one-time machine key);
  repeats refresh in place. `machine_id` required; blank → CORE-400.
- Payload gains two optional liveness-projection fields (absent = keep the
  stored value; `live_wi_ids: []` = replace with nothing held live):
  `mode` (daemon admission mode) and `live_wi_ids` (JSON array of WI ids the
  daemon currently holds live: running/recovering/sealing).
- **No client timestamp**: `last_heartbeat_at` is server-stamped
  (`core.Now()`, RFC3339Nano). One clock, no skew; the gate judges the
  server-stamped value.
- Fix rode along: the refresh UPDATE mixed plain `?` placeholders with
  `WHERE id=?1`, so the id parameter was bound to `Now()` and every repeat
  heartbeat was a silent no-op (matched 0 rows). Repeat heartbeats now
  actually refresh — pinned by test.

### 7.2 GET /api/v1/machines (NEW, admin)

Operators' liveness read face (`authAdmin`, matching the users/api-keys
admin face). Response: `{machines: [{id, user_id, runtime_version, mode,
live_wi_ids, last_heartbeat_at, heartbeat_age_seconds?, stale}],
stale_after_seconds, count}` ordered oldest-heartbeat-first. `stale` is
server-computed: `age > stale_after` where the threshold is
`-machines-stale-after` (default 5m = 5× the heartbeat default). An
unparseable stamp reports `stale=false` with no age — cannot-judge is not
dead. Schema rode along: `machines` gains `mode`/`live_wi_ids` via the same
guarded ALTER TABLE migration discipline as the session columns
(`migrateMachines`).

### 7.3 Daemon side (internal/polyforge/daemon/heartbeat.go)

`pf daemon -heartbeat-every` (default 60s; 0 = disabled) drives a heartbeat
goroutine on runCtx: POSTs machine_id, runtime_version (`v1.5`
generation constant), current mode, live WI ids (never nil — an idle daemon
states `[]` so the server's keep-old semantics cannot leave ghost ids).
Failures are log-only with bounded backoff (interval doubles per
consecutive failure, capped at 16× base; success resets). Never fatal,
never blocks Run. The registration response's one-time machine key is
deliberately not surfaced by the client type — the daemon runs on its
operator-issued credential.

### 7.4 gate-metrics reader

`readAihub` resolves the current holder per WI from
`work_items.session_machine IS NOT NULL` (set on claim/attach, nulled by
session-end and terminal transitions — exactly the deleted
`owner_generations WHERE ended_at IS NULL` semantics), with the v1 query
kept as fallback for pre-v1.5 pilot roots. Verified live (lane hb-m3) on a
core.Open-built aihub.db: fresh heartbeat excuses a 53h in_progress step;
the same stamp backdated past the threshold flips the reading to stuck
(1).
