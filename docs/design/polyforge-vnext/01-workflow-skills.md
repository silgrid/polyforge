## 1. Scope and non-goals <!-- §1 -->

### 1.1 Scope <!-- §1.1 -->

- The bundle's directory layout and the boundary between the two kinds of skill (the routing skill / the step definition file) (§2.1, §4.4).
- The `workflow.md` frontmatter: every key the driver parses and the load-time validation (§4.1); the step definition file frontmatter (§4.4).
- The reference flow and grill (§4.2, §4.3); context between steps (§4.4a).
- Execution semantics (§6): sequential advance, the bounded rewind on a business gate FAIL, in-place retry and candidate switching on infrastructure failure, incomplete, the driver main loop, the budget.

### 1.2 Non-goals <!-- §1.2 -->

- Spawning the step process, supervision's death judgement and cause handling (`v2-converge.md#§2`, `reference.md#§7.6`).
- The capsule layout and the git chain (`v2-converge.md#§14`, appendix E).
- There is no per-step isolation: a step runs natively on the host (the 2026-10-14 trust model, `v2-converge.md#§0`).

## 2. Terms and invariants <!-- §2 -->

### 2.1 Definitions <!-- §2.1 -->

- **Routing skill**: `skills/polyforge/` (`SKILL.md` + one fragment per verb under `verbs/`, plus doctor/help/init, `execute-intent.md` which carries the execution-intent routing, `ship.md` which only says "delivery is already the deliver step", and `followup.md` which owns the AIHub `doc.track` follow-up ledger and its ingest/present/claim/dismiss/dedupe lifecycle (session-only; step agents never run it); the directory is authoritative). The only routing skill in the user's harness: it only turns intent into `pf` verbs, never parses a workflow, never touches the execution scene, and **never executes a workflow**. Install also ships the independent `skills/output-format/` skill (owner-facing output discipline; no verbs and no routing), loaded alongside it. **It also carries the execution intent** (owner ruling 2026-10-20): code work the owner directs (change a repo / upgrade / fix a bug / deploy) is an execution intent, and the routing layer's correct action is to turn it into an execution ticket — `file create --bundle` + `submit` — **turning intent into a ticket is routing, not execution**; "never touches the execution scene" constrains the routing layer's own hands (the capsule, worktrees, execution-state files, steps), not the category of intents it may route. A session agent never does code work by hand: git branch/commit/push, gh pr create and `.repo/` writes happen only inside a claimed capsule (the v2 home of v1's IR1 write-operation gate — the iron rule was lost when the v1 skill set was deleted, and this item is its migration; carriers: the SKILL.md description's standing advertisement + session rule 7 + `verbs/execute-intent.md`).
- **The executor of a workflow** is the Go driver inside the daemon process (`internal/polyforge/driver`), which spawns short-lived harness processes step by step along the step graph; there is no execution skill and no long-lived agent.
- **Workflow bundle**: `workflows/<bundle-name>/` = `workflow.md` (frontmatter + body) + `steps/<id>.md`; step files shared verbatim by several bundles live in `workflows/_shared/steps/` (§4.4). There is no registry / registration interface / digest: a WI records only `bundle_name`, and the worker machine's daemon materializes from `-workflows-dir` (in production `<data-dir>/release/current/workflows`) (`reference.md#§7.1`).
- **workflow.md**: its frontmatter is the sole structural schema of the execution graph (§4.1); the body is flow-level prose and takes no part in parsing.
- **Execution graph**: the frontmatter's `steps` array, whose array order is the execution order. The copy materialized into the capsule does not change during that WI's execution; Core stores no parse result.
- **Step definition file**: `steps/<id>.md`; of its frontmatter the driver reads only `output` (§4.4), and the body is spliced into that step's dispatch prompt.
- **budget**: only the step-level `budget.wall_minutes`, an estimate: T = max(3 × wall_minutes, `--step-timeout`) (§6.6).
- **on_fail rewind**: the bounded rollback to an earlier step on a business gate FAIL (§6.2).
- **model_candidates**: a step's ordered candidate list `<harness>:<model>[:<effort>]` (§4.1; priority and switching in `reference.md#§7.5`).
- **grill / grill-review**: the two explicit steps of the reference flow (§4.2, §4.3).
- **e2e-author**: before code, writes acceptance scenarios for the new behavior only, commits them, and in the same step proves them red scenario by scenario at the assertion level against the pre-implementation tree; after code, `verification` reruns them (polyforge#165).
- **gate FAIL / infrastructure failure**: the former is a gate's negative judgement of the output (a `gate_failed` result); the latter is every failure that produced no judgement (process death, exit without a result, timeout, rate limiting and so on; causes of death in `v2-converge.md#§2.3`). Output that does not fit the `output` schema is **not** an infrastructure failure (for the release/deploy steps the envelope is rejected, elsewhere it is only recorded, §4.4).
- **Human gate**: `requires_human_answer: true` (without a human answer in this attempt chain the step can neither complete nor gate_fail) or `if_asked` (the question can only be answered by a human; completing with zero questions is allowed but records a `human_gate_unasked` event). The old key `interactive:` is an unknown key and is ignored — writing it **does not** give a human gate.
- **`next_step_by_order`**: the driver main loop's procedure for choosing the next step to execute (the earliest non-done step); it does not judge whether the workflow succeeded or failed (§6.5).

### 2.2 Invariants <!-- §2.2 -->

- INV-1a: `bundle_name` is frozen at first claim (the R2 window, `wi-kind-contract.md#§2`); the materialized copy inside the capsule is read-only and unchanged during execution; a re-claim re-materializes without content verification, and drift of the local checkout is a configuration accident.
- INV-1b: a rewind is triggered only by a business gate FAIL; an infrastructure failure always retries in place and never rolls back.
- INV-1c: the cumulative rewind count of each workflow instance has an upper bound (§6.2).
- INV-1d: a rewind resets every step in `[target, gate)` to `pending` and archives the old outputs as historical attempts; there is no second invalidation mechanism.
- INV-1e: `next_step_by_order` returns empty for only two reasons — all done, or the workflow is already `failed_gate` / `failed_rewind_exhausted`; the main loop must distinguish them before deciding how to wrap up (§6.5).
- INV-1g: model candidates live only in the workflow.md frontmatter (plus the `.polyforge.yaml` / `pf submit --models` overrides, `reference.md#§7.5`); the candidate pointer (an identity anchor located in the live list, plus pending advancement) is advanced only by model-class causes of death and by the second `ended_without_result` on one candidate, and a gate FAIL never switches candidates (a rewind resets the pointer).
- INV-1h: a step definition file never writes `model`; a completed result's `output` should match the declared `output` schema: enforced for the release bundle's `release`/`deploy` (a non-conforming result is rejected), record-only for the rest (§4.4), with one dedicated rejection on the `plan` step: a declared write without a `coupled_obligations` entry.

## 4. Data structures: the workflow.md frontmatter schema and step definition files <!-- §4 -->

### 4.1 The full workflow.md frontmatter schema (the sole structural schema) <!-- §4.1 -->

`workflow.md` opens with YAML frontmatter (delimited by `---`). Top-level fields (the driver parses only `defaults`, `rewind` and `steps`; `name`/`description` are for humans and not parsed):

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | by convention | the bundle name, by convention equal to the directory name (not parsed) |
| `description` | string | by convention | a one-line description (not parsed) |
| `rewind.max_total` | int | optional | the cumulative bound over the workflow's automatic rewinds (owner-routed ones never count); an omitted (or ≤0) value falls back to min(4, #on_fail edges × max_per_step) — 4 on a lane without rewind edges |
| `rewind.max_per_step` | int | optional | default 2; the bound charged per gate→target edge — each gate rewinding to the same target carries its own slots |
| `defaults.model_candidates` | []string | optional | the ordered candidates when a step declares none; each item `<harness>:<model>[:<effort>]` (harness ∈ pi/claude, split at the first `:`, the prefix is required, polyforge#175) |
| `steps` | []Step | required | non-empty, `id` unique; **the array order is the sole execution order** |

There is no workflow-level `budget`.

Step element fields — the twelve keys the driver parses (`extStep` in `internal/polyforge/driver/workflow.go`); every other key is silently ignored (including `kind`, `interactive`, `tools`, `inputs`, `silence_minutes`, `tool_minutes`):

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | required | non-empty, unique; binds `steps/<id>.md` and is also the key of `.polyforge.yaml` `steps.<project>.<step-id>.models` (a same-named step shares one key across bundles) |
| `gate` | bool | default false | this step produces a business judgement |
| `requires_human_answer` | bool \| `if_asked` | default false | human gate (§2.1): with `true`, a completed / gate_failed envelope without a human answer is rejected (repo review 2026-10-16 V-8) |
| `requires_command_evidence` | bool | default false | a completed result must carry `command_evidence` (§4.4a; there is no implicit rule by step id — the delivery bundles' `verification` declares it explicitly, ruling G10 of 2026-10-16) |
| `mechanical_fix` | bool | default false | **verification step entries only** (polyforge#260): arms the mechanical fast lane — an armed lane's all-static verification FAIL may carry a mechanical classification (`mechanical_bound` in the verdict output: one entry per failed check, its repo, its exact command and the files it named) and rewind cheaply (uncharged: no edge slot, `max_total` only; a light re-entry of the target resuming its previous session, one light recheck bounded to the failed commands, fail-closed escalation to the existing full verification). Absent = off: every fast-lane branch in the driver is gated on it, and an unarmed lane's FAIL rewinds exactly as today. Shipped armed in feature-full only |
| `plan_conformance` | bool | default false | **verification step entries only**: the verification prompt receives the driver-computed plan-conformance facts section (see "Plan-conformance facts" in §4.4) beside `review`, which receives it on every lane with a done `plan` step. Shipped on chore only |
| `on_fail` | `{target}` | only with `gate: true` | `target` is an earlier step id — declaring it is the rewind edge; not declaring it means `failed_gate` terminates (§6.2). The FAIL verdict's full text is delivered to the target unconditionally |
| `context_policy` | string | default `inherit` | `inherit`\|`fresh` (§4.4a); a `gate: true` step must be `fresh` |
| `handoff` | bool | default false | this step writes the handoff file `artifacts/handoff-<step-id>.md` (§4.4a); the default is false, so do not write `handoff: false` |
| `recall` | bool | default false | the step's prompt carries the project-memory recall duty (`workflows/_shared/memory.md`); the shipped lanes declare it on the decision/authoring steps (grill, spec, plan, repro, root-cause, e2e-author, code, fix), never on review, verification, deliver, grill-review or the release lane. The workflow's last step carries the wrap-summary duty (`memory-wrap.md`) independently of it |
| `budget.wall_minutes` | int | optional | a run-time **estimate**: T = max(3 × wall_minutes, `--step-timeout`) (§6.6) |
| `model_candidates` | []string | optional | overrides `defaults` (replaced whole, not merged); may span harnesses, and switching to a candidate on another harness opens a new session carrying the old transcript as read-only reference — continued in place when the capsule tree hash matches the hash recorded on the step's latest failed attempt **and the dispatch runs on the same claim (a re-claim keeps the from-scratch reference)**, except in a rewound round of the lane's build step when the retry's task-repo (`repos/**`) tree still equals the tree the rewinding gate judged (`judged_repo_hash`) — no code progress, so the from-scratch reference stays beside the FAIL verdict ( criterion 5; an unknown judged hash or a repos-hash error keeps the wording here) — else from scratch |
| `vars` | map[string]string | optional | fills the `{{name}}` placeholders in this step's definition file (§4.4 "step variables"); the lane differences of a shared step text are declared only here |

The frontmatter declares no inter-step input wiring, no `cwd` and no ordering key: upstream artifacts land in the capsule's `artifacts/` and in `execution.json`'s `steps.<id>.output`, a downstream step's instructions read them by path convention; the step process's cwd is always the capsule root.

**Load-time validation (the code is authoritative)**: AIHub does not parse the frontmatter when creating a WI. Before claiming, the daemon first runs a candidate check on the local checkout's bundle (`common/workflow.CheckCandidates`: a candidate without a prefix, a `harness` key, or broken YAML → `DAEMON-414`, the WI stays queued; auto-pull skips that bundle). Structural validation runs when the worker machine's driver loads the materialized bundle (`LoadWorkflow` → `validateWorkflow`); any rule failing → that workflow fails to load and the WI is not dispatched; the error names the step and the problem, without a rule number or error code. Reading is lenient: unknown keys are ignored.

| Rule | Content |
|---|---|
| V2 | `steps` non-empty; every step has a non-empty, unique `id` |
| V3 | the array order is the sole execution order (guaranteed structurally, no separate check) |
| V5 | `on_fail` appears only on a `gate: true` step; `target` exists and its array position is strictly earlier than this step |
| V11 | `context_policy` ∈ `inherit`\|`fresh`; `gate: true` must be `fresh` |
| V12 | `mechanical_fix` appears only on the `verification` step entry (polyforge#261) |
| V13 | `plan_conformance` appears only on the `verification` step entry |

Also: `requires_human_answer` accepts only `true`/`false`/`if_asked`; candidates are validated by `harness.ParseCandidate` when the driver is built (`driver/driver.go`). Deleted rule numbers (V1, V4, V6–V10) are not reused; the result envelope's "V4 command-evidence gate" is unrelated to them and remains in force.

### 4.2 The reference flow (review may sit at any position) <!-- §4.2 -->

The `steps` order of the reference bundle `feature-full` (`workflows/feature-full/`):

1. `grill` (not a gate; feature-full does not declare `requires_human_answer`, autopilot's grill declares `if_asked`)
2. `spec` (consumes `grill`'s Q&A record)
3. `grill-review` (`requires_human_answer: true`, `gate: true`; `on_fail: {target: spec}`)
4. `plan` (maps every deliverable it demands from a later step to the step contract that carries it — `## Deliverables and carriers`; a deliverable no step contract carries is excluded with a stated reason or raised to the owner with `needs_input`, never promised;; an owner presentation is declared with an `owner-review:` line and carried by deliver's owner-review gate,)
5. `e2e-author` (`requires_command_evidence: true`; writes acceptance scenarios for the new behavior only, commits them, and runs only the author's files against the pre-implementation tree to prove them red scenario by scenario at the assertion level; outputs `baseline[]`; a baseline whose every row is `pass` is not accepted — the driver parks `e2e_all_green` with the answers `rewind-to-spec` (an owner-routed rewind of `[spec, e2e-author]`), `skip` (e2e-author re-dispatched fresh, records the owner's rationale verbatim in `artifacts/grill-qa.md` and completes skipped: the named discipline-① exception) and `cancel`; the mode's one audit anchor is `artifacts/grill-qa.md`, never `plan`'s restatement)
6. `code` (continues `e2e-author` through the inherit handoff)
7. `review` (`gate: true`; reads the complete diff (the test commits included) and judges design fit and quality — it runs BEFORE verification and never reads a verification report; a re-entry also reads the latest verdict-bearing prior round's archived findings list (§6.2); `on_fail: {target: code}`)
8. `verification` (`gate: true`, `requires_command_evidence: true`; the full test bar + the authored scenarios' per-scenario results, on the tree review already passed merged with the latest origin default branch, using the scope review recorded on the scoped tier; `on_fail: {target: code}`)
9. `deliver` (`gate: true`, `requires_command_evidence: true`; merge, push the feature branch, PR; a declared `owner-review:` artifact is shown in a `deliver-owner-review` question before any PR merge and the merge waits for the owner's approval answer — no declaration, no question; `on_fail: {target: code}`; the file is at `_shared/steps/deliver.md`; answer sets: `deliver-merge` offers merge / don't merge / back to code (plus the full re-verification answer on a scoped delivery) and, for an already-merged repo, `acknowledge` / back to code — `acknowledge` completes `merged: true` once the merge contains the verified head; a MERGED PR followed by back to code gets exactly one follow-up PR, an OPEN PR is reused)

The delivery bundles feature-full / bug-fix / chore uniformly end with `… → review → verification → deliver` (the judgment first, so a quality failure never costs a full machine bar); autopilot is `grill → fix → verification → deliver` (no review). The flow-level `rewind`: `max_total: 9`, `max_per_step: 3` — the per-step bound is charged per gate→target edge, the global cap counts every rewind.

**Release is its own bundle (ruling of 2026-10-13)**: the delivery bundles carry no `release` slot; release and deploy go only through the project-agnostic `workflows/release/` bundle, submitted as a separate WI. Three steps: `release` (`gate: true`: inside the capsule fetch and reset to the origin default branch head, record the remote tags before the release, probe whether `.polyforge/release.sh` supports `--verify`, run `.polyforge/release.sh [bump]`; the owner = the repo carrying `.polyforge/release.sh`: zero → FAIL, exactly one → execute, ≥2 → FAIL `PF-RELEASE-AMBIGUOUS_OWNER`) → `verify` (`gate: true`, fresh context: the release commit against the origin head, the new tag exists and points at the release commit, every pre-release tag unchanged, the release notes non-empty, finally `release.sh --verify <version>`) → `deploy` (`gate: true`: deploys only the version verify wrote to `artifacts/verified-version.json`; the owner = the repo carrying `.polyforge/deploy.sh`, zero → `defer`, ≥2 → FAIL; runs `.polyforge/deploy.sh <v> --confirm <v>`, rollback = step FAIL). All three steps are `requires_command_evidence: true` and none declares `on_fail` (a failure is `failed_gate`; a published tag/release/image is immutable, and a re-release is a separate WI filed by a human). The verdict vocabulary is bound mechanically by the driver (`driver/result.go`): `release` is `[pass, fail]` (pass must carry a non-empty `version` and at least one `artifacts_published`), `deploy` is `[pass, defer, fail]` (pass must carry a non-empty `version`). The defence lives inside `.polyforge/deploy.sh`: `--confirm <version>`, a server-side lock, automatic rollback on failure. A re-dispatched `release` adopts a published tag only under three conditions — the tag on `origin_head`, this capsule's `artifacts/pre-release-tags.txt` present, the tag absent from it — writing the release record with `notes` = the published release page URL (`verify`'s check (d) reads it) and passing; otherwise it refuses `PF-RELEASE-ALREADY_RELEASED` as before.

Key points:

- Data flow between steps is not in the structural schema: upstream artifacts are read by path convention (e.g. grill's `artifacts/grill-qa.md` is consumed by `spec` and `grill-review`).
- The positions of `grill`, `grill-review` and `review` are all expressed by the array order and are not validated.
- When `grill-review` FAILs with target `spec`, the FAIL verdict's full text is sent back with the target step's input, reusing §6.2, introducing no new state.

### 4.3 The two-phase behavior of grill <!-- §4.3 -->

1. **`grill`** (before spec): asks about the vague requirement item by item, not a gate; the Q&A record is written to the capsule's `artifacts/grill-qa.md`.
2. **`grill-review`** (after spec): one summarizing confirmation of the spec, `requires_human_answer: true` and `gate: true`; PASS advances to `plan`; FAIL triggers `on_fail: {target: spec}`, and the Q&A is appended to the same `artifacts/grill-qa.md`.

The driving engine does not distinguish the source of a verdict: a `grill-review` FAIL takes the same path as the other gates. **The interaction channel**: a step asks with a `needs_input` result, the driver writes the question into `execution.json`'s `steps.<id>.pending_question`; a human answers through `pf answer` → the daemon's `POST /jobs/{wi}/answer` → the driver, and the driver resumes the same step in place (`reference.md#§7.3`, `v2-converge.md#§3`). An agent must not answer on a human's behalf: the daemon refuses an answer request that comes from a step process tree (DAEMON-403).

### 4.4 The step definition file <!-- §4.4 -->

```
workflows/<bundle-name>/
├── workflow.md            # required: frontmatter (structure) + body (flow-level prose)
└── steps/
    └── <step-id>.md       # one per step; file name = step id
workflows/_shared/
├── principles.md          # generic engineering principles: rendered by {{principles}} into the grill/spec/plan/code-like steps, review, and the long-run repro/e2e-author/deliver/release-verify steps
├── <name>.md              # shared fragments: blocks several step files repeat, included by {{<name>}} (no vars entry;)
└── steps/
    └── <step-id>.md       # step definitions shared by several bundles (deliver.md, verification.md, review.md)
```

Each `steps/<step-id>.md` = frontmatter (metadata) + a Markdown body (execution instructions); the driver reads it directly from the materialized bundle (`driver/spawn.go`, `driver/outputschema.go`).

**Shared step definitions (ruling G1 of 2026-10-16)**: the lookup order is decided by `workflow.StepDefinitionPath` — the bundle's own `steps/<id>.md` is used if it exists (it may override the shared version); otherwise it falls back to `workflows/_shared/steps/<id>.md`. `_shared` is not a bundle (it has no `workflow.md`), and materialization copies the whole directory into the capsule's `workflows/_shared/`. Do not share through symlinks: the materializing `copyTree` skips symlinks. A step file that several bundles have verbatim identical must go into `_shared` (guarded by `driver/shared_steps_test.go`).

**Step variables (follow-up to ruling G1, 2026-10-16)**: a step whose lanes differ in only a few facts (the rewind target, artifact names, lane-specific checks) is also written as one shared text, the differences written as `{{name}}` placeholders and filled by the `vars:` of that step's entry in workflow.md (`common/workflow.RenderStepVars`; `name` matches `[a-z][a-z0-9_]*`). There are only three rules: rendering applies to the whole definition file (the frontmatter's `output` schema and the body are both rendered, and `readStepDefinition` and `loadStepOutputSchema` read the same rendered result); values are inserted verbatim (the trailing newline of a YAML block scalar is removed) and never expanded a second time; both directions fail closed — a placeholder used in the file but neither declared nor backed by a fragment file, and a variable declared but never used, are both errors (the step definition is unreadable at dispatch, and the schema records `output_schema_unloadable`; `TestShippedStepDefinitionsResolve` guards every shipped bundle). A difference that can be expressed in neutral wording does not get a variable. A literal `{{name}}` has no escape; variable values are inserted verbatim (on a schema line that is unquoted YAML), the bundle is treated as trusted and guarded by tests (`TestShippedStepOutputSchemasCompile`, `TestShippedStepDefinitionsResolve`). The shipped `verification` (`output_required`, `build_step`, `position`, `lane_checks`, `never_pre_existing`) and `review` (`build_step`, `scope_source`, `intro`, `judge`) are shared this way; `TestSharedStepPromptsKeepLaneFacts` dispatches bundle by bundle and checks that every lane fact is still in the prompt and that no other lane's fact is mixed in. The delivery and release notes in the workflow.md body are likewise reduced to one paragraph pointing at `_shared/steps/deliver.md`, the "Delivery and releases".

**Shared fragments**: a block several step files repeat verbatim (the per-unit fast-check bar, the grill batch-question table, the handoff duty, the plan's deliverable-carrier check `deliverable_carrier`, the plan and build steps' owner-review declaration `owner_review`) lives once as `workflows/_shared/<name>.md`, and every step file includes it with `{{<name>}}` — the `{{principles}}` include generalized: no `vars` entry declares it, `workflow.ReadStepDefinition` renders the fragment's trimmed text verbatim (never re-scanned, so a fragment cannot inject placeholders), a declared var that shadows a fragment file is a load error, and a placeholder with neither a var nor a fragment file fails closed. A definition that does not include a fragment never reads it (an old capsule from before materialization runs as usual). A fragment is lane-neutral: no bundle, project or repo name is hardcoded in one.

**Rare-path sections rendered by the driver**: material only one dispatch shape needs is not in the step body but in a `workflows/_shared/<name>.md` section file the driver reads on that shape alone and renders as its own prompt section (the `mechanical-fix.md` pattern): `scoped_verification.md` — the scoped tier's rules — rides the `# Verification tier` section of a scoped verification dispatch only; `scoped_review.md` — review's `scope_adequate`/`scope` obligation — rides a review dispatch of a work item that opted into the scoped tier (keyed on the opt-in, like its validation, never on the recorded verification tier); `review_reentry.md` rides a review re-entry (below). A section file may name the step entry's vars (`{{build_step}}`), rendered like the body. A section that cannot render — unreadable, or a placeholder the step entry declares no var for — fails the dispatch closed (`driver: <bundle>/<step>: shared section <name>: …`), like a step definition's missing fragment ( W3); a MISSING file renders no section and writes that line to stderr — transition code for a capsule claimed before's release, whose snapshot carries the old static step text and no section file, deleted once no such capsule is in flight.

**Shared principles (polyforge#191)**: `workflows/_shared/principles.md` holds the engineering principles that hold for any project (simple, recoverable, least privilege, evidence, behavior decided by the owner), plus one requirement: before starting, a step reads the `AGENTS.md` (else `CLAUDE.md`) at the root of every repository under `repos/`, project rules bind equally and win on conflict, and the conflict is noted in the artifact. The full text exists only in this one copy: writing `{{principles}}` in a step definition file makes `workflow.ReadStepDefinition` render it as that file's content — it needs no declaration in `vars:` (the general shared-fragment rule above; a step entry declaring a variable of the same name is an error); a definition that does not use it does not read the file (an old capsule from before materialization runs as usual). Every step that uses it first writes, in a `## Principles` section, a paragraph on how this step uses the principles, then places `{{principles}}`. Shipped coverage: feature-full's `grill`, `spec`, `plan`, `code`; autopilot's `grill` (which also writes the memo, used as grill+spec) and `fix` (plan/code-like); bug-fix's `root-cause` (which gives guidance on the fix scope, used as plan-like + evidence) and `fix`; chore's `plan` and `code`; the shared `review` (every principle is a blocking check, the checklist expanded item by item); and the long-running steps that carry the waiting rule: bug-fix's `repro`, feature-full's `e2e-author`, the shared `deliver` (in every delivery lane) and release's `verify`. The waiting rule binds background work too: a shell `wait` is a wait like `sleep`, a step manufactures no artificial load on a shared host, and every background process it starts is killed by process group before the call returns. Each section is at most 2728 bytes (`driver/principles_test.go` guards the coverage, exactly-once and the byte cap). A rule that holds for only one repository does not go into `workflows/` but into that repository's own `AGENTS.md` — polyforge's own (backward-compatibility code, the reachability statement for new daemon/aihub entry points and so on) is in this repository's root `AGENTS.md`, and `CLAUDE.md` is just one line `@AGENTS.md` (Claude Code reads it via import; pi loads only the first `AGENTS.md`/`CLAUDE.md` existing in each directory, which is the `AGENTS.md`).

Frontmatter fields — **the driver reads only `output`**:

| Field | Category | Notes |
|---|---|---|
| `name` / `description` | by convention | not parsed |
| `output` | optional, the only key read | a draft-07 JSON Schema (written in YAML): injected into the dispatch prompt (placed before the body) and used by the driver to validate a completed result's `output` (an optional property whose value is `null` is treated as default). A `properties` entry may carry `x-prompt-when: scoped\|armed\|authored\|reentry`: validation keeps the full schema, the prompt drops the entry on a dispatch where the condition does not hold and never shows the marker; an unknown condition fails the load |
| `model` | forbidden | model selection lives only in the workflow.md frontmatter (INV-1g); `model` is not read |
| `tools` | deleted (G10) | never read; leftovers in old snapshots are ignored |

**The output contract (INV-1h)**: **enforced** for the release bundle's `release` and `deploy` steps (`outputSchemaEnforced` in `driver/outputschema.go`): a non-conforming result means the envelope is rejected (retried in the same process lane), not counted as an infrastructure failure and not advancing the candidate. Every other step is in **record-only mode**: a non-conforming result only records a durable `output_schema_violation` event, rejects no envelope, is not an infrastructure failure and does not advance the candidate. A schema that is declared but cannot be loaded records `output_schema_unloadable` and writes stderr; on `release`/`deploy`, a missing or unloadable schema means results are always rejected (the verdict contract lives in the schema). The `plan` step (chore, feature-full) stays record-only for its schema as a whole — enforcing it whole would refuse real plans for unrelated violations — but carries one dedicated, enforced contract (`checkPlanObligations` in `driver/planobligations.go`,): every `touched_files` entry with `write` intent owes `coupled_obligations`, a non-empty list of `{path, note?}` (the documents, tables and projection rules that must change with the file) or exactly one `{none: true, reason}`; a completed plan without it is an envelope rejection, so `code` never runs on it. Whether the listed obligations are the right ones stays `review`'s judgment.

**Plan-conformance facts (`driver/planconformance.go`)**: before a `review` dispatch on a lane with a done `plan` step, and before a `verification` dispatch whose entry declares `plan_conformance: true`, the driver compares the plan's declared set — its `write` entries, their `coupled_obligations`, the build step's `declared_extensions`, and the test files an earlier authoring step declared (`output.test_files`) and committed (feature-full's e2e-author, bug-fix's repro; declared by that step's own output, not the plan, so they are never changed-but-undeclared facts) — with each task repo's committed diff (`git diff --name-only --no-renames $(git merge-base HEAD <origin default>)..HEAD`, the default being `origin/HEAD`, else `origin/main`/`origin/master`; read outside the driver lock) and renders the result as the prompt section `# Plan conformance (driver-computed facts)`, every line carrying its owner-ruled severity: a changed file neither declared nor cited is **blocking**, a declared coupled obligation left unchanged is **blocking**, a declared plain write left unchanged is **non-blocking** — in every review round. A `declared_extensions` entry `{path, source, ref}` counts as declared only when a rewind record from that source's gate to the build step exists in `rewind_stats` and `ref` is well formed for it — `review` + a positional finding reference `s<n>#<k>`, `verification` + the FAIL dispatch `s<n>` (its fail_reason carries no finding id), `deliver` + the human answer's question id (the human's instruction declares the file outright); anything else is listed as not counted. The mirror `withdrawn_obligations` (`{path, source, ref}`, the same citation rule) withdraws a coupled obligation a cited finding made moot, and an obligation none of whose declaring writes is in the diff lapses by itself; both render as no longer owed (not blocking), while an uncited withdrawal of an obligation whose parent write is present withdraws nothing and stays blocking. The citations are cumulative over the build rounds since the plan: a fresh rewind resets the build step's live output, so the fold reads the `declared_extensions` of every build attempt archived (its `attempts[].result`) at or after the plan's acceptance plus the live output — a later round need not re-cite, the live entry wins for a path cited twice, and a citation from an archived round renders marked as carried over. `plan` is never re-run and is not a rewind target. When the base cannot be resolved or git fails, the section names the reason and computes no set difference (fail-open, said so). The facts are not persisted: each dispatch recomputes them.

### 4.4a Context passing between steps: `context_policy` and `handoff` (polyforge#147) <!-- §4.4a -->

Both context relations are declared by the step keys in the frontmatter, **and the semantics rest entirely on path convention, with no summary/manifest validation**:

- **`context_policy: inherit` (default)**: at dispatch the driver takes the **nearest earlier step that declared `handoff: true`** (it must already be done, else dispatch errors), reads the handoff body from `artifacts/handoff-<step-id>.md`, and splices it verbatim into this step's dispatch prompt (the "Handoff from step …" subsection); with no such upstream, or no such file, that subsection is simply missing, not a failure (`driver/spawn.go` `resolveHandoff`).
- **`context_policy: fresh`**: no handoff body is injected; upstream artifacts are fetched by path convention. A `gate: true` step is always `fresh` (enforced by the parser).
- **`handoff: true`** (declared only when some downstream inherit step has this step as its nearest handoff source; ruling G10 of 2026-10-16 deleted 7 declarations without a reader): this step must write `artifacts/handoff-<step-id>.md` before wrapping up.

**The result envelope is a minimal contract** — `outcome` + `output` (`needs_input` also carries `question_id` + `question`) plus the dispatch-identity fence, with no `handoff_ref`, no sha256, no artifacts manifest (`v2-converge.md#§2.6`). The driver's mechanical gates beyond the minimal contract: V4 command evidence (a completed result of a step declaring `requires_command_evidence: true` carries `command_evidence: [{argv, exit_code, duration_ms}]`, at least one entry, argv non-empty, `duration_ms > 0`, and the accepted evidence is written by the driver into `output.commands`); the committed-test-files gate (every path in `output.test_files` must be committed at HEAD of the task repo it lives in, polyforge#156); written tests are immutable (polyforge#164 H4); the `defer` verdict is allowed only on `deploy` (the remaining verdict rules of release/deploy are in the output schema they enforce). A violator's envelope is rejected, with the rejection reason, and retried in the same process; the 3rd consecutive rejection (`maxEnvelopeRejects` = 3) → the step is blocked `result_invalid`. The count is persisted on the step (with the ordinal it last counted), so a restart neither resets the bound nor counts a re-collected archived envelope twice. In addition: the needs_input question shape, the pre_existing-failure boundary, deliver binding, human-gate rejection, `fail_reason` being required for release/deploy and `defer` being legal only on deploy (`driver/result.go`, `driver/deliver.go`).

### 4.5 Bundle reference <!-- §4.5 -->

The bundle reference is the single scalar `bundle_name` (polyforge#149 B9 deleted the whole digest chain: no aggregate digest, no stand-in, no explicit pin accepted, and `internal/` has no `Digest`/`FileEntry`). The execution side materializes from the local checkout by `bundle_name` without content verification; a missing or drifted checkout is a configuration accident (a materialization warning, and execution continues).

## 6. Core flows <!-- §6 -->

### 6.1 The success path: sequential advance <!-- §6.1 -->

1. Execute one by one in the order of the `steps` array.
2. Each step's result is written atomically by the driver to the capsule's `runtime-state/execution.json` (structure in `Execution`/`Step` of `internal/common/capsule/capsule.go`); the supervisor's push loop pushes the capsule onto the aihub chain at every commit boundary (`reference.md#§8`).
3. At runtime there is no jumping and no reordering.

### 6.2 Business gate FAIL → a bounded on_fail rewind <!-- §6.2 -->

When a `gate: true` step produces FAIL (a `gate_failed` result, or completed with `verdict: fail` — the driver rebinds it to gate_failed) (`driver/transition.go` `applyGateFailLocked`):

1. No `on_fail` declared: the workflow terminates as `failed_gate`, and the verdict's full text is written to `execution.json`.
2. `on_fail: {target: X}` declared: classify first (a text-only light review FAIL, a mechanical verification FAIL, or a converging review round charges no edge slot), then check two kinds of bound — the cumulative automatic rewinds (charged or not; an owner-routed record — a deliver FAIL a human answered in its attempt chain, the review owner exit, the e2e-author/bug-fix owner answers — counts toward neither bound and no bound refuses it) have reached `rewind.max_total` (the omitted-block default derives min(4, #on_fail edges × max_per_step)), or this gate→target edge's CHARGED records have reached `rewind.max_per_step` (default 2) — either one hit terminates as `failed_rewind_exhausted`, and the rollback below is not performed. A rewind ledger that cannot attribute its own count (a pre-w69 shape with no per-record history) proves no quota: the next rewind fails closed with a durable event, no compat path.
3. Neither hit: `rewind_stats`'s cumulative count and the edge's record (`rewinds[]`: `{gate, to_step, class}`, `class` ∈ `charged`/`uncharged`/`owner`) are each incremented by one.
4. Each step in `[target, gate)`: its current result is archived as an attempt carrying `rewind_gate` (the id of the triggering gate) — the target itself as `cause: gate_fail_rewind`, the steps between the target and the gate (they did not fail, their output was merely invalidated by the later gate) as `cause: superseded_by_rewind`; the status is reset to `pending` and the output cleared (so downstream does not consume stale artifacts).
5. The current position is set back to the target; the FAIL verdict's full text is persisted as `steps.<target>.pending_rewind_input` for the WHOLE round: every dispatch of the round carries it — the first re-entry, a retry after an infra death (a model-class upstream error included), and a restart after a daemon death — and it is cleared only by the acceptance write that ends the round (or replaced by the next rewind/reset), so a retry can never lose the verdict. The dispatch SHAPE survives the crash window between the rewind write and the re-entry's spawn-journal line: a resume never crosses a rewind boundary. If a restart lands after the target's `step_start` but before the first new-round dispatch is journaled, the target re-enters fresh with the same persisted verdict (the light causes keep their resume and their note), a `superseded_by_rewind` step starts without resume, and the gate (item 6) re-enters fresh without a verdict.
6. The gate that triggered FAIL is itself not archived and stays `in_progress`, re-entering in fresh form with the cumulative T zeroed (`v2-converge.md#§2.4`); under the same crash-window rule as item 5 it never resumes the conversation that delivered the FAIL (the archive whose `rewind_gate` names it is its boundary).
7. Continue §6.1 from the target.

**No-progress resubmission guard**: a gate's verdict records the task-repo tree it judged (`steps.<gate>.judged_repo_hash`, driver-written in the same settlement write; the hash covers `repos/**` only, so driver-owned `artifacts/steps/` archives never move it). When that verdict was delivered is derived from the attempts ledger (the gate's newest accepted attempt, or the rewind archive naming it), not persisted a second time. The guard applies only when the rewind's target is the lane's BUILD step (the verification entry's `build_step` var, else its `on_fail` target — never a hard-coded step id); a rewind of an artifact-producing target (spec, repro, the deliver override that re-runs verification at full through `rewind_to: verification`) may legitimately change its artifact on an identical repos tree and is left alone. Two consequences follow. First, a retry inside such a rewound round whose current task-repo tree still equals that judged tree made no code progress, so the continue-in-place wording is suppressed: its prompt keeps the from-scratch reference beside the FAIL verdict. Second, once the rewound build step has delivered an accepted result that leaves that identical tree — whether or not an attempt crashed on the way ( D3: re-judging an identical tree can only repeat the verdict or pass by chance) — a gate re-entry over it is not dispatched at all: verification does not re-run, review does not re-judge, and no further rewind slot is charged. A metadata-only plan-conformance repair is the exception: the guard recomputes the facts the gate last judged — the same diff, folding the build round the FAIL's rewind archived as the live output and the older archives as carried — and re-runs the gate on the same tree only when those judged facts carried a blocking entry (a changed-but-undeclared file or an unchanged coupled obligation) and the gate's current recomputed facts carry none; the input the gate would judge did change even though the tree did not, and the metadata-only round charges no rewind slot (a fact that still blocks, or facts the gate already judged clean, keeps the park). A live `declared_extensions` citation is not the test: the list is cumulative across rounds, so a later no-change round re-emits the same citation. The driver parks the workflow `blocked` with a `blocked_reason` stating that the build round produced no change, naming the gate that is not re-run, the rewinding gate and its verdict round, a bounded one-line excerpt of the build step's own `summary` (why it changed nothing), and — when an `infra_failure` attempt was archived after the rewind — the crashed build attempt; the owner's `pf resume` is the explicit override (it clears the gate steps' judged trees, so the resumed gate tail may run once on the same tree). The light recheck and its in-place escalation are exempt: they are the designed same-tree fast lanes (polyforge#260). The full verification after a light recheck that a fresh re-derivation abandoned is not ( S2): its `light_recheck_escalated` audit record carries `abandoned: true`, and a fresh build round came between. A light rewind (text-only, mechanical) is not: its re-entered build step resumes in order to change the tree, so a resumed round that changed nothing parks like any other, unless that round is the metadata-only conformance repair above.

**Light rewind (polyforge#222, a sub-form of the sequence above)**: when a `review` gate's FAIL has all of its recorded blocking findings (at least one) carrying `text_only: true`, the same atomic write takes the light path — the bounds are checked first (item 2: the light rewind charges no edge slot, so only `max_total` can refuse it) and the rewind is counted (item 3: the cumulative count rises, the edge's record is written `class: uncharged` — a later `needs_code_change` self-report flips it, below), the target is archived as `cause: gate_fail_rewind_text_only`, and the verdict's full text is delivered to the target together with the light re-entry note (the `Note` of `pending_rewind_input`); the target's re-dispatch resumes its previous session (same harness, same session identity) instead of re-deriving in full — the resume instruction is not written a second time but derived from the ledger that same write already persisted (the target is pending and its last non-`infra_failure` archived attempt is the light cause — the same fact the `needs_code_change` self-report validation reads); when a resume is impossible (a different harness, or the native session/transcript no longer exists) it degrades to today's fresh-plus-read-only-reference rollback, within the same rewind, with the spawn journal recording `resume: false`. A light re-entry's completed result may carry `needs_code_change: true` (a self-report of a structural fix; without the light context, or with a non-boolean value, it is rejected): the same write archives the target as `gate_fail_rewind`, resets it to pending, and delivers the same FAIL verdict as the input of a fresh re-entry, taking no further slot (a misclassification is not charged twice) but charging the light rewind's gate→target edge once (the edge bound is checked first and a spent edge ends `failed_rewind_exhausted`; otherwise the light record flips to charged, with no new record and no new `max_total` count — the fresh round is an ordinary one, and without the charge a light → self-report → fresh → light loop was stopped only by `max_total`). The gate itself still re-enters fresh (item 6 unchanged).

**The reserved cancel answer**: every question the driver persists (a step's `needs_input` or a driver-authored one) ends with the one sentence ``Answer `cancel` (the whole answer, ignoring case and surrounding whitespace) to abandon this work item.``, appended in the write that persists it. The daemon's answer route authorizes that answer at the hub (a dry-run of the cancel door with its own credential — the `pf cancel` gate, never `--by`) before relaying it; the answer's write archives it, records `cancel_requested` and parks the workflow `blocked`; the runtime's blocked close then cancels the work item through the hub's existing door, the verbatim answer on the `work_item_canceled` event. No routing, ruling or wrap follows. The door is called whenever that blocked close settles (at once, on a restart's end_pending replay, or with its answer lost); a cancel that still does not land (a crash between the settled close and the door, a hub refusal) leaves the work item blocked with `blocked_reason` naming the request — `pf cancel` finishes it, and the owner's resume drops `cancel_requested`.

**The fix→root-cause rewind (bug-fix)**: a COMPLETED `fix` result carrying `root_cause_addressed: false` (the literal boolean) on a workflow that declares a `root-cause` step before `fix` is routed in its own result write, before acceptance and before the light `needs_code_change` self-report is judged (`applyRootCauseFalseLocked`, `driver/transition.go`). With no `fix → root-cause` record in `rewind_stats.rewinds`, the driver archives `root-cause` as `cause: root_cause_unaddressed` (`rewind_gate: fix`), resets it, moves the position to it, appends one charged `{gate: fix, to_step: root-cause}` record (the global count increments; neither bound refuses this one rewind — once is stricter than the edge bound, and the spec makes the first false unconditional) and routes the fix's `summary` as root-cause's `pending_rewind_input`; `fix` stays `in_progress` holding its false report (the gate-holds-its-verdict shape) and re-dispatches fresh after the new diagnosis. Root-cause's own `on_fail: repro` is untouched. With that record already present, nothing rewinds: a driver-authored `pending_question` (`root_cause_false`) asks the owner to continue with corrective guidance or cancel and re-file, the `needs_input` event notifies, and the answer re-dispatches `fix` in place (D9) — this path never reaches `failed_rewind_exhausted`. The once-only memory is the per-edge ledger itself; no new state. A false report owes no commit (an empty `commits` list is legal only with the literal `false`; a completed `fix` claiming `true` with no commit is rejected at validation, and re-listing an earlier attempt's commits stays forbidden). A lane without an earlier `root-cause` step (autopilot) accepts the false report as before. **The bug-fix dead ends (siblings of `root_cause_false`)**: a completed `repro` reporting the literal `reproduces: false` is not accepted — it stays on the step and the driver-authored question `repro_not_reproduced` parks the loop; and a `root-cause` FAIL on an edge that already carries a root-cause→repro record does not rewind again — `root_cause_inconclusive` parks the gate. Both offer `re-run-repro: <evidence>` (repro re-runs with it: in place, or an owner-routed rewind from root-cause), `continue: <guidance>` (repro: the held report is accepted and the lane moves on, the verbatim answer riding root-cause's next dispatch as its `pending_rewind_input`; root-cause: the gate re-runs in place with the guidance) and `cancel`; any other answer is asked again; neither ever reaches `failed_rewind_exhausted`. The first accepted `repro` records the task-repo heads it ran on (`pre_fix_heads`); after a fix→root-cause record exists, every rewind input to `repro` carries the note naming that pre-fix base, so the reproduction never runs on the mitigated tree.

**Mechanical light rewind (polyforge#260, the second light cause)**: when a `verification` gate's FAIL — on a lane whose verification step entry declares `mechanical_fix: true` — carries a mechanical classification (`mechanical_bound` in the verdict output: one entry per failed check — its repo, its exact command and the files it named; the classification is the verification agent's own verdict field, instructed by the shared material `workflows/_shared/mechanical-fix.md` the armed prompt renders — the driver classifies nothing and judges staticness nowhere), the same atomic write takes the mechanical light path: the bounds are checked first and the rewind counted exactly like the text-only light rewind (uncharged: only `max_total` can refuse it, the edge record `class: uncharged` until a self-report flips it), the target is archived as `cause: gate_fail_rewind_mechanical`, the verdict routes with the mechanical light re-entry note (fix only inside the bound — modifications of bound-named files, ≤ 40 changed lines and ≤ 5 files summed across repos, hard-coded — or self-report `needs_code_change: true`), and the gate additionally records the pending light recheck marker `steps.<gate>.pending_light_recheck` (the bound copied verbatim from the verdict's own classification + each task repo's HEAD at the FAIL settlement as the repair-diff base, driver-recorded, never step-supplied). The target's re-dispatch resumes its previous session exactly like #222's light rewind (the same ledger-cause derivation; the same `needs_code_change` self-report fresh rewind reusing the slot and charging the edge once — which also clears the marker in the same write: the self-report's fresh rewind abandons the light path), and the marker is cleared by every rewind-range reset (a reset step never carries a stale one) and by every other write that opens a fresh re-derivation of the build step a fresh (non-light) gate FAIL whose range does not reach verification (a structural review FAIL, now that review runs first), a light re-entry's `needs_code_change` self-report whichever light cause rewound it, and the fix's first `root_cause_addressed: false` — which archives the escalation's audit-only `light_recheck_escalated` attempt on verification and emits one `light_recheck_escalated` event, so the next verification is the escalated full re-run, never a light recheck over a fresh re-derivation.

**The light recheck (polyforge#260)**: the marker present makes the verification step's next dispatch a light recheck — a fresh conversation whose prompt carries the light section (the bound commands per repo + the shared light contract + the light output schema, all from `workflows/_shared/mechanical-fix.md`) beside the untouched step definition, still under the command-evidence gate. Before it dispatches, the driver validates the bound's coverage (every check the FAIL verdict recorded `fail` covered by exactly one entry, each command and file list non-empty, each repo a declared task repo) and measures the repair diff deterministically (per repo: every changed path a modification of a bound-named file — any add, delete or rename breaks it — the numstat lines and file counts summed across repos against the hard-coded 40/5); a malformed classification or a broken bound escalates IN PLACE: the `light_recheck_escalate` write archives an audit-only `light_recheck_escalated` attempt with the reason in `detail` and the audit facts in `result` (the bound, the diff base, the measured diff, the recheck's own record, `escalated: true` — archived before the same write clears the marker, because the full re-run's own output never carries them), clears the marker and orders the next dispatch fresh — no rewind slot, no rewind input — so the loop re-dispatches the step in full mode (the existing full verification, unchanged, its prompt carrying the escalation note — the shared material's `Escalated full re-run (the mechanical fast lane)` section, `workflows/_shared/mechanical-fix.md`: it owes the fast-lane section of `artifacts/verification-report.md` that the light recheck never settled to write, beside the untouched classification duty). A light recheck that does not pass (its own FAIL verdict, or a completed claim whose command evidence does not show every bound command run with exit 0 in its repo — the test-bar re-run machinery, mechanical never semantic) escalates in the result's own settlement write the same way, and the escalation emits one `light_recheck_escalated` event with the reason — never a `rewind` event (the escalation charges no slot and routes no verdict). A light pass settles in the same write: `mechanical_pass` on the verification output (the bound, the measured diff, the recheck commands and results, the recheck heads, `escalated: false`), the FAIL verdict's own `test_bar` carried verbatim (the driver copies it — the step agent never re-transcribes it), and NO `verified_heads` (a head verified only by a light recheck is never tests-covered). Both the escalation and the light pass ride the existing single atomic write; an interrupted light recheck re-dispatches and replays idempotently (deterministic commands plus the deterministic diff check — the marker is the mode switch on both sides, dispatch and settlement).

**The light-pass handover (polyforge#260)**: a light-passed workflow carries no verified head, so deliver's tests-covered guarantee rests entirely on the merge dispatch's recorded re-run of the carried `test_bar` — unconditional, no head-equality shortcut — and the hand-made-history walk anchors on the light record's `recheck_heads` (the repair range `diff_base..recheck_head` is covered strictly by the driver's modifications-only/caps check — an anchor replacement, not a weakening). A repo with no carried `test_bar` entry keeps today's rule: a human decides. Review runs in full before verification either way (the lane order is build → review → verification; review never reads the report); #222's review text_only tail is unchanged.

**Review re-entry (quota semantics by)**: every review gate keeps `context_policy: fresh` — the prior reviewer's conversation is never inherited — but a re-entry additionally reads the latest prior round's **structured findings list** from its archive (`artifacts/steps/review/s<n>/result.json`, the R14 staging copy every collected envelope already leaves there; only the verdict-bearing archives count — `output.verdict` `pass` or `fail` under `outcome: completed` or `gate_failed`; a `completed` + `verdict: fail` review is re-bound by the driver to a gate FAIL and IS verdict-bearing, while a `needs_input`/`incomplete` archive judged nothing and is never the prior round, N1). Two additive faces then run over the current tree: the **checklist face** verifies each prior finding's disposition (fixed, or waived with an owner ruling on record) — a still-present prior **blocking** finding is a **residual**, reported `blocking` and referenced by its position in that round's findings list (`residual_of`, the schema marker the driver's quota accounting reads), explicitly without re-deriving it as a new finding, while a still-present non-blocking finding stays `non-blocking` and never fails the gate; the **fresh face** is the existing full judgment, now including the fixes' new surface (the branch's own first-parent, non-merge commits since the last verdict round's recorded heads — `steps.review.last_review_round.heads`, written for every verdict-bearing round —, per repo `git log --first-parent --no-merges <head>..HEAD`, and their semantic propagation; never `git diff <head>..HEAD`, which after a passed round also carries the upstream changes verification's or deliver's machine-made `git merge --no-edit origin/<default>` brought in,), and genuinely new defects stay new findings. A **first round** (no verdict-bearing archive) is exactly the existing behaviour. Since the re-entry text (the two faces, the round contract below and the light-round mis-marking duty) lives in `workflows/_shared/review_reentry.md` and the driver renders it as the `# Review re-entry` prompt section only on a review dispatch whose `steps.review.last_review_round` is on record (`StepSpawn.ReviewReentry`) — a first round's prompt carries none of it; the shared review body keeps a one-line pointer and the text-only boundary's single definition. The round contract (owner ruling): from the second round on only residuals, new discoveries on the fix surface, true bugs (correctness/security/data/concurrency) anywhere and violations of the project's own rules (its `AGENTS.md`) anywhere block — everything else is a `non-blocking` follow-up `deliver` summarizes (no step ever files a ticket). The verdict-bearing rounds record their facts (`steps.review.last_review_round`: the round ordinal, its blocking count and the heads it judged, written in the settlement's own atomic write; needs_input/incomplete rounds move nothing), and a FAIL whose blocking findings are all residuals and strictly fewer than the last verdict round's is a **converging round** — it charges no edge slot, only `max_total` (fail-closed: a missing baseline, an unmarked finding or a non-decreasing count keeps the rewind charged). Every blocking finding also carries a machine-readable `repair_target` (`code` — every repair the build step can make in its own round, including updating a declared obligation the diff left unchanged, withdrawing a moot one and citing an undeclared file — or an off-graph class: `authored-suite`, `spec`, `declared-obligation` (reserved for an obligation that is itself wrong and that the build step can neither satisfy nor withdraw), `instruction`; a missing class is an unfilled result the driver rejects); a residual re-emits its class, and the convergence count holds the `code` findings alone — off-graph findings ride along a mixed FAIL's rewind uncounted. **Review owner exit**: a review FAIL whose blocking findings (at least one) are all off-graph (`repair_target` ≠ `code`) is not rewound — the settlement write parks the driver-authored `needs_input` question `review_owner_exit` on the gate (its context lists each blocking finding's `s<n>#<k>` reference and class) and spends no slot; the answer's own write routes it: `amend-upstream` records the ruling (`steps.review.owner_rulings[]`, the machine copy) and rewinds, owner-routed (`class: owner`), to the authoring step for a suite gap (its rewind note orders append-only) or else to the build step, with the ruling as the target's `pending_rewind_input` — `spec` and `plan` never re-run; `waive` records exactly the well-formed references it names (none = asked again) and re-runs review; `cancel` is the reserved answer; any other answer is asked again. After the write the driver appends each ruling verbatim, once (keyed on question id + answer stamp, re-checked at every Run start), to `artifacts/grill-qa.md`'s `## Owner rulings` — the one landing point review re-entry and the build step read. A review re-entry an amend-upstream ruling opened is exempt from the unchanged-tree guard (the ruling is new gate input).

**The candidate pointer is reset in a rewind** (INV-1g): a reset step reruns from the first item of the candidate list; no gate-FAIL path switches candidates. The bounds are configurable in the frontmatter (a bound ≤0 falls back like an omitted one — `max_total` derives `min(4, #on_fail edges × max_per_step)`, `max_per_step` falls back to 2 — so a rewind cannot be turned off with 0), and reaching a bound terminates — there is no third path of "continue after human authorization", and what follows can only be a decision at the WI level (`pf cancel`, then open a new WI).

### 6.3 Infrastructure failure → in-place retry of the current step (bounded candidate switching by cause of death) <!-- §6.3 -->

1. Judgement: every failure that produced no business verdict (process death, exit without a result, timeout, harness silence, rate limiting, a transient upstream error, a host error), judged dead by the supervisor or found by the driver while waiting for the result; the cause classification and handling table are in `v2-converge.md#§2.3`.
2. Handling (one atomic write, `TransStepFailed`): the step stays `in_progress`, a record with `cause: infra_failure` (carrying `failure_cause` plus `tree_hash`, the capsule tree hash at archive time — live and `daemon_restart` — which a new-conversation re-dispatch compares against the current tree) is appended to `steps.<id>.attempts[]`, the failure count and the relaxed thresholds are updated, and the next dispatch form is written. In a rewound round of the lane's build step the fast path is additionally suppressed when the retry's task-repo tree still equals the tree the rewinding gate judged (`judged_repo_hash`): there was no code progress to continue ( criterion 5).
3. Re-dispatch the same step in place, never skipping and never rolling back; a step already done is never rerun.
4. **Candidate switching** (`driver/candidates.go`): the effective list is obtained by the priority of `reference.md#§7.5`; the pointer = the number of `infra_failure` entries with a model-class cause of death (`model_error`, `model_hung`, `step_timeout_slow_model`, `exit_model_class`; a `model_error` advances only as the second consecutive model-class death on its candidate — the first resumes it) after the last rewind archive (`gate_fail_rewind`, `gate_fail_rewind_text_only`, `gate_fail_rewind_mechanical` or `superseded_by_rewind`), capped at the last position — it depends only on `execution.json` and is recomputed identically after crash recovery. A host-class cause of death blocks the step without advancing; the other causes (`rate_limited` and `upstream_transient` within its bound included) retry on the same model. After the candidates run out the pointer stays at the last one.
5. Counted failures reaching the cap (`DefaultMaxStepFailures` = 3) → the step is blocked; the count is **per candidate**: it is zeroed on switching to a new candidate; `rate_limited` and `upstream_transient` within its bound are not counted (for the latter, after 2 consecutive occurrences the 3rd is classified as `exit_model_class` and switches candidate); consecutive `model_error` / `upstream_transient` / `ended_without_result` deaths on one candidate wait 1m, 3m, then 9m before a re-dispatch of that candidate — a switch dispatches at once and the next candidate's ladder starts at 1m — derived from the attempts archive (v2-converge §2.3 retry pacing); an interruption caused by a daemon restart is not counted as a failure and does not advance the pointer (`driver/supervision.go`). A gate's own FAIL verdict closes the round it judged: the rewind resets the gate's failure count and long-task timeouts, so its re-entry starts a fresh failure window (the same reset its target gets).

### 6.3b The two-way split of archived attempts (cause semantics) <!-- §6.3b -->

The non-accepted records of `steps.<id>.attempts[]` fall into two lanes, told apart by `cause` and mutually exclusive (there is also one non-failure kind of record: each accepted completed result appends one `cause: accepted`, `driver/transition.go`, used by the recovery engine's progress ledger and the candidate-pointer recomputation):

1. **Rewind archive**: appended by §6.2 item 4 — the archive of the business lane, after which the step is reset to `pending`. A rewind's target is recorded as **`gate_fail_rewind`**, the target of a text-only light rewind (§6.2) as **`gate_fail_rewind_text_only`**, and the target of a mechanical light rewind (§6.2, polyforge#260) as **`gate_fail_rewind_mechanical`**; when a light re-entry self-reports a structural fix with `needs_code_change: true`, the same write of the completed branch likewise archives that re-entry as **`gate_fail_rewind`** (reusing the same verdict and slot, see §6.2 light rewind); a step between the target and the gate that is invalidated as collateral is recorded as **`superseded_by_rewind`** (it did not itself fail). All four causes carry `rewind_gate` and all reset the candidate pointer.
2. **`infra_failure`**: appended by §6.3 item 2 — an auditable interruption record that does not change the step's status (it stays `in_progress`) and is also an input to the candidate-pointer recomputation.

Only a rollback archive produces `gate_fail_rewind` / `gate_fail_rewind_text_only` / `gate_fail_rewind_mechanical` / `superseded_by_rewind` / `root_cause_unaddressed` — the rollback of a gate FAIL verdict (§6.2), a light re-entry's structural self-report (likewise archived as `gate_fail_rewind`, reusing the same verdict and slot), or the bug-fix lane's one fix→root-cause rewind of a completed `root_cause_addressed: false` (`root_cause_unaddressed`,); every interruption that produced no verdict is an `infra_failure`. The two kinds of record coexist in time order.

### 6.4 The incomplete result <!-- §6.4 -->

1. A step may honestly produce `incomplete` (not a quality veto, but a failure to finish).
2. The driver puts the workflow into `blocked` with the current position unchanged; the runtime first seals and pushes the capsule, then puts the WI into aihub `blocked` with `SessionEnd(blocked)` (`waiting_on=owner`; `runtime/recover.go`).
3. The way out is left to a human: `pf resume <wi>` (continue: re-claim and continue at the original step) or `pf cancel <wi>` (give up) (`v2-converge.md#§6`).

### 6.5 The driver main loop <!-- §6.5 -->

The main loop is the Go driver inside the daemon (`driver/driver.go` `Run`), repeatedly calling `next_step_by_order` to pick the next step and dispatch it, until there is no next step:

1. A step is returned → dispatch (one short-lived harness process), and wait for its result envelope.
2. `completed` → mark `done`, back to 1.
3. `gate_failed` → §6.2; on entering `failed_gate`/`failed_rewind_exhausted` exit at once, else back to 1.
4. Infrastructure failure → §6.3, re-dispatch the same step in place.
5. `needs_input` → wait for a human to answer (during the wait there is no step process and no timing), and resume in place after the answer.
6. `incomplete` → §6.4, exit at once.
7. When empty is returned for the first time, check the state explicitly: already a failed terminal state → exit, never misjudged as complete; otherwise all done → the workflow is `completed`.

**The wrap-up mapping** (`runtime/recover.go`): `completed` → after the seal push, `SessionEnd(wrapped)`; `failed_gate`/`failed_rewind_exhausted` → after the seal push, `SessionEnd(failed)`; `blocked` → after sealing, `SessionEnd(blocked)`. When the terminal seal push fails, the close degrades to blocked (`v2-converge.md#§D`).

### 6.6 Budget <!-- §6.6 -->

- Structure: the step-level `budget: {wall_minutes: int}`, the only key; there is no requests/tokens dimension and no workflow-level budget (polyforge#147).
- Semantics: `wall_minutes` is an **estimate** — the bound T on that step's cumulative run time across all dispatches is T = max(3 × wall_minutes, the global `--step-timeout`, default 90m) (`WallEstimateFactor` in `driver/supervision.go`; `v2-converge.md#§2.4`). Under the default `--step-timeout` of 90m an estimate of ≤30 minutes has no effect, so the delivery bundles declare none; the release bundle's `release` step declares 45 (T = 135m).
- Exceeding T: the supervisor judges `step_timeout_long_task` / `step_timeout_slow_model` and handles it per `v2-converge.md#§2.3` (T is relaxed and persisted; a slow model switches candidate — only when the dying dispatch itself ran at least half of T and spent at least half of its own runtime waiting for the model, every other expiry being a long task ( D1); a long task retries the same model and is blocked after its second timeout).
