# UDS routes — the daemon's local HTTP face

The routes mounted by the daemon's local Unix-socket HTTP face
(`internal/polyforge/daemon/routes.go`). **Face** marks who calls the
route: `user` = the operator's CLI / watch tooling; `step` = a workflow
step's own process, identified by its process tree (every other caller
is refused); `task` = a one-shot task agent's process, identified by its
own markers (`PF_TASK_ID` + `PF_DAEMON_ID`,). Every mutating
(non-GET) route refuses a caller that belongs to a step agent's process
tree, or whose UDS peer credential is unavailable, with `DAEMON-403`
(polyforge#122 accident guard) — except the one step write the step route
scopes itself: `POST /step/call`.
A caller in a TASK agent's process tree is
refused `DAEMON-403` on EVERY mutating route with no allowlist at all —
`/step/call` included, and `/task/spawn` itself (no
recursion); its reads stay open, and the two `/task/memories` GETs are
scoped to its own project. The
concepts (daemon, claim, decision feed) are defined on the [concepts
page](../concepts.md); the failure codes of the recovery paths are the
[failure-codes page](failure-codes.md).

**Host and Cells.** One daemon process (the Host) serves one or more Cells
behind this one socket. Every route below is Cell-scoped unless marked
Host-level: the Host routes the request to the Cell its `X-PF-Profile`
header names, and a request without the header is served by the default
Cell — a permanent protocol default (an older client keeps working against
the default Cell), not a transition path. An unknown profile, or a
configured Cell with no live runtime, is `DAEMON-404` naming the profile
(and the expected `cli-<profile>.toml`) — never another Cell, never a
direct connection. The header only routes, it never authorizes: a request
from a step or task agent's process tree is served by the Cell that holds
its work item or task (the Host's own record), and one whose header names
another Cell is refused `DAEMON-403`; the CLI sends no header in a step or
task. Host-level: `GET /profiles`; `GET /status` without a
profile (the aggregate); `GET /decisions` and `POST /decisions/dismiss`
(the decision feed covers every Cell); `POST /ops/config` without a profile (every Cell's
auto switch and the Host ceiling); `POST /shutdown` (always the whole Host;
a request carrying a profile is refused `DAEMON-400`).

| Method | Path | Role | Face |
| --- | --- | --- | --- |
| POST | `/jobs/{wi}/answer` | The owner's words to the work item's current step — the **owner-message relay** (workflow contract v2 §5.2): `{answer_text, answered_by?}` (decoded strictly: a `question_id` or `option` — the v1 answer's fields, gone with workflow contract v2 change 19 together with the reserved `cancel` answer and the option selection — is refused `DAEMON-400`) is appended to the capsule's `runtime-state/asks.jsonl` first (`kind: reply` naming the open ask by `ask_at`, else `kind: message`; `step` and `spawn` the dispatch current when written), the `owner_message` event is emitted, and the words are delivered into the current step's agent — the live process (claude: a stream-json user message; pi: `prompt` with `steer`), framed with a neutral first line and the delivery marker `[pf-msg:<at>]`, or a resumed session (claude `--resume` / pi `--session`, a new `spawn_n`) when no process is alive; the answer is the ack `{status: accepted, at, kind, ask_at?, step, spawn_n, delivered, disposition?, note?}` — `delivered` true once the marker was observed in the harness's stream within 3 s (then the `delivered` line and event), `disposition` `started` / `queued` / `resume`. Nothing in the words is read: empty words and words over 64 KiB are refused `DAEMON-400`, a disabled Cell refuses `DAEMON-409`, and a terminal workflow answers `DAEMON-409` naming the path. A work item parked blocked or paused is not refused (workflow contract 4): it is woken in two requests with the owner's door between them. Without `wake`, the daemon names the park and records nothing — `{status: parked, park: blocked|paused, wake, step, spawn_n}`, `wake` the way it continues (`step_blocked`, `step`, `write_failed`, `paused`); the CLI then opens the door `pf resume` opens with the caller's own key (aihub's resume-blocked route, or `clean_pause` cleared); with `wake: <park>` the daemon records the words (the record first, as above), claims the work item and wakes the step concerned — its own session after its `blocked` hand-off, the failed step after two timeouts or three exits without a hand-off, the current step after a pause, a replay of the pending writes after `write_failed` (docs/reference/workflow-contract.md, "The daemon's reactions"). A park no agent can start (no usable model, a failed composition, a snapshot of another contract) is refused `DAEMON-409` with reason `WAKE_CANNOT_START`, naming why and `pf resume` / `pf cancel`, nothing recorded; a `wake` naming a park the work item is no longer in is refused `DAEMON-409` with reason `WAKE_PARK_CHANGED`. The daemon never opens a door with its own key. No new door and no permission tier: authority is reaching this daemon (the step-origin guard refuses step and task process trees). | user; step agents refused |
| POST | `/jobs/{wi}/claim` | Start a queued work item: enqueue its claim (`pf submit`; optional body `models`: the manual candidate list of `--models`) and answer the claim's verdict — when a slot is free the daemon claims at aihub before it answers, `{accepted, work_item_id, state: claimed, machine_id?, capsule_path?, missing_repos?}` (the placement once aihub answered the claim; the capsule clone may still run); otherwise the entry waits on the queue and the answer is `state: queued` with `queued_reason` (no free execution slot, aihub unreachable — retried with backoff —, or the daemon shutting down) and no placement, a refusal at that later claim being the `submit_rejected` event; an aihub refusal of the claim is aihub's own typed error (e.g. `CORE-409`, `extra.reason: DEPENDENCY_BLOCKED`) with nothing kept queued; or with `{"resume":true}` claim and start it now — the daemon half of `pf resume` on a blocked work item (the CLI lands aihub's resume-blocked door with the human's own key first). | user |
| POST | `/jobs/{wi}/resume-paused` | The live-holder half of `pf resume` on a paused work item (the CLI clears `clean_pause` at aihub first; this makes the online holder re-attach). | user |
| POST | `/jobs/{wi}/pause` | CLI close path: seal the job with reason `paused`. | user |
| POST | `/jobs/{wi}/wrap` | CLI close path: seal the job with reason `wrap` or `fail`. | user |
| GET | `/status` | Machine status: jobs (the current dispatch's open `pf step ask` — the capsule's `runtime-state/asks.jsonl` — as the job's question, `needs_input`; for a job in a dispatch, the current step's wait calls `wait_calls` / `wait_seconds`, absent when it has none; and — additive, — for a job in a dispatch, `context: {tokens, window, percent, model, as_of}`: the current step session's context-window usage, counted from the session transcript the step's harness writes locally (tokens the way the chat header counts that harness, the model id, the timestamp of the transcript record counted; `window` and `percent` only when the step's harness itself reported that model's context window during the dispatch — claude's `result.modelUsage` — the daemon holding no model catalog); each unknown field is absent and the whole object when nothing is known; numbers and the model id only — no transcript content, no credential read or passed on, no aihub call — so any local peer, a step process included, may read it like the rest of this route; and — additive — `retry_in_sec` / `retry_cause` while the job's current step waits a decided retry backoff before its next dispatch: whole seconds left, rounded up, and the death cause that owes it, derived from the same file; and — additive, — `verify_queue: {position, reason, since}` while the job's dispatch of a step declaring `resources: { admission: heavy }` waits in the heavy-run admission queue (`position` is 1-based in the admission order — priority, then first queued, then arrival), which holds no job slot: `queue.running` leaves such a job out), queue stats, auto switch and cap, the additive `version` (the running daemon's own build version, a daemon still running the binary an install replaced answers the old one; omitted by an older daemon), plus the additive `model_health` summary (window + current warnings). `queue.max_configured` is the daemon's last applied/startup cap (additive, read-only): `pf ops max` changes only `queue.max_concurrent`, so the pair distinguishes a temporary override from a stale file value. Without a profile this is the Host aggregate: the default Cell's machine facts, every Cell's `jobs` (each row carries its `profile`), the summed queue counts and `cells` — one `GET /profiles` row per Cell; with a profile, that Cell's own status (`execution_disabled` names a closed execution plane: while it is set, a submit, a task spawn, `POST /jobs/{wi}/resume-paused` and every answer are refused `DAEMON-409` naming the reason, and no queued entry starts, nor does the restart reconciliation attach an operator-paused record whose `clean_pause` was cleared; `pf resume` reads it here before it clears `clean_pause` at aihub; queries, cancel, pause/wrap and work already running are unaffected). | user |
| ANY | `/aihub/{path...}` | The data-plane proxy: every AIHub business call of the CLI (`file`, `queue`, `cancel`, `recall`, `remember`, `memory`, `msg`, `users`, `api-keys`, `machines`, `projects`, `backup`) is forwarded — method, **escaped** path, query and body — through the routed Cell's effective connection with that Cell's credential, and the Hub's status and body come back unchanged. One body is not forwarded as sent: a work-item create (`POST /api/v1/work-items`) whose `bundle_name` names a lane of the project's lane set (the built-in lanes and the user lanes of the workspace the project maps to) declaring `exclusive: true` goes to the Hub with `"exclusive": true`, so the Hub refuses it `CORE-409` `OPEN_ON_BUNDLE` while another work item of the project on that lane is not finished; any other create — another lane, no lane, a lane the set does not carry or refuses, a body that is no JSON object — is relayed byte for byte. The path is relayed byte for byte (`r.URL.EscapedPath()` minus the `/aihub` mount prefix): the proxy decodes no segment, so an escaped reserved byte (`%23`, `%3F`, `%2F`, `%25`) in a `<project>#<seq>` reference or a project name survives to the Hub, which is the one place that decodes it. Only `/api/v1/…` paths are forwarded (never the Hub's `/web/` console or `/git/` mount); no queue slot, no cache, no retry. An unreachable Hub is `DAEMON-503` naming the Cell (a side-effecting request's outcome is reported unknown and never resent) and marks the Cell degraded until its next success; a Hub `401` (the Cell's credential refused) is relayed unchanged and degrades the Cell too. A degraded Cell (also after a failed heartbeat) stops its automatic claims; its running work keeps the existing recovery, `GET /profiles` and the `GET /status` aggregate show `state: degraded` with the reason, and other Cells are unaffected. | user; step and task processes refused `DAEMON-403` (agents hold no AIHub access) |
| GET | `/profiles` | The Host's Cell registry: `{dir, profiles: [{profile, file, state, valid, reason, server (normalized), workspaces, data_dir, machine_id, heartbeat, execution_disabled, cell_max_concurrent_jobs, max_concurrent, running, pending, draining, pending_change}], index: [{profile, workspace}]}`. `machine_id` is the Cell's own identity (its `cells/<profile>/daemon-id`), `heartbeat` its last heartbeat outcome (`ok`, `error: …`, or empty before the first beat). `cell_max_concurrent_jobs` is the Cell's applied (persisted) optional ceiling — the file value as of the startup or the last reload that changed it, absent when unset — and `max_concurrent` the effective one the Cell admits by after that reload (the applied value clamped to the Host's current ceiling; unset = that ceiling); lowering it kills no running job. `draining` is true while a verified same-identity `api_key` rotation waits for the Cell to go safe-idle (`pending_change` names it — every row carries it, `""` once nothing is pending; new submits, automatic claims and task spawns are refused `DAEMON-409` meanwhile and nothing is queued; a job record, a queued entry or a running one-off task keeps the Cell from switching; queries/answers/resume/cancel go on). `index` is the EFFECTIVE workspace index — what the Host actually serves; a pending change's newer disk mapping is not in it — and is what the CLI resolver matches a cwd against. No credential is ever carried. | user; step and task processes refused `DAEMON-403` |
| POST | `/profiles` | `pf cell add\|repair`: body `{"profile"}` — apply that named Cell's file now: add an absent Cell, repair an invalid or removed one, reload a serving one in place, with no Host restart. An invalid file or a conflict with a serving Cell is refused `DAEMON-409` and the registry keeps serving; a same-name restore over another AIHub than the one recorded in the Cell's state dir (`identity.json`) is refused `DAEMON-409` with the new-profile route, and a file `api_key` other than the Cell's effective one is adopted only after the identity check (same Hub user; else reported, not used). | user; step and task processes refused `DAEMON-403` |
| PATCH | `/profiles/{profile}` | `pf cell update`: re-apply the Cell's file (same rules as `POST /profiles`). | user; step and task processes refused `DAEMON-403` |
| DELETE | `/profiles/{profile}` | `pf cell remove`: stop the Cell — refused `DAEMON-409` while it holds any work (a job record of any state, a queued submit, a running task), refused `DAEMON-400` for `default`; its state directory (history, identity) is kept and it reads `removed`. | user; step and task processes refused `DAEMON-403` |
| POST | `/profiles/{profile}/cleanup` | `pf cell cleanup`: the permanent cleanup of a removed Cell. Body `{confirm}`; without `confirm` (or with another value: `DAEMON-400`) it only answers the impact `{profile, state_dir, state_dir_exists, decisions, applied:false}` — the retained state dir and the Host decision feed's entries naming the profile; with `confirm` equal to the profile it deletes all of them (`applied:true`) so nothing can route to it; a repeat is a no-op. Refused `DAEMON-400` for `default`, `DAEMON-409` for a still-configured Cell (remove first). CLI-only: the page offers no control. | user; step and task processes refused `DAEMON-403` |
| GET | `/models` | The read-only model+effort × step profile over the events-retention window (`pf ops models`; `--json` re-emits this document). Read-only, no write face, no config, no mutation: any non-GET on the path is refused (405). Reachable by any local UDS peer, including a step process, exactly like `GET /status`. The payload carries only model/effort names, step ids, counts, rates, durations, the window and the current warnings — no paths, prompts, transcripts, envelopes or credentials. | user; step processes may read |
| POST | `/ops/config` | `pf ops auto on\|off` / `pf ops max N`: body `{"auto":bool,"max":N}` (either or both). Without a profile: the Host (every Cell's auto switch, the Host ceiling); with one: that Cell only. | user |
| POST | `/config/reload` | With `X-PF-Profile` naming a non-default Cell, the Host applies that profile like `POST /profiles` (add, repair, reload in place). Otherwise `pf config set/unset` (after its write) and `pf config reload`: re-read the daemon's own `cli.toml` through the shared validator and apply each key by its class (live / next-claim / connection-change / restart-only); a changed `server` or another user's `api_key` is refused `DAEMON-409` naming the new-profile route, a same-identity rotation is reported `pending-drain` and switches once the Cell is idle; an `api_key` removed from the file is reported `pending-restart` (never shadowed by the persisted credential: from the next Host start the Cell holds none and refuses AIHub business, `DAEMON-409`), and a same-user key given to a Cell holding none is `applied` at once. A failure applies nothing, answers a typed error naming the key and leaves the daemon up. Local Unix socket only; a step agent's process tree is refused `DAEMON-403` by the step-origin guard. | user; step agents refused |
| POST | `/config/check` | `pf config set/unset`'s pre-write preflight: a proposed `[workspace]` mapping, checked against the held jobs (a removal/re-route that would strand an in-flight work item is refused, listing it) without writing anything. Local Unix socket only; step agents refused `DAEMON-403`. | user; step agents refused |
| GET | `/decisions` | Host-level: `pf watch decisions` and Pi Web's Polyforge panel — the machine's decision feed over every Cell, `{"decisions":[…], "attention": N}`, newest first, bounded to the newest 300 entries and none older than 14 days. An entry is `{id, at, kind: work_item\|task, profile, wi, slug, class, source, phrase, question_id, repo, task_id, text, attention, resolved, dismissed, replied, replied_at}` (empty strings omitted, booleans always present); `class` is `needs_input`, `blocked`, `failed`, `completed`, `canceled`, `paused`, `terminal`, `step_dead`, `candidates_exhausted`, `carrier_push_failed`, `submit_rejected`, `submit_dropped`, `daemon_restarted` or `superseded` (this machine released the work item — another session holds it, or a local close the hub never confirmed) for a work item, `completed`, `failed`, `capped` or `interrupted` for a task (its `text` = the report's tail). OPEN = `attention && !resolved && !dismissed`; the top-level `attention` counts the open entries. A step's `pf step ask` (the `awaiting_owner` event) is recorded under the same class `needs_input` with `source: awaiting_owner` and `question_id` = the ask's stamp; that entry resolves when the step's result is accepted (`step_done`, `gate_verdict`, `incomplete`) or a new ask supersedes it. The owner's reply naming that ask (`owner_message` with `kind: reply` and `ask_at` = the entry's `question_id`) marks the entry `replied: true` with `replied_at` (the reply's stamp) and `attention: false` — no longer open, still unresolved: the daemon does not judge whether the words answered; an interjection (`kind: message`) or a reply naming another ask changes nothing. The daemon resolves entries itself (an `answered` event resolves the work item's open `needs_input`; a new `job_started` every earlier open entry of the work item; a later status the earlier `needs_input` / `blocked` / `paused` ones, and a final one (completed, failed, canceled) the work item's `carrier_push_failed` ones; the runtime's release records the reason the close actually ended with — a wrap whose push failed ends `blocked`, a record dropped at restart records aihub's status — superseding an earlier end of another class; a blocked or paused work item with no local job is re-read at aihub every 60 s; open entries are never pruned). | user; any local peer, including a step or task agent, may read (like `GET /status`) |
| POST | `/decisions/dismiss` | Host-level: `pf watch dismiss`, body `{"ids":[12,13]}` or `{"all":true}` → `{"dismissed":N}` — marks open entries dismissed (the human has seen them); nothing about the work item changes. | user; step and task processes refused `DAEMON-403` |
| POST | `/machine/role` | `pf ops role interactive\|runner [--force\|--if-unset]`: body `{"role":"interactive"\|"runner","force":bool,"if_unset"?:bool}` → `{role, force, applied, profile}` — the Cell's machine-role request on its next heartbeat; `force` takes the interactive role over from the machine that holds it (supersession); `if_unset` (the session-start adapters') applies only while no operator chose a role explicitly (`applied:false` otherwise); an explicit choice is kept in the Cell's data dir (`machine-role.json`) across restarts; `force` with `if_unset` is `DAEMON-400`. Cell-level. | user; step and task processes refused `DAEMON-403` |
| POST | `/shutdown` | Host-level: shut the whole Host down — every Cell stops its agents and saves each job's task-repo WIP, then the process exits (≤30s). A request carrying `X-PF-Profile` is refused `DAEMON-400` (a Cell has no shutdown of its own). | user |
| GET | `/jobs/{wi}/watch` | `pf watch <wi> --once`: per-work-item snapshot (status, step, pending question — the current dispatch's open `pf step ask` read from the capsule's `runtime-state/asks.jsonl`, its `id` and `asked_at` the ask's own stamp — and, while the workflow is blocked, `execution.blocked: {kind, step, reason, required_action, evidence?}` (`kind` `incomplete` = the step handed off `blocked` — its section of `artifacts/handoff.md` says why, and an owner message resumes its session; `write_failed` = a pending `pf step hub` write of a step round that handed off `done` could not be made — fix the cause, then an owner message or `pf resume` replays the writes not yet done; `contract` = the capsule's lane snapshot targets another workflow contract version — resuming parks it again: cancel it and file it anew (docs/upgrade.md names the section); `driver` = the driver parked it — a supervision bound, a model no candidate can replace), never shown as a question; `execution.rewinds: {agent, max_rewinds, owner}` (the automatic rewinds counted toward the bound, the bound, and the owner-cited rewinds charged to no budget; absent when the workflow is unreadable); events (a dispatch waiting for the heavy-run admission is the `verify_queued` event here, and the job row's `verify_queue` of `GET /status`)). A WI running/blocked on another fresh machine is resolved through a signed 5 s progress query and the answer carries `holder_machine`; stale/deregistered/unsupported holders answer CORE-504/410/501. The relayed snapshot is cached per WI for 10 s, so remote progress refreshes at most every 10 s (a status or `updated_at` change at aihub refreshes at once; errors are not cached). A step process may read its own local snapshot but is refused DAEMON-403 before a remote query leaves this daemon. The job's `origin` is `{kind, owner}` — kind `chat` (an interactive submit) or `auto`; no chat id is recorded. The in-flight dispatch's `progress` block carries — additive, — the same `context: {tokens, window, percent, model, as_of}` as `GET /status`'s job row (`window` / `percent` only when the harness reported the window; numbers and the model id only; a step process reading its own snapshot sees it too). | user |
| GET | `/jobs/{wi}/artifact?path=<relpath>` | `pf watch <wi> --artifact <relpath>`: read a capsule `artifacts/` file (relative, no `..`/absolute/symlink escape, ≤4 MiB) through the same decision chain, never cached; queued/terminal answers a pointer only. A step process is refused DAEMON-403. | user |
| POST | `/messages/{id}/analyze` | `pf msg analyze <id>`, body `{caller_id}`: spawns ONE task in the task lane — the message's project, else the first mapped project; models from `steps.<project>.task` (else `.default`); the read-only tool profile; a fixed 5 min / 100000-token budget; the caller as reporter — blocks until it is terminal (6 min wait bound) and answers `{message_id, task_id, project, type, summary, suggested_actions, model, duration, reply_draft?}` only to the caller. No analyzer lock: the lane's two slots bound it (slot-full `DAEMON-409`, nothing created); no task chain `DAEMON-400`, unmapped project `DAEMON-412`; a `failed`/`capped`/`interrupted` task `DAEMON-500` naming the state. The task record (whole prompt, message body included) is readable through `/task/show` under the task store's retention; a dropped client ends only the wait. A step or task process is refused DAEMON-403; no loop starts it. | user |
| POST | `/messages/{id}/prompt` | `pf msg prompt <id>`, body `{caller_id}`: built like `/messages/{id}/analyze` — ONE task in the task lane (the anchored work item's project, else the first mapped project; `steps.<project>.task` models, else `.default`; the read-only tool profile; the fixed 5 min / 100000-token budget; the caller as reporter), blocking until it is terminal (6 min wait bound). The task prompt carries the message, at most the 10 most recent earlier messages of its conversation (one hub page below its seq, oldest first), the replied-to message and the anchored work item; a refused conversation or reply read is the caller's typed refusal before any task. Answers exactly `{prompt, task_id, model, duration}`; slot-full `DAEMON-409`, no task chain `DAEMON-400`, unmapped project `DAEMON-412`, a `failed`/`capped`/`interrupted` task or a blank report `DAEMON-500` naming the state and the task id, with no prompt text. The task record is the only stored copy. A step or task process is refused DAEMON-403; no loop starts it. | user |
| POST | `/step/call` | `pf step` (workflow contract 4): body `{verb, args}`, verb `handoff`, `ask`, `recall`, `memory.show`, `remember` or `hub.<get\|list\|file\|attrs\|wrap-attrs\|batch>`. The daemon resolves the calling step from its process tree, appends the call to the capsule's `runtime-state/step-calls.jsonl` before running it (a ledger it cannot write runs nothing) and what it came to after (`ok`, `refused`, `failed`; an accepted hand-off's record; the hub writes recorded pending). `handoff` appends a daemon-stamped section to `artifacts/handoff.md`; `recall` searches the calling step's own project's memories (search only — no browse mode: an empty `q` is refused before any forward, and the call takes no cursor, sort or project), `memory.show` reads one memory of that project, `remember` writes the wrap summary (type `experience.wrap`, attributed to the step's own work item, idempotent per step dispatch); the hub reads go to aihub on the daemon's key scoped to the step's project; the hub writes are only recorded pending (an `attrs` write is made later through aihub's signed `PATCH /work-items/{id}/attrs` on the daemon's machine key — the only way a step reaches that route); a hub verb outside the step's whitelist, or an `attrs` key outside its `hub.attrs`, is `DAEMON-403`. | step |
| POST | `/task/spawn` | `pf task spawn`: start one one-shot task agent; the id is answered immediately. A step or task process tree is refused `DAEMON-403` (no recursion). The task always gets the standard tool surface: the read-only profile is daemon-internal (the analyze route's), never a body key. A Cell whose execution is disabled refuses every spawn `DAEMON-409` `execution is disabled on this Cell: <reason>` before any record, slot or run (the analyze/prompt spawns share the same admission); its queries, cancel and running work are unaffected. While the Cell's connection rotation is pending (`draining` on `GET /profiles`) a spawn is refused `DAEMON-409` naming the pending connection rotation, nothing queued, and a running task keeps the Cell from switching. | user; step and task processes refused |
| GET | `/task/list` | `pf task list`: every known task (id, project, state, age, and `prompt_summary` — the prompt's first non-empty line, at most 120 code points; `reporter` — the spawn-time snapshot of the self-asserted caller id's display name as a human member of the task's project, else `machine`, never re-read from aihub; `report_tail` — the report's last non-empty line, at most 200 code points (`…` + the last 199 when longer), `""` while running or for an empty report, never the error; no full report and no full prompt — those stay on `/task/show`). | user; any local peer, including a step or task agent, may read (like `GET /status`) |
| GET | `/task/show/{id}` | `pf task show`: one task's metadata and full report. | user; any local peer may read (like `GET /status`) |
| POST | `/task/cancel/{id}` | `pf task cancel`: end a running task (it ends `interrupted`). | user; step and task processes refused |
| GET | `/task/memories/search` | A task agent's `pf recall`: search the calling task's own project's memories (the daemon holds the key). Search only — no browse mode: an empty `q` is refused before any forward and `after`/`sort` are never forwarded (browse is the human direct-aihub `pf recall`). | task |
| GET | `/task/memories/{id}` | A task agent's `pf memory show`: read one memory of the calling task's own project. | task |
